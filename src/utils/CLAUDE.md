# src/utils/CLAUDE.md

Utility layer: settings, build-mode flag, P4K extraction, enhancement support modules. See the root `CLAUDE.md` for project context.

## Files

- `settings.py` — `AppSettings` wraps a backend that is either `QSettings` (registry mode, default) or `JsonSettings` (portable mode — see `build_mode.py` / `json_settings.py`). User data lives under the configured root (default `Documents\Smart Citizen\`, or `<exe-dir>/data/` portable) plus `{active_channel}\`. The backend is the single source of truth for all paths and prefs. Owns canonical paths (`get_user_data_dir()`, `get_cache_dir()`, `get_user_ini_path()`, `get_backups_dir()`, `get_dataforge_cache_dir()`, which creates the folder it returns and raises when it cannot, and `get_dataforge_cache_leaf(channel)`, the same per-channel folder named without creating it, for a check that must leave the disk alone such as the guard on the queued old-cache cleanup, #486. Every check that only reads the cache (its status, freshness and build key) goes through the leaf, so a cache folder Windows refuses or one on a drive that is gone reads as not extracted instead of stopping the app opening (#494). Only code about to write there calls `get_dataforge_cache_dir()` (the migrator, `MainWindow._run_dataforge_extraction`, `MainWindow._run_p4k_extraction` for the global.ini extraction's working folder beside the cache, and `ConfigTab._maybe_apply_cache_change` for a newly picked folder), which `tests/test_cache_dir.py::TestOnlyWritersCreateTheCache` enforces. `get_default_dataforge_cache_base()` is the base used with no override, whatever the override is now, so the Config tab can name it when a reset to it fails. The module-level `cache_folder_failure(error)` reads why a cache folder could not be made, so the Config tab and the start of an extraction pick their message the same way (#494): `CACHE_FOLDER_UNREACHABLE` for a `FileNotFoundError` (WinError 2, 3, 15, 53, 67) or a drive that is not ready (WinError 21, `ERROR_NOT_READY`, a card reader or optical drive with nothing in it, which Python raises as a `PermissionError`), `CACHE_FOLDER_REFUSED` when Windows denied permission, read by #490's `pak_extractor.windows_refused()` (ERROR_ACCESS_DENIED, ERROR_NETWORK_ACCESS_DENIED or no Windows code), and `CACHE_FOLDER_UNUSABLE` for anything else (the rest of the range Python raises as `PermissionError`, a write-protected or failing drive or a file another program holds, a name Windows does not take, a path through a file, a full drive, a path Windows cannot parse, WinError 161 `ERROR_BAD_PATHNAME`, and a path too long for it, WinError 206 `ERROR_FILENAME_EXCED_RANGE`, which a deep cache folder gets where long paths are not turned on: Python raises those two as a `FileNotFoundError`, so they are read first), whose message gives `windows_reason(error)`: the error's `strerror`, already in the user's Windows language, or the whole error when it has none) and a chain of one-shot migrators run every launch (all idempotent, all no-op in portable mode since there's no registry to migrate from):
  - `migrate_legacy_settings()` — seeds `[global, user]` defaults for fresh installs.
  - `migrate_remove_retired_url_sources()` — 1.0 prune of contracts/components/ships/commodities/gear from upgrader registries. Only when the stored path is a URL; local-path overrides survive.
  - `migrate_global_to_p4k_local()` — rewrites `global` from URL to the local cached `base.ini`.
  - `migrate_registry_appname()` — `SC Localization Editor` → `Smart Citizen` registry tree.
  - `migrate_docs_folder_rename()` — `Documents\SC Localization Editor\` → `Documents\Smart Citizen\`.
  - `migrate_installer_data_move()` (#455): a YES on Setup's OneDrive warning leaves the folder the data was in as `pending_data_move_from`. This moves Smart Citizen's own folders out of it (`user_ini_manager.move_owned_user_data`) into the data folder in use, before `migrate_game_path_to_channel_layout` and the DataForge cache migrator so they work on the moved data. It deletes the value first, so the move is tried once and what stays behind is reported, never retried, and returns the `DataMoveResult` that `src/main.py` hands to `MainWindow._report_installer_data_move`. `pending_data_move_from` is in `PROFILE_EXCLUDE_KEYS`.
  - `migrate_data_to_documents()` — `AppData\Roaming\...` → configured data root.
  - `migrate_game_path_to_channel_layout()` — 0.9.3+ flat layout → per-channel.
  - `migrate_dataforge_cache_to_local()` — 1.x move of the DataForge XML cache from `Documents\...\cache\dataforge\` to `AppData\Local\...`, escaping OneDrive / Defender / Search Indexer per-file hooks on the ~31k extracted XMLs. With a `CACHE_DIR` override, leaves an already-correct path alone; otherwise queues the old tree via `set_pending_cache_cleanup()` for removal after successful re-extraction, avoiding a pre-window copy. The no-override migration stages its move under `dataforge.migrating` so interrupted cross-volume copies cannot masquerade as complete caches.

  Also owns the **settings backup** filter (Config tab's Export / Import Settings; the zip I/O lives in `settings_profile.py`). `export_all_values()` lays down `profile_default_values()` first and writes stored values over the top, so a backup describes the user's whole configuration rather than only what differs from stock. That matters because a setting is not written to the backend until the user changes it: before #383 anything still at its default had no key to enumerate, so it never reached the backup and an import could not put a preference *back* to its default (rename a Mission Label, import an older backup, and the rename survived — same for theme, UI mode, the favourites prefix, and every checkbox). `profile_default_values()` is a function, not a constant, because `merge_hierarchy` is declared further down the class body and the theme default needs a deferred `src.gui.theme` import; it composes from the same maps the getters read (`_MISSION_HEADER_SETTING`, `_MISSION_FIELD_SETTING`, `_MISSION_TITLE_TAG_SETTING` / `_MISSION_TITLE_TAG_DEFAULTS`, `ENHANCEMENT_LABELS`, `DEFAULT_TAG_CONFIGS`) so those can't drift. `PROFILE_DEFAULT_EXCLUDE_KEYS` / `_PREFIXES` hold the deliberate carve-outs — per-machine state and user *data* whose "unset" default would make an import destructive rather than restorative (the install paths, since clearing one forces re-detection that can land on the wrong install per #370; `owned_items`; the starter-blueprint seed marker, which describes the owned set, so `import_values` applies it only from a backup that carries `owned_items` and resets it when that backup predates it (#416); the blueprint log watermark; the test-plan keys). `PROFILE_EXCLUDE_KEYS` still filters machine-local keys ahead of all this. `tests/test_settings_profile_defaults.py::TestNoDrift` replays every no-arg getter against a recording backend and fails if a defaulted key is neither materialised nor excluded, so a new setting can't silently reintroduce the bug.

  Also owns the language layer (2.0, #30): `get_selected_language()` / `set_selected_language()` (registry key `SELECTED_LANGUAGE`), `get_available_languages()` (hides languages whose `ui.json` is a stub), `SC_LANGUAGE_IDS` + `get_sc_language_id()` (app folder name `portuguese_br` → game id `portuguese_(brazil)`, used in both the Localization path and `g_language`), `get_base_ini_path(language)` (English: `{channel}\cache\base.ini`; others: `{channel}\cache\lang\{language}\base.ini`), `get_global_source_base_ini(language)` (the base.ini the `global` merge source reads: the language's own when the active channel's cache has it, otherwise the English one, #502) and `sync_global_source_path(context)` (points a file-backed `global` source there and leaves a URL source alone; `main()` runs it at every start and `MainWindow._sync_canonical_source_paths` after a channel switch or a data-folder change, and a successful global.ini extraction points the source at the same file: all three but startup used to point every language at the English base.ini, and the bundled `languages/<language>/global.ini` overlays are empty, so the table, and the next Apply, turned English), `get_enhancements_dir(language)` (always `get_base_ini_path(language).parent`, so enhancements sit next to the base.ini they were generated from), `get_/set_enhancements_stamp()` (`.dataforge_stamp` marker recording the DataForge build a language's enhancements came from; missing/stale forces regen on switch; it and `.tag_config_stamp` are written in one step and read with a short retry through `atomic_io.py`; both setters take `folder=`, the folder a generation captured when its run started, as `get_dataforge_build_key(forge_dir)` takes its cache folder), `invalidate_enhancements_stamp(folder)` (empties `.dataforge_stamp` just before the generator's `main()`, so a run cut off or failed from there reads as out of date), `enhancements_built_from_current_dataforge(language)` (the stamp is set and matches the current build key: the one definition of "current" for the startup check, the Generate button and the language switch), and `get_language_base_url()` + `get_/set_language_source_override()` (download URL from a per-user override, falling back to the bundled `languages/sources.json`).
- `json_settings.py` — `JsonSettings`: file-backed key-value store mirroring the four `QSettings` methods `AppSettings` uses (`value` / `setValue` / `remove` / `sync`). Writes on every set, thread-safe via `RLock`. Used when `build_mode.IS_PORTABLE` is true. We do **not** use `QSettings(IniFormat)` — it mangles slash-prefixed keys (e.g. `enhancements/categories/foo/enabled`) into nested groups and can't round-trip them; `tests/test_json_settings.py` locks this.
- `build_mode.py` — single `IS_PORTABLE` flag. Default `False`; `scripts/build/build_exe.py --portable` writes a generated `src/utils/_build_info.py` (git-ignored) with `IS_PORTABLE = True` that `build_mode.py` picks up via `try: from src.utils._build_info import IS_PORTABLE`. The build script deletes the generated file post-build so the source tree is never committed in portable state. Tests flip the flag via `monkeypatch.setattr`; production code only reads it.
- `locpack_exporter.py` — pure-Python writer for the **Export Loc-Pack** toolbar action. Zips the applied `global.ini` from the game's localization directory into `SmartCitizen-LocPack-{channel}-{YYYYMMDD}.zip` (compression 9; bare `global.ini` at the zip root so recipients drop it straight into `StarCitizen\<channel>\data\Localization\english\`). The Qt button lives on `MainWindow.export_locpack`; this module owns the I/O so the logic is testable without Qt.
- `tag_builder.py` — pure-Python (Qt-free) **Tag Builder** engine, new in 1.4.0. Drives the bracketed annotations on component (`[CLASS-Sx-grade]`), missile, ship-weapon, commodity and FPS armor (#492, `[H]` weight class) names in generated enhancement INIs, plus the mission-title route. One tab per `CATEGORIES` entry, in that order (Armor last). A `TagConfig` per category captures element order, per-element style (e.g. `Short`/`Medium`/`Long`), separator, enclosing brackets, placement, and the variant mapping of its mapped kinds (class/type/ordinance/damage/label/usage/collection/weight; `DEFAULT_KIND_MAPPINGS`). The armor `weight` keys must match the class names the generator's `_armor_weight` returns; `render_tag(config, values)` produces the bracketed string. `DEFAULT_TAG_CONFIGS` is calibrated so an unconfigured user sees the pre-1.4.0 format byte-for-byte (`tests/test_tag_builder.py::TestDefaultBackwardsCompat`). Consumed by the generator (`scripts/generate_enhancements_ini.py`, with a `sys.path` shim so it still runs as a standalone CLI from `scripts/`) and the Enhancements tab live preview. Persisted by `AppSettings.get_tag_config()` / `set_tag_config()` / `get_all_tag_configs()` as one JSON blob per category under `tag_builder/{category}/config` — flat slash-key so `JsonSettings` round-trips it.
- `dataforge_diff.py` — manifest-based diff cache for the ~31k-file DataForge XML cache. **Nothing calls it now** (perf proposal): `extract_dataforge` no longer writes the manifest, and `EnhancementsGeneratorWorker` no longer asks it before a run (2.5.0). Each hashed the whole cache (measured on a real 31,202-file, 1.2 GB cache: about 4.5 s after every extraction and 3.5 to 4.5 s before every generation, far longer on a hard drive with the files out of memory), and the generator has not used the answer since ded720a. The module and its tests stay until #495 decides whether to delete it or use it again. `update_manifest(cache_dir)` snapshots SHA-256 + mtime of every XML; `dirty_categories(cache_dir)` returns the set of enhancement categories whose source subtree changed since the last snapshot (`None` = no prior manifest → run all; empty set → skip all). See *The DataForge diff manifest is neither written nor read* below. Both wrap `cache_dir` via `win_paths.win_long_path()` at entry (see that file) — this is where a deep portable install path's `WinError 3` actually got reported, since the hash sweep's `stat()`/`open()` calls had no long-path protection until then. `CATEGORY_SUBTREES` maps each enhancement category to the DataForge paths it reads and **must stay in sync with `DATAFORGE_KEEP_SUBPATHS` in `pak_extractor.py`**. The hash sweep runs in a `ThreadPoolExecutor` — work is I/O-bound (Defender / Search Indexer / OneDrive intercept every file open on Windows).
- `updater.py` — per-source GitHub downloads. Drives the auto-update workers that refresh cached source INIs from their GitHub URL. Post-1.0 the only URL-backed source is `global` (`base.ini`); the four legacy URL sources are gone (replaced by local Data.p4k extraction).
- `app_updater.py` — *separate* from `updater.py`. Polls `GET /repos/Osiris-DevWorks/smart-citizen/releases/latest` and compares `tag_name` to local `VERSION.TXT`. As of #211 (2.1.2) the check runs on every launch (one unauthenticated call, far under GitHub's 60-req/hr cap) and gates the rest of startup in `MainWindow` until it resolves. Also owns `pick_installer_asset()` (finds the `SmartCitizen-*-Setup.exe` release asset) and `AppUpdateDownloadWorker` (streams the installer to `%TEMP%\SmartCitizen-Update\` with progress; `.part`-then-rename so a partial download is never runnable). The install/relaunch side lives in `MainWindow._launch_installer_and_quit` + `installer.iss`'s `/AUTOUPDATE=1` relaunch, which runs in `CurStepChanged` at `ssPostInstall` right after the registry writes (not as a `[Run]` entry, which Setup would run first).
- `pak_extractor.py` — P4K extraction pipeline: `unp4k.exe` (extracts Game2.dcb) → `unforge.exe` (converts to entity XMLs). After unforge writes the full DataForge tree to the run's working folder, `_cache_filtered_records()` puts only the `DATAFORGE_KEEP_SUBPATHS` subtrees (what the generator reads) into the persistent cache, which halves its file count. When the working folder is beside the cache each subtree is moved with one folder rename (#484), so the working folder has half as much left to delete. In `%TEMP%`, or when a rename is refused (another program holds a file under it past a 0.7 s retry, `_MOVE_RETRY_DELAYS`), the subtree is copied, and a rename that finds the drive full is not retried. The renames use `os.rename`, never `os.replace` or `shutil.move`. A new read path in the generator needs an entry in `DATAFORGE_KEEP_SUBPATHS`; `tests/test_pak_extraction.py::TestDataForgeKeepList` locks the contract. The cache layout itself (`raw/libs`, `foundry/records`) is named once here as `DATAFORGE_LIBS_SUBPATH` / `DATAFORGE_RECORDS_SUBPATH` and joined by every reader, and so is the generator's lookup pickle folder, `DATAFORGE_LOOKUPS_SUBPATH` (`.lookups`), which `_cached_lookup` writes and `EnhancementsGeneratorWorker` sweeps for leftover temps (`TestCacheLayoutNamedOnce` fails on any quoted `"raw"` or `"foundry"` path segment elsewhere in `src/` or `scripts/`, whether joined with `/`, passed to `Path()` or `joinpath()`, or written as `"raw/libs"`, and on any string starting `".lookups"`, a versioned `".lookups-v2"` included). `extract_dataforge()` and `dataforge_cache_is_fresh()` both wrap `dataforge_cache_dir` via `win_paths.win_long_path()` at entry — see that file.

  **Working folder and stopping (#471).** The tools used to work in `tempfile.TemporaryDirectory()` under `%TEMP%`, so a full run's ~2 GB (Game2.dcb plus ~62k XMLs) hit the system drive whatever cache folder the user had picked, and closing the app left unforge running on its own while Python's exit-time cleanup failed under it. Now each DataForge run works in its own `dataforge.extracting-XXXXXXXX` folder beside the cache leaf (`_scratch_location`: same drive, outside the leaf that step 3 wipes, inside the channel folder the uninstaller's wipe covers). It falls back to `%TEMP%\SmartCitizen-DataForge-XXXXXXXX` for a network share, OneDrive, a removable or network drive, or a run folder over 190 characters (unp4k's working folder must stay within what CreateProcess accepts; unforge itself was measured fine with 368-character output paths). The tools are handed plain paths (`win_plain_path`), while Python's own reads of their output stay long-path safe. The global.ini extraction (the English global.ini alone, ~10 MB, see *What the tools are asked for and what they print* below) follows the same rules in its own `globalini.extracting-XXXXXXXX` folder (`scratch_near=` the DataForge cache folder, which `MainWindow._run_p4k_extraction` resolves on the main thread and replaces with `None`, meaning `%TEMP%`, when that drive is offline), so neither extraction writes to `%TEMP%` unless a fallback applies. The global.ini extraction also falls back to `%TEMP%` when the folder beside the cache can't be made (permissions, Controlled Folder Access, a read-only drive), since it only ever needed `%TEMP%` before. DataForge does not: its cache writes go to that same drive and would fail anyway, after a minute of unforge. `_begin_scratch` sweeps both places and opens the run's folder for either extraction. `_make_run_folder` makes it with one `os.mkdir` per random name (the prefix and `_MKDTEMP_RANDOM_CHARS`, 8 hex characters from `secrets.token_hex`), not `tempfile.mkdtemp` (#490). On the Python 3.11 the release builds use, mkdtemp takes a `PermissionError` for a name that may be taken and tries again up to `os.TMP_MAX` (2,147,483,647) times, about 39 hours against a folder that refuses, so the extraction looked stuck and the fallback above never started (Python 3.14.6 stops at 20). Only a taken name is tried again (a `FileExistsError`, or a `PermissionError` for a name that is there, which a folder Windows is still deleting can give), up to `_SCRATCH_NAME_ATTEMPTS` (10) names, then `FileExistsError`. A `PermissionError` making the folder or opening its marker becomes `WorkingFolderRefusedError` in `_begin_scratch` (`_folder_refused_error`: the Windows error at WARNING, then a `tr()` message that names the folder and says Windows denied permission there; Python raises the whole range of Windows errors 19 to 36, a write-protected or failing drive or a file another program holds, as `PermissionError` too, so `windows_refused()` counts only ERROR_ACCESS_DENIED, ERROR_NETWORK_ACCESS_DENIED or no Windows code as a refusal, and any other gets `extract.folder_unusable`, which gives `windows_reason()`, the error's own text in the user's Windows language, with no advice about permissions), unless the global.ini fallback moves the work first, so global.ini reports a refusal only when `%TEMP%` refuses too. Beside the cache the advice is to check the folder's permissions, allow Smart Citizen through Controlled folder access, or choose another DataForge cache folder (`extract.folder_refused_fix_cache`). In `%TEMP%` it leaves out the cache folder, which may not help there (`extract.folder_refused_fix`). Any other OSError (a drive that is gone, a path too long) behaves as before: DataForge raises it, and global.ini moves to `%TEMP%` on it. Step 3's wipe deletes the cache leaf and makes it again in the folder that holds it. Beside the cache, making the working folder in that same folder has already shown it takes a new folder; in `%TEMP%` nothing has, and a folder that refuses new folders let the run delete the old cache and then fail to make the new one with a raw `PermissionError` (#494). So a DataForge run in `%TEMP%` calls `_require_cache_can_be_remade` right after `_begin_scratch`, before any tool runs: it makes one empty folder there with `_make_run_folder` and the DataForge prefix (making the folder that holds the cache folder first when it is missing) and removes it with `os.rmdir`, and a `PermissionError` becomes `_folder_refused_error` for that folder with the cache advice, the old cache untouched. Any other OSError is raised as it is, as above. It runs after the free-space check, so a full drive still gets its own message. A test folder that will not go is logged at WARNING and left for a later DataForge run's sweep, which takes it as an unmarked leftover once it is 10 minutes old. A run holds an `.in_use` marker open, and `_sweep_stale_scratch` at the start of every extraction deletes only leftovers whose marker it can delete (a crash or hard kill releases it) or that have no marker and are over 10 minutes old (a run that died before making one, or a removal that got part-way), so a live run in another window is never touched. The window also runs it with the DataForge prefix, off the GUI thread (`StaleWorkingFolderSweepWorker`, perf proposal), once a session beside the active cache folder at startup and beside a queued old cache folder after `_cleanup_pending_old_cache`, because a working folder now outlives its run while it is deleted in the background, and one a crash left there would otherwise wait for the next extraction beside the same cache folder (see `src/gui/CLAUDE.md`). `_run_tool` replaces `subprocess.run`: it polls `communicate(timeout=...)` so a `should_cancel()` request kills the tool within a quarter of a second, and raises `ExtractionCancelled` (deliberately not a `RuntimeError`) before any exit code is read. `extract_dataforge` also checks for a stop just before the old cache is wiped (the last point that leaves it untouched) and after the stamps (the cache is complete, but the stop is reported so nothing chains into generation), so a stop never leaves a half-filled cache: nothing checks for a stop between the wipe and the stamps, so the renames, their retries and any fallback copy always finish. unforge's `foundry/records` folder is checked before the gate, so output without it, or with none of the kept subtrees in it, keeps the old cache. The working folder goes in a `finally` (`_close_scratch` logs every OSError, never raising it over the real outcome), unless a successful run hands it over (see below). The workers feed `should_cancel` from `QThread.isInterruptionRequested`; `tests/test_extraction_working_folder.py`, `tests/test_extraction_stop.py` and `tests/test_folder_refused_strings.py` lock all of this.

  **Deleting the working folder after the run (perf proposal).** Both big deletes of a DataForge run (the old cache, about 31,000 files, and what unforge wrote that the cache does not keep, about 31,000 more) used to come before generation could start. Beside the cache, step 3 no longer wipes the old cache: once its stamps are gone, `_set_old_cache_aside` renames it into the run's working folder (`_SET_ASIDE_CACHE_NAME`, one rename on one drive, with #484's retries for a held file), so nothing can read it as fresh there. It is wiped in place, as before, in `%TEMP%` (another drive), when a stamp would not go, when the rename is refused, and on a drive that has room only once it is gone: `_require_room_for_new_cache` returns True when it counted the old cache's room (or the drive is short and that room could not be measured). A copy after a refused move deletes a set-aside cache first (`_cache_filtered_records(before_copy=)`), so it gets the room the #482 checks counted. A caller that passes `defer_cleanup` (the DataForge worker) is handed a `WorkingFolder` for a run that saved and stamped the new cache with no stop pending, and not on such a tight drive, instead of the folder being deleted before `extract_dataforge` returns; every other outcome still deletes it in the `finally`, except that a stop arriving right after the hand-over still raises `ExtractionCancelled` with the folder already handed over, and the caller then owns it (`DataForgeExtractWorker._finish` deletes it). The folder is beside the cache folder, or in `%TEMP%` when the work was there, never inside the cache folder. `_close_scratch`, which `WorkingFolder.delete` uses, deletes everything but the `.in_use` marker while the marker is held, then the marker and the folder, so another window's sweep never touches a folder still being deleted, and a crash part-way leaves the marker file for the next sweep to take at once (on the Python 3.11 the release builds use, rmtree deleted the marker first). An entry that will not go (a file another program holds under `Data`) does not stop the others: each entry is tried, the first error is logged once, and the set-aside old cache still goes, with the marker file left for the next sweep. `WorkingFolder.release` closes the marker and leaves the folder to that sweep. Who deletes it, when, and how closing waits is in `src/gui/CLAUDE.md`. `tests/test_extraction_working_folder.py` (`TestTheOldCacheIsSetAside`, `TestTheWorkingFolderGoesAfterTheRun`) locks this.

  **Free space (#482).** Each extraction checks free space in `_begin_scratch`, through its `check_space` callback, after both sweeps (a crashed run's leftover is gone before it is counted) and before any folder is made (a drive with nothing left still gets the clear message, not a raw `os.mkdir` error). The input checks come first, so a missing tool is still reported ahead of a short drive. `_require_free_space` counts each part on the volume it lands on: for DataForge (`_dataforge_needs`) the working folder (Game2.dcb plus unforge's whole tree, ~62k files) where the run works and the new cache (~31k files) at the leaf, less the old cache when the leaf holds a stamped one (`.p4k_mtime` and `raw/libs`, the same probe as the Config tab's), which the run sets aside or wipes, and frees before any copy (`_credit`: at least its bytes and at least a cluster per file, as the new cache is charged); for global.ini (`_global_ini_needs`) its work, one English global.ini (`_GLOBAL_INI_WORK_BYTES` is `_BASE_INI_BYTES`, 11 MiB in one file, measured at 10.1 MB), and base.ini on the data folder's drive. Parts on one volume (`os.stat().st_dev`, which gets subst drives and mounted folders right) are added together, and each part is measured at its nearest existing folder, because the Windows calls fail on one that does not exist yet. `_space_for` adds 15% and one cluster per file (`GetDiskFreeSpaceW` on the volume, 4096 when unknown), so a 128 KiB-cluster exFAT stick asks for far more, and free is the smaller of `shutil.disk_usage` and `GetDiskFreeSpaceExW`'s caller figure (NTFS quotas). Each volume gets one INFO line, `Free space on D: is N bytes, about M needed (4096-byte clusters)`, named by its mount path from `GetVolumePathNameW` (`_drive_label`, the drive in the path's text, only when that call fails). The figures are the `_DATAFORGE_*`, `_GLOBAL_INI_*` and `_BASE_INI_BYTES` constants, measured on LIVE 4.10 with GB read as GiB: a first run on an NTFS drive needs about 4.2 GiB, a re-extract over a complete cache about 3.0 GiB. The figures stay sized for a copy of the new cache even though the work beside the cache moves it (#484): a rename is refused while another program holds any file under the subtree, and that subtree is then copied after the wipe, so only a copy-sized check keeps that fallback from running out of room. The old cache's credit holds although beside the cache it is now set aside rather than wiped, and freed only after the run (perf proposal): a run that needed that room to pass the check before the wipe wipes it in place as before (`_require_room_for_new_cache` returns True), a move takes no new room, and a copy deletes a set-aside cache first (`before_copy`). Every probe is best effort: one that fails, or a part with no existing folder above it (a drive that is gone), is logged at WARNING and skipped, so measuring never refuses a run. `_require_room_for_new_cache` checks again just before the old cache is wiped (the drive can fill while unforge runs), from one walk of what unforge really wrote, and counts the old cache's allocation as room when the drive is short, except files the directory listing marks `OFFLINE`, `RECALL_ON_OPEN` or `RECALL_ON_DATA_ACCESS` (OneDrive online-only files, `_ONLINE_ONLY_ATTRIBUTES`, `_walk_files(local_only=True)`), which free nothing. When it refuses, it adds this run's working folder's allocation to both figures if that folder is on the cache's volume (`st_dev`), so the box matches the drive once the working folder is deleted, and it never names less than a retry's up-front check asks that drive for (the new cache, plus the working folder when it was there). Its INFO line (`DataForge run wrote ... The new cache is ...`) is how the constants get checked against a real run. A copy (in `%TEMP%`, or after a refused rename) passes `copy_function=_copy_file_checked`, which turns a full drive (ENOSPC, or winerror 39, 112 or 1295, of which Python maps only 112 to ENOSPC) into `_DiskFullDuringCopy`, not an OSError, so `copytree` stops at once instead of folding it into `shutil.Error` and copying on, and a rename that finds the drive full raises `_DiskFullDuringCopy` too; a full drive anywhere from the cache's mkdir to its stamps becomes the "cache incomplete" message, both stamps are removed (`_remove_stamps`, after any failure in that stretch and before the wipe; the mtime stamp alone reads as fresh), and the unstamped leaf is offered for a re-extract at startup. A shortage raises `NotEnoughSpaceError`, a `RuntimeError` (never an OSError, so `_begin_scratch`'s `except OSError` cannot read it as a folder that cannot be made) with a `tr()` message that names each short drive with what it has (rounded down) and needs (rounded up), and the advice that fits it: the cache advice for DataForge's cache drive, the temp advice for DataForge's work in `%TEMP%`, and the plain advice for every global.ini part, because a global.ini run can be in `%TEMP%` for reasons the temp advice does not list. It sits in `ANTICIPATED_EXTRACTION_ERRORS` with `P4kLockedError`, `DataForgeTimeoutError` and `WorkingFolderRefusedError` (#490), which the workers report at WARNING (see `src/gui/CLAUDE.md`). The global.ini extraction moves its work to `%TEMP%` only when the work's own drive beside the cache is short, as it does when that folder cannot be made. That shortage and the move are both INFO lines, with nothing at WARNING: `check_space`'s third argument (`movable`) hands the folder beside the cache to `_require_free_space(movable=)`, which then raises the private `_WorkDriveShort` that `_begin_scratch` catches. A short data folder drive alone (base.ini's part, which no move helps) refuses at once, at WARNING, naming only that drive with the plain advice. When the drive beside the cache and `%TEMP%`'s are both short, the refusal names `%TEMP%`'s drive only. DataForge never falls back: its cache needs that drive anyway. `tests/test_extraction_working_folder.py` (`TestFreeSpaceCheck` and the global.ini tests) and `tests/test_free_space_strings.py` lock this.

  **Data.p4k being written (#516).** Both extractions call `_refuse_if_p4k_being_written` right after the input checks, before any folder or tool. It raises `P4kLockedError` (the same "wait for the launcher" message as the locked case, logged at WARNING) when `_p4k_has_writer` finds another handle that can write the archive (a `CreateFileW` read with `FILE_SHARE_READ` only fails with a sharing violation; the game and an idle launcher only read, so they pass) or `_p4k_changed_recently` finds its modified time inside `_P4K_RECENT_WRITE_SECONDS` (120; a future time does not count).   **A cache folder that is a link (#491).** A user can make the DataForge cache folder itself a junction or a symbolic link, usually to keep the cache on another drive. `shutil.rmtree` refuses a link and deletes nothing, and `robust_rmtree`'s error hook used to call the refusing `os.path.islink` again, which returns instead of raising, so the wipe read as done: every re-extract then met the old cache after unforge and failed with a raw `FileExistsError`, and Clear Cache and the queued old-cache cleanup reported a folder gone that was not. Nothing is deleted through a link now. `linked_folder_target(path)` reads a link by rmtree's own rule (a symbolic link, or a junction, `IO_REPARSE_TAG_MOUNT_POINT`, which is also how a drive mounted in a folder looks) without following it, so a link whose target is gone counts, and names the folder at its end (`os.path.realpath`, without the long-path prefix, or the link's own text from `os.readlink` when realpath raises, as it does for an error it does not expect such as a network that cannot be reached, or "" when neither can be read); any other reparse point, such as a OneDrive folder, is not a link to it. `robust_rmtree` raises `LinkedFolderError` for a link, also one whose target is gone (it asks `os.path.lexists`, not `exists`), at once and never again: an `OSError`, so every caller's `except OSError` reports it. A folder that only holds a link is still deleted, the link with it and its target kept. `extract_dataforge` asks `linked_cache_folder_error(leaf)` before anything runs, which logs the link at WARNING and returns `CacheFolderIsLinkError` (in `ANTICIPATED_EXTRACTION_ERRORS`, so one box), its `extract.cache_folder_is_link` naming the folder and where it leads and saying to choose that folder as the DataForge cache folder in the Config tab, with the old cache and the link kept. `MainWindow._run_dataforge_extraction` asks the same before any worker exists (see `src/gui/CLAUDE.md`). Only the cache folder itself counts: a link higher up the path is an ordinary path to the wipe. `tests/test_linked_cache_folder.py` locks this.

  **Deleting a tree (perf proposal).** `robust_rmtree` deletes the working folder (and the old cache set aside in it), the old cache where a re-extract wipes it in place or deletes a set-aside one before a copy, the cache for Clear Cache and the queued old-cache cleanup. One file at a time it took about 220 us a file on a real run (6.9 s for the ~31k files unforge wrote that the cache does not keep, and a re-extract also wipes the ~31k-file old cache). Each attempt now runs `_delete_files_first` first: it walks the tree on one thread and hands the plain files to `_DELETE_THREADS` threads (`min(8, os.cpu_count())`) in batches of `_DELETE_BATCH` (64), each clearing the read-only bit and trying once more when a delete fails, and leaves anything that still will not go. The threads are daemon threads, started one per batch up to `_DELETE_THREADS` and handed at most twice that many batches ahead through a bounded `queue.Queue`, so Python's exit never waits for them. A `ThreadPoolExecutor`'s threads were joined at exit only after every queued batch had run, and the walk queues nearly the whole tree while the first deletes run, so a close past `_stop_workers_for_close`'s 180 s deadline kept the hidden process alive until the tree was gone, or for ever behind one delete that blocked. Once Python begins to exit (`_EXITING`, set by `atexit`) the walk stops and the threads drop the batches still queued: `shutil.rmtree` goes on with the rest on the calling thread, which Python does not wait for either (the delete worker's `QThread`), and what the process does not finish stays with the working folder's marker file for the next sweep, since `_close_scratch` deletes the marker last. Where Python starts no new thread (while it exits, from 3.12) rmtree deletes it all, one file at a time. Any other exception in a thread (an OSError never gets out of one) stops the walk and is raised on the calling thread, its failure list emptied as it is raised: the list and the exception's traceback held each other, which kept everything in those frames alive until the cyclic GC ran, a working folder's marker included, so a sweep straight after skipped that folder. `shutil.rmtree` then runs as before over what is left, the folders bottom-up and any file the threads could not delete, one at a time with the read-only hook, so every error a caller sees is still rmtree's, raised by the hook. Measured on this PC on a synthetic 30,000-file tree shaped like the DataForge records: 3.9 to 5.1 s one at a time, 1.3 to 1.4 s with 8 threads (16 were no faster). The daemon threads are as fast as the pool they replaced: medians of 1.31 s against the pool's 1.37 s and 4.08 s one at a time, over six interleaved rounds. The walk follows rmtree's own rule (`_is_link`, which `linked_folder_target` uses too): it goes into a real folder only, never a junction or a symbolic link, and deletes only plain files, so a link handed in is still refused by rmtree's hook with `LinkedFolderError` and nothing deleted, and a link inside is still unlinked by rmtree without being followed (#491). The whole-tree retry keeps its backoff (0.2, 0.4, 0.8, 1.6 and 3.0 s between six attempts), but nothing waits after the last attempt: the last failure used to sleep up to 3 s before raising, and the leftover sweep's second attempt slept for nothing. `tests/test_robust_rmtree.py` locks this.

  **base.ini freshness (perf proposal).** `base_ini_is_fresh(p4k_path, base_ini)` says whether the extracted English base.ini is still current, by #209's rule for the DataForge cache: Data.p4k's byte size, not its modified time, which the RSI launcher's file verification moves on an ordinary game launch. The old rule (Data.p4k newer than base.ini) asked to extract global.ini again (20 to 26 s) at the next start, channel switch or data folder change after nothing more than playing, and lit the Config tab's Extract button. `extract_global_ini` reads Data.p4k's size before unp4k runs, so a Data.p4k that changes during the run reads as changed afterwards (`extract_dataforge` now reads the stat for its `.p4k_mtime` and `.p4k_size` stamps there too: read after unforge, a patch landing during a DataForge run made the old build's cache read as current), and `_write_base_ini_stamp` records it with base.ini's own size in `BASE_INI_STAMP` (`.base_ini_stamp`, beside base.ini). base.ini's size ties the stamp to the base.ini it was written for, because the files in that cache folder come and go on their own: Clear Cache deletes `*.ini` and leaves the stamp, and a data folder change copies a file only where the new folder has none. A stamp for another base.ini, or one that is not two numbers, counts as no stamp, and then the old rule decides, so an upgrade asks for nothing the old rule would not have asked for, and reads a patch as the old rule reads it at that check. When the old rule reads fresh (Data.p4k no newer than base.ini, which normally means untouched since base.ini was written), its size is recorded there and then, and the next launcher touch needs no extraction first. A patch the old rule misses (one that left Data.p4k's modified time no newer than base.ini's) is recorded the same way, so it stays missed until the next patch changes the size, where the old rule would have asked after the next game launch: nothing else tells a launch from such a patch. `extract_global_ini` removes the old stamp once the new base.ini is in place and before it writes the new one (one that will not go is logged at WARNING; removed before the copy, a copy that failed left the old base.ini with no stamp, and the modified times could read it fresh against a patched Data.p4k), and a new stamp that cannot be written is logged at WARNING and fails nothing, so the old rule then decides. Kept past such a failed write, the old stamp spoke for the new base.ini whenever the two were the same size, and after a patch that left global.ini as it was, base.ini read stale straight after every extraction. Both callers use it: `MainWindow._check_p4k_freshness` and `ConfigTab._refresh_p4k_status` (see `src/gui/CLAUDE.md`). As with #209, a patch that left Data.p4k's size exactly as it was would go unnoticed. `tests/test_base_ini_freshness.py` locks this.

- `win_paths.py` — `win_long_path(path)`: prefixes a path with `\\?\` (or `\\?\UNC\` for a network share) so Windows file APIs accept it past the legacy 260-char `MAX_PATH`, with no machine-wide config needed (unlike the inbox "Enable Win32 long paths" policy, which requires admin rights and isn't guaranteed on for any given user — issue #221). - `atomic_io.py`: writes a file in one step. `atomic_writer(path, mode)` (`"w"` or `"wb"`) writes to a `.sc-XXXXXXXX.tmp` file beside the target, flushes, syncs and closes it, then swaps it in with `os.replace`, so a run cut off by a close or a crash leaves the old file or the new one, never part of one. `atomic_write_text()` wraps it. The temp is made by `_create_temp_beside`, not `tempfile.mkstemp`: on Python 3.11, which the release builds use, mkstemp retries a PermissionError up to `os.TMP_MAX` (2^31) times on Windows, so a folder that refuses new files (Controlled Folder Access, a read-only share) hung the write for about two days. Only a name already taken is retried, up to `TEMP_CREATE_ATTEMPTS` (20) times, and any other error raises at once, naming the target rather than the temp, so the error dialog and the log say which file could not be written. Only a PermissionError from the swap is retried, for about 1.3 s (on Windows any other open handle on the target blocks `os.replace`, even one that shares delete). Any failure removes the temp, keeps the old file and raises. It never falls back to writing in place, which is what let readers see partial files. `read_bytes_retrying()` is the reader's side: a reader that opens a file during a swap gets PermissionError for a moment, retried for about 0.15 s. `sweep_stale_temps(folder)` removes temps over 10 minutes old, which only a hard kill between the temp and the swap leaves; `EnhancementsGeneratorWorker` sweeps the INI folder and the lookup pickle folder (`pak_extractor.DATAFORGE_LOOKUPS_SUBPATH`, `.lookups`) at the start of each run, and `dataforge_patcher` sweeps the folder of every record it patches, rewritten or not. Text mode writes the bytes `Path.write_text` wrote (UTF-8, no BOM, CRLF on Windows). Used by the generator's `write_ini` and lookup pickles (through its `src` shim), `mining_catalog`'s `write_crafting_index` and `load_crafting_index`, the stamp setters and getters in `settings.py`, `dataforge_patcher.py` and `ini_io.read_ini_text`. Stdlib only, Qt-free and settings-free, so a test can run it in a child on the base interpreter. `tests/test_atomic_io.py` locks it.
- `ini_io.py`: `read_ini_text(path)`, the INI text reader `parse_ini_file` and `merge_ini_files` share (#251). - `sco_digit_reader.py` — Qt-free SCO digit reader. `read_signature(width, height, red, digit_px)` thresholds the red channel (drops wide horizontal runs so a bright panel edge can't merge with the digits), chains digit-sized blobs (8-connected, so the planet HUD's thin "3" stays whole; labelled by joining pixel runs, which the regex engine finds, never pixel by pixel in Python: the reader runs every 250 ms while the game plays, and a per-pixel loop cost 3-5x the CPU) into rows, keeps only rows shaped `N,NNN` / `NN,NNN` (a comma blob before the last three), drops coloured text (red "WARNING", green "UNKNOWN") when given the `green` and `blue` channels: a row needs `MIN_WHITE_FRACTION` of its inked pixels to have green and blue at `WHITE_LEVEL` of their red within `FRINGE_PX` sideways (tolerates the chromatic fringes and the orange planet panel, which a plain green:red ratio rejected), and matches each glyph to its nearest reference glyph on a coarse 4x7 grid. A decoded reading needs a mean match of `MIN_READING_SCORE` (keeps desktop clocks/dates silent while alt-tabbed); an undecoded one needs every digit at `MIN_UNDECODED_SCORE`. ## Design decisions

### Portable vs registry build mode
One source tree, two build variants:
- **Registry (default)** — `python build_exe.py`. Settings → Windows Registry via `QSettings`. Data root → `Documents\Smart Citizen\` (or whatever the user configured).
- **Portable** — `python build_exe.py --portable`. Settings → `<user_data_dir>/config.json` via `JsonSettings`. Data root → `<exe-dir>/data/` when frozen, `<repo-root>/portable_data/` unfrozen for testing.

The build-time switch is `build_mode.py::IS_PORTABLE`. The `--portable` build writes a generated `_build_info.py` (git-ignored) with `IS_PORTABLE = True` before PyInstaller runs and deletes it after, so the source tree is never committed in portable state. The repo on disk always shows `IS_PORTABLE = False`.

At runtime the flag flips exactly two things:
1. `AppSettings._backend` — `QSettings` or `JsonSettings`. The `QSettings` surface `AppSettings` touches is tiny (`value` / `setValue` / `remove` / `sync`), so the `json_settings.py` shim is a focused mirror, not a full re-implementation.
2. `AppSettings.get_user_data_dir()` — Documents path vs `<exe-dir>/data/`.

Registry-tree migrators no-op in portable mode. When editing settings-touching code, use `AppSettings` helpers — reaching for `QSettings` directly breaks portable mode silently.

### The DataForge diff manifest is neither written nor read
`dataforge_diff.py` snapshotted every XML in the DataForge cache after each extraction (`update_manifest`), and `dirty_categories` reports which enhancement categories' source XMLs changed since that snapshot. Generation used the answer to skip unchanged categories until ded720a (2026-05-11) removed the narrowing, and since then every run generates every enabled category. `EnhancementsGeneratorWorker` still called `dirty_categories` at the start of every run, hashing the whole cache for an answer nothing read, which only lengthened the window a close could cut off. 2.5.0 removed that call, and `tests/test_enhancements_stale_startup.py::test_generation_no_longer_hashes_the_cache` keeps it out. The extraction no longer writes the manifest either (perf proposal): `update_manifest` hashed the whole cache after every extraction (about 4.5 s on a real 31,202-file cache, far longer on a hard drive) for that same unread answer, and nothing calls either half now. The module and its tests stay, and the rule below still holds, until #495 decides whether to delete it or use it again. `CATEGORY_SUBTREES` maps each category (`ships`, `components`, `ship_weapons`, `fps_weapons`, `missions`, `commodities`, `journal`) to the DataForge paths it reads. **A new enhancement category or a change to existing subtree coverage still needs updates in both `CATEGORY_SUBTREES` here AND `DATAFORGE_KEEP_SUBPATHS` in `pak_extractor.py`**: the former says what each category reads, the latter what goes into the cache. They are not the same list (subtree filters can be finer than keep filters) but must agree on coverage.

### Parallel pipelines report progress via ProgressSink
Lookup builders and enhancement output generators run in parallel worker threads, except that a stage runs inline on the calling thread whenever its pool would get only one worker, `min(max_workers, number of jobs) == 1`. The lookup stage and the generator stage each make that check on their own, so a single job runs inline at any worker count, and everything runs inline when `main()` gets `max_workers=1`. The GUI's `EnhancementsGeneratorWorker` always passes `max_workers=1`, so a GUI run is always inline. A pool of one inside the worker's `QThread` is the shape #389's heap corruption traced to (see `scripts/generate_enhancements_ini.py`). They share one `ProgressSink` (`progress_sink.py`) so the UI shows one determinate progress bar. Never call `QProgressBar.setValue()` from workers — go through the sink so updates are coalesced and throttled on the main thread.

### Tag-config hand-off to the enhancements worker
`EnhancementsGeneratorWorker.__init__(categories, tag_configs)` (in `src/gui/workers.py`) takes tag-builder configs as a plain dict, not from inside the worker thread. `MainWindow.run_enhancements_pipeline` calls `AppSettings.get_all_tag_configs()` on the **main thread** and hands the result to the worker, so the generator code path never touches a live `QSettings` / `JsonSettings` handle from a background thread. Don't shortcut this — `QSettings` is thread-safe but the JSON shim's file write is point-in-time, and we want the generator's input frozen at pipeline-launch time so a mid-run tab edit can't half-rewrite an enhancement INI.
