# src/utils/CLAUDE.md

Utility layer: settings, build-mode flag, P4K extraction, enhancement support modules. See the root `CLAUDE.md` for project context.

## Files

- `settings.py` — `AppSettings` wraps a backend that is either `QSettings` (registry mode, default) or `JsonSettings` (portable mode — see `build_mode.py` / `json_settings.py`). User data lives under the configured root (default `Documents\Smart Citizen\`, or `<exe-dir>/data/` portable) plus `{active_channel}\`. The backend is the single source of truth for all paths and prefs. Owns canonical paths (`get_user_data_dir()`, `get_cache_dir()`, `get_user_ini_path()`, `get_backups_dir()`, `get_dataforge_cache_dir()`) and a chain of one-shot migrators run every launch (all idempotent, all no-op in portable mode since there's no registry to migrate from):
  - `migrate_legacy_settings()` — seeds `[global, user]` defaults for fresh installs.
  - `migrate_remove_retired_url_sources()` — 1.0 prune of contracts/components/ships/commodities/gear from upgrader registries. Only when the stored path is a URL; local-path overrides survive.
  - `migrate_global_to_p4k_local()` — rewrites `global` from URL to the local cached `base.ini`.
  - `migrate_registry_appname()` — `SC Localization Editor` → `Smart Citizen` registry tree.
  - `migrate_docs_folder_rename()` — `Documents\SC Localization Editor\` → `Documents\Smart Citizen\`.
  - `migrate_data_to_documents()` — `AppData\Roaming\...` → configured data root.
  - `migrate_game_path_to_channel_layout()` — 0.9.3+ flat layout → per-channel.
  - `migrate_dataforge_cache_to_local()` — 1.x move of the DataForge XML cache from `Documents\...\cache\dataforge\` to `AppData\Local\...`, escaping OneDrive / Defender / Search Indexer per-file hooks on the ~28k extracted XMLs.

  Also owns the **settings backup** filter (Config tab's Export / Import Settings; the zip I/O lives in `settings_profile.py`). `export_all_values()` lays down `profile_default_values()` first and writes stored values over the top, so a backup describes the user's whole configuration rather than only what differs from stock. That matters because a setting is not written to the backend until the user changes it: before #383 anything still at its default had no key to enumerate, so it never reached the backup and an import could not put a preference *back* to its default (rename a Mission Label, import an older backup, and the rename survived — same for theme, UI mode, the favourites prefix, and every checkbox). `profile_default_values()` is a function, not a constant, because `merge_hierarchy` is declared further down the class body and the theme default needs a deferred `src.gui.theme` import; it composes from the same maps the getters read (`_MISSION_HEADER_SETTING`, `_MISSION_FIELD_SETTING`, `_MISSION_TITLE_TAG_SETTING` / `_MISSION_TITLE_TAG_DEFAULTS`, `ENHANCEMENT_LABELS`, `DEFAULT_TAG_CONFIGS`) so those can't drift. `PROFILE_DEFAULT_EXCLUDE_KEYS` / `_PREFIXES` hold the deliberate carve-outs — per-machine state and user *data* whose "unset" default would make an import destructive rather than restorative (the install paths, since clearing one forces re-detection that can land on the wrong install per #370; `owned_items`; the blueprint log watermark; the test-plan keys). `PROFILE_EXCLUDE_KEYS` still filters machine-local keys ahead of all this. `tests/test_settings_profile_defaults.py::TestNoDrift` replays every no-arg getter against a recording backend and fails if a defaulted key is neither materialised nor excluded, so a new setting can't silently reintroduce the bug.

  Also owns the language layer (2.0, #30): `get_selected_language()` / `set_selected_language()` (registry key `SELECTED_LANGUAGE`), `get_available_languages()` (hides languages whose `ui.json` is a stub), `SC_LANGUAGE_IDS` + `get_sc_language_id()` (app folder name `portuguese_br` → game id `portuguese_(brazil)`, used in both the Localization path and `g_language`), `get_base_ini_path(language)` (English: `{channel}\cache\base.ini`; others: `{channel}\cache\lang\{language}\base.ini`), `get_enhancements_dir(language)` (always `get_base_ini_path(language).parent`, so enhancements sit next to the base.ini they were generated from), `get_/set_enhancements_stamp()` (`.dataforge_stamp` marker recording the DataForge build a language's enhancements came from; missing/stale forces regen on switch), and `get_language_base_url()` + `get_/set_language_source_override()` (download URL from a per-user override, falling back to the bundled `languages/sources.json`).
- `json_settings.py` — `JsonSettings`: file-backed key-value store mirroring the four `QSettings` methods `AppSettings` uses (`value` / `setValue` / `remove` / `sync`). Writes on every set, thread-safe via `RLock`. Used when `build_mode.IS_PORTABLE` is true. We do **not** use `QSettings(IniFormat)` — it mangles slash-prefixed keys (e.g. `enhancements/categories/foo/enabled`) into nested groups and can't round-trip them; `tests/test_json_settings.py` locks this.
- `build_mode.py` — single `IS_PORTABLE` flag. Default `False`; `scripts/build/build_exe.py --portable` writes a generated `src/utils/_build_info.py` (git-ignored) with `IS_PORTABLE = True` that `build_mode.py` picks up via `try: from src.utils._build_info import IS_PORTABLE`. The build script deletes the generated file post-build so the source tree is never committed in portable state. Tests flip the flag via `monkeypatch.setattr`; production code only reads it.
- `locpack_exporter.py` — pure-Python writer for the **Export Loc-Pack** toolbar action. Zips the applied `global.ini` from the game's localization directory into `SmartCitizen-LocPack-{channel}-{YYYYMMDD}.zip` (compression 9; bare `global.ini` at the zip root so recipients drop it straight into `StarCitizen\<channel>\data\Localization\english\`). The Qt button lives on `MainWindow.export_locpack`; this module owns the I/O so the logic is testable without Qt.
- `tag_builder.py` — pure-Python (Qt-free) **Tag Builder** engine, new in 1.4.0. Drives the `[CLASS-Sx-grade]`-style annotations that prefix component / missile / ship-weapon names in generated enhancement INIs. A `TagConfig` per category captures element order, per-element style (e.g. `Short`/`Medium`/`Long`), separator, enclosing brackets, placement, and the class/ordinance/damage variant mapping; `render_tag(category, values, cfg)` produces the bracketed string. `DEFAULT_TAG_CONFIGS` is calibrated so an unconfigured user sees the pre-1.4.0 format byte-for-byte (`tests/test_tag_builder.py::TestDefaultBackwardsCompat`). Consumed by the generator (`scripts/generate_enhancements_ini.py`, with a `sys.path` shim so it still runs as a standalone CLI from `scripts/`) and the Enhancements tab live preview. Persisted by `AppSettings.get_tag_config()` / `set_tag_config()` / `get_all_tag_configs()` as one JSON blob per category under `tag_builder/{category}/config` — flat slash-key so `JsonSettings` round-trips it.
- `dataforge_diff.py` — manifest-based diff cache for the ~28k-file DataForge XML cache. `update_manifest(cache_dir)` snapshots SHA-256 + mtime of every XML; `dirty_categories(cache_dir)` returns the set of enhancement categories whose source subtree changed since the last snapshot (`None` = no prior manifest → run all; empty set → skip all). Both wrap `cache_dir` via `win_paths.win_long_path()` at entry (see that file) — this is where a deep portable install path's `WinError 3` actually got reported, since the hash sweep's `stat()`/`open()` calls had no long-path protection until then. `CATEGORY_SUBTREES` maps each enhancement category to the DataForge paths it reads and **must stay in sync with `DATAFORGE_KEEP_SUBPATHS` in `pak_extractor.py`**. The hash sweep runs in a `ThreadPoolExecutor` — work is I/O-bound (Defender / Search Indexer / OneDrive intercept every file open on Windows).
- `updater.py` — per-source GitHub downloads. Drives the auto-update workers that refresh cached source INIs from their GitHub URL. Post-1.0 the only URL-backed source is `global` (`base.ini`); the four legacy URL sources are gone (replaced by local Data.p4k extraction).
- `app_updater.py` — *separate* from `updater.py`. Polls `GET /repos/Osiris-DevWorks/smart-citizen/releases/latest` and compares `tag_name` to local `VERSION.TXT`. As of #211 (2.1.2) the check runs on every launch (one unauthenticated call, far under GitHub's 60-req/hr cap) and gates the rest of startup in `MainWindow` until it resolves. Also owns `pick_installer_asset()` (finds the `SmartCitizen-*-Setup.exe` release asset) and `AppUpdateDownloadWorker` (streams the installer to `%TEMP%\SmartCitizen-Update\` with progress; `.part`-then-rename so a partial download is never runnable). The install/relaunch side lives in `MainWindow._launch_installer_and_quit` + `installer.iss`'s `/AUTOUPDATE=1` Run entry.
- `pak_extractor.py` — P4K extraction pipeline: `unp4k.exe` (extracts Game2.dcb) → `unforge.exe` (converts to entity XMLs). After unforge writes the full DataForge tree to a temp dir, `_copy_filtered_records()` copies only the `DATAFORGE_KEEP_SUBPATHS` subtrees (what the generator reads) to the persistent cache — halves cache file count and cuts copy/rmtree wall time. A new read path in the generator needs an entry in `DATAFORGE_KEEP_SUBPATHS`; `tests/test_pak_extraction.py::TestDataForgeKeepList` locks the contract. `extract_dataforge()` and `dataforge_cache_is_fresh()` both wrap `dataforge_cache_dir` via `win_paths.win_long_path()` at entry — see that file.
- `win_paths.py` — `win_long_path(path)`: prefixes a path with `\\?\` (or `\\?\UNC\` for a network share) so Windows file APIs accept it past the legacy 260-char `MAX_PATH`, with no machine-wide config needed (unlike the inbox "Enable Win32 long paths" policy, which requires admin rights and isn't guaranteed on for any given user — issue #221). The DataForge XML tree's long CIG-authored filenames routinely cross this limit once nested under a deep portable/tester install path (or a zip double-extracted into an already same-named folder), and `WinError 3` ("cannot find the path specified") fires even though the file exists. No-op on non-Windows and on already-prefixed paths. Every DataForge-cache consumer wraps its own root path once at its entry point so every path it derives (via further `/` joins, `rglob`, `ET.parse`, etc.) inherits long-path safety for free — see `pak_extractor.py` (copy/cleanup + the two entry points above), `dataforge_patcher.py` (patch target reads), `dataforge_diff.py` (`update_manifest`/`dirty_categories` — where the follow-up crash was actually reported, the post-extraction snapshot/hash pass), and `scripts/generate_enhancements_ini.py`'s `main()` (wraps `forge_dir` once, covering 20+ `ET.parse` sites and 18+ `rglob` walks). `tests/test_win_long_path.py` locks all of the above.
- `user_ini_manager.py` — saves user-modified entries to `user.ini` (plain `key=value`, no sections) via `save_user_ini(entries, path)`; coordinates with `ImportConflictDialog` for external imports. Exports `should_autosave_user_ini(entries, path)`: a v1.3.0 regression guard called from `MainWindow.closeEvent`. v1.3.0 used to re-write `user.ini` from the in-memory entry list on close, which on a load mismatch (channel drift after migration, transient I/O) truncated a populated `user.ini` to 0 bytes. The guard refuses the write when nothing is modified but the on-disk file is non-empty. Exports the **rotating user.ini backup** safety net (#172): `backup_user_ini(path, *, keep=5)` snapshots the current `user.ini` into the channel's `backups/` dir as `user.ini.bak_{YYYYMMDD_HHMMSS_ffffff}` (microsecond timestamp, sorted by name so ordering is deterministic), keeping the newest `keep`; both `save_user_ini` and `save_user_ini_dict` call it via `_backup_if_changing` *before* overwriting, but only when the new content differs (identical saves don't rotate real history out). `list_user_ini_backups(path)` returns them newest-first and `restore_user_ini_backup(backup, path)` restores one (snapshotting the current file first, so a restore is itself reversible) — wired to the Config tab's **Restore user.ini** button via `MainWindow._handle_restore_user_ini`. This closes the gap where `user.ini` (every hand-entered edit) had no backup while the applied game `global.ini` did. Also exports `reset_user_ini(path, *, backup=True)` — the Config tab's **Reset user.ini** button: default renames the existing `user.ini` to a timestamped sibling (`user.ini.YYYYMMDD-HHMMSS.bak`) before removal so an accidental wipe is recoverable; `backup=False` deletes outright. Returns the backup `Path` or `None` when the source was absent. Also exports `migrate_user_data_dir(old_root, new_root, *, move=False)` (issue #103, the Config tab's data-folder change): copies every file under the old root into the new one, merging but never overwriting (data already in the new location wins); `move=True` (2.0) deletes successfully transferred originals and prunes emptied source dirs. Snapshot-before-copy plus a destination-subtree skip make the new-folder-nested-inside-old case safe. `tests/test_user_data_dir_migration.py` locks the contract.
- `user_cfg.py`: manages SC's `user.cfg` in the active channel's install dir. `ensure_user_cfg_language(language=None)` sets `g_language` to the selected language's SC id (via `SC_LANGUAGE_IDS`); pre-2.0 this was hardwired to `english`. Regex-based key match tolerates SC's lenient spacing/casing/quoting so it updates in place instead of appending duplicates.
- `i18n.py`: UI string localization (2.0, #30). `tr("dot.path.key", **kwargs)` resolves into the JSON tree loaded from `languages/{lang}/ui.json`; `set_language()` rebuilds the table from the English base with the target language overlaid, so missing keys fall back to English and then to the bare key (never raises). Loaded once at startup in `src/main.py`; a runtime switch re-merges strings but widgets already constructed keep their old text until restart. Game strings are unaffected: they reload through the normal merge path.
- `version.py` — reads version string from `VERSION.TXT`; handles both normal and PyInstaller-frozen runs.
- `test_plan.py` — Qt-free core of the tester **Test Plan** panel (#144): the `TEST_SECTIONS` checklist content (tracks the active release's diff over its base — update it per release), plus `plan_hash()` (digest that invalidates a tester's stale check-marks when the plan changes), `progress()`, `build_report()` (markdown run report), and `discord_chunks()` (line-safe 2000-char split). Consumed by `src/gui/test_plan_panel.py` and `TestPlanSubmitWorker`. Persistence + webhook resolution live on `AppSettings` (`get_/set_test_plan_checks`, `get_/set_tester_name`, `get_test_webhook_url`); this module never imports settings.
- `perf.py` — `@timed` decorator for debug-level perf profiling. No-op when DEBUG logging is off.
- `progress_sink.py` — `ProgressSink` coalesces `advance()` calls from many worker threads into throttled `(completed, total, message)` callbacks. Used by the parallel lookup builders and enhancement generators to drive determinate progress bars without flooding the Qt event loop.
- `dataforge_patcher.py` — applies declarative JSON patches from `patches/` to the DataForge XML cache right after extraction. Fixes upstream CIG data bugs (e.g. mission records pointing at wrong loc-keys) so downstream consumers see corrected data. Patches mirror the DataForge layout under `patches/<category>/.../<name>.patch.json`.
- `applied_file_validator.py` — `validate_applied_file(written_path, cache_dir, stock_keys=None)`: re-parses the just-written `global.ini` against the cached `base.ini` and returns a human diff (missing / unexpected keys) or `""` when valid. `MainWindow._validate_applied_file` is a thin wrapper that supplies the cache dir from `AppSettings`. Lets `apply_to_game` auto-rollback on a merger bug.
- `entry_filter.py` — `filter_entry_indices(...)`: pure-Python row filter for the strings table (column filters + category / status / hide-unmodified / favorites-only). Imports `NUM_COLUMNS` from `string_table_model` so the OOB guard tracks added columns; bad indices drop + log once instead of raising `IndexError` deep in the per-entry loop. A per-call getter tuple lets the hot path call only the getters for active filters.
- `resource_path.py` — `get_resource_path(rel)` (PyInstaller `_MEIPASS`-aware) and `resolve_patches_dir()` (`Path` to bundled `patches/`). Lives here, not in `src/gui/`, because `main_window.py` and `workers.py` both depend on it — leaf-level placement avoids a `gui` ↔ `gui` import cycle.
- `blueprint_log_scanner.py` — Qt-free, settings-free (#222; #223 moved its button + result UI onto the Blueprint Tracker tab, unrelated to these internals): scans Star Citizen's `Game.log` / `logbackups/*.log` for "Received Blueprint" reward notifications so the Blueprint Tracker's Owned list can auto-populate from a player's actual play history. `parse_events(text)` keys only on the `<SHUDEvent_OnNotification> Added notification` line (anchored, not a bare `Received Blueprint: ...` match, so `<UpdateNotificationItem>` UI-echo/continuation lines quoting the same notification are never mistaken for a second event) and captures both the timestamp and the raw name up to the fixed `: " [<id>]` suffix (embedded quotes survive — e.g. `Demeco "Purgatory Camo" LMG`). Two time filters bound the work: an epoch floor (`BLUEPRINT_EPOCH`, March 2026 — blueprints didn't exist before then) and an optional watermark (`since`, the newest event a prior scan already consumed) so a re-scan only imports genuinely new blueprints. `find_log_files(channel_install_path, since=None)` discovers `logbackups/*.log` plus the live `Game.log`, oldest-first, pre-filtering out any file whose mtime predates the effective floor so an unchanged rotated log isn't even opened; `scan_files(paths, since=None, progress=None)` streams each file line-by-line (some live logs run tens of MB) and returns a `ScanResult` (raw names, `latest_timestamp` for advancing the watermark, counts); `scan_channel(channel_dir, ...)` composes both for the worker's entry point. Deliberately returns raw display names, not normalized ones — normalization (`owned_items.normalize_item_name`, so e.g. `Agni [Industrial-S3-B-Quantum]` reduces to `Agni`) and watermark persistence (`AppSettings.get_/set_blueprint_log_watermark()`) both live in `MainWindow._on_blueprint_log_scan_finished`, so the one canonical normalizer does the matching. Driven by `BlueprintLogScanWorker` in `src/gui/workers.py` (off-thread — a channel's logbackups can hold hundreds of rotated session files).
- `onedrive.py` — Qt-free OneDrive detection (#172). `is_onedrive_path(path, environ=None)` is True when a path is at/under a OneDrive root (`%OneDrive%` / `%OneDriveConsumer%` / `%OneDriveCommercial%`) or contains a `OneDrive` / `OneDrive - Org` path segment; `suggest_local_data_dir()` returns `%USERPROFILE%\Documents\Smart Citizen` (the local path even when the shell Documents is redirected into OneDrive). Drives `MainWindow._maybe_warn_onedrive_data_dir` (startup, once, suppressible via `AppSettings.get_/set_onedrive_warning_dismissed`) and the Config tab's data-folder OneDrive warning. The default data root resolves Documents via the shell `Personal` key, which honors OneDrive redirection — so on a redirected machine the per-user data lands inside OneDrive's reach, the loss path this warns about.
- `crash_handler.py` — `install_crash_handler(logs_dir)` wraps `sys.excepthook` and `threading.excepthook` so an uncaught exception (main thread *or* worker `QThread`) writes `crash_YYYYMMDD_HHMMSS.log` to `{logs_dir}` before the default hook runs. The frozen PyInstaller build has no console, so without this a crash vanishes silently with no diagnostic trail. Maintains its own in-memory ring-buffer `logging.Handler` (independent of the LogTab buffer, which may have died with the GUI). Installed from `src/main.py` after `AppSettings` is importable but before the QApplication is constructed — `install_crash_handler(AppSettings.get_logs_dir())` — so even import-time crashes get dumped. Idempotent: the second call is a no-op.
- `crash_logger.py`: `show_crash_dialog(exc_type, exc_value, crash_path)`, the modal "Smart Citizen crashed" dialog the main-thread hook in `crash_handler.py` shows after writing the dump. Degrades to a no-op without Qt/pyperclip or a QApplication. Capture and dump-writing live in `crash_handler.py`, not here; this module once carried a parallel crash system and was trimmed to the dialog in 2.0. Dialog strings stay English on purpose: the crash path must not depend on i18n state.

## Design decisions

### Portable vs registry build mode
One source tree, two build variants:
- **Registry (default)** — `python build_exe.py`. Settings → Windows Registry via `QSettings`. Data root → `Documents\Smart Citizen\` (or whatever the user configured).
- **Portable** — `python build_exe.py --portable`. Settings → `<user_data_dir>/config.json` via `JsonSettings`. Data root → `<exe-dir>/data/` when frozen, `<repo-root>/portable_data/` unfrozen for testing.

The build-time switch is `build_mode.py::IS_PORTABLE`. The `--portable` build writes a generated `_build_info.py` (git-ignored) with `IS_PORTABLE = True` before PyInstaller runs and deletes it after, so the source tree is never committed in portable state. The repo on disk always shows `IS_PORTABLE = False`.

At runtime the flag flips exactly two things:
1. `AppSettings._backend` — `QSettings` or `JsonSettings`. The `QSettings` surface `AppSettings` touches is tiny (`value` / `setValue` / `remove` / `sync`), so the `json_settings.py` shim is a focused mirror, not a full re-implementation.
2. `AppSettings.get_user_data_dir()` — Documents path vs `<exe-dir>/data/`.

Registry-tree migrators no-op in portable mode. When editing settings-touching code, use `AppSettings` helpers — reaching for `QSettings` directly breaks portable mode silently.

### DataForge diff cache skips unchanged enhancement generators
`dataforge_diff.py` snapshots every XML in the DataForge cache and, on the next extraction, reports which enhancement categories need to re-run. `CATEGORY_SUBTREES` maps each category (`ships`, `components`, `ship_weapons`, `fps_weapons`, `missions`, `commodities`, `journal`) to the DataForge paths it reads. **A new enhancement category or a change to existing subtree coverage needs updates in both `CATEGORY_SUBTREES` here AND `DATAFORGE_KEEP_SUBPATHS` in `pak_extractor.py`** — the former drives "what to re-run", the latter "what to copy to the cache". They are not the same list (subtree filters can be finer than keep filters) but must agree on coverage.

### Parallel pipelines report progress via ProgressSink
Lookup builders and enhancement output generators run in parallel worker threads (see `scripts/generate_enhancements_ini.py`). They share one `ProgressSink` (`progress_sink.py`) so the UI shows one determinate progress bar. Never call `QProgressBar.setValue()` from workers — go through the sink so updates are coalesced and throttled on the main thread.

### Tag-config hand-off to the enhancements worker
`EnhancementsGeneratorWorker.__init__(categories, tag_configs)` (in `src/gui/workers.py`) takes tag-builder configs as a plain dict, not from inside the worker thread. `MainWindow.run_enhancements_pipeline` calls `AppSettings.get_all_tag_configs()` on the **main thread** and hands the result to the worker, so the generator code path never touches a live `QSettings` / `JsonSettings` handle from a background thread. Don't shortcut this — `QSettings` is thread-safe but the JSON shim's file write is point-in-time, and we want the generator's input frozen at pipeline-launch time so a mid-run tab edit can't half-rewrite an enhancement INI.
