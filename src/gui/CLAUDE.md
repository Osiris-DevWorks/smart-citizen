# src/gui/CLAUDE.md

GUI layer (PyQt6). See the root `CLAUDE.md` for project context and cross-cutting design decisions.

## Files

- `main_window.py` — main window with table, toolbar, filters, backup/restore, DataForge extraction trigger, worker orchestration. The largest file in the repo; runs the core workflow load→merge→edit→apply. Workers live in `workers.py`; pure-Python helpers (`validate_applied_file`, `filter_entry_indices`, `markdown_to_html`) live in their own modules and are wrapped by thin `MainWindow` methods. Owns `_stamp_frontend_version` — see *Frontend version stamp on apply* below. Less-frequent toolbar actions (restore backup, clear localization/cache, import/export INI, open loc dir) live under a **More** overflow `QMenu` (2.0). `_on_language_changed(language)` runs the language-switch pipeline (2.0, #30): cancel any in-flight loader, `i18n.set_language()` + `retranslate_ui()`, then `_apply_language_base_source()` repoints the `global` source at that language's base.ini (downloading it via `LanguageBaseDownloadWorker` when a URL is mapped; falling back to a cached copy, then to English), and `_reload_with_language_enhancements()` regenerates that language's enhancements first when the `.dataforge_stamp` is stale (skipped if no DataForge cache: prose loads without stat overlays). user.cfg's `g_language` is NOT set here; that happens at window init and apply-to-game time. Its DataForge cache status and freshness checks read the cache folder without creating it, and `_run_dataforge_extraction` reports a cache folder it cannot create in one box before any worker starts (see *Status checks never create the DataForge cache folder* below, #494), as it does a cache folder that is a link (#491). More > Clear Cache (`clear_cache`, #479) deletes the active channel's cached `*.ini` and `*.txt` and, when the user agrees, the DataForge cache in use: the folder `get_dataforge_cache_leaf()` names (the default, the portable build's or a cache folder override), offered only when it holds a cache (its `.p4k_mtime` stamp or its records). It used to look in the data folder's `cache\dataforge`, where the cache lived before 1.x, so the real one was never offered; a leftover there is the queued old-cache cleanup's. A cache folder on a drive or share that is not there is named in the summary and the rest still clears, the file question is skipped when there are no files (a No to the DataForge question then changes nothing, just as a No to the file question), nothing is cleared while an extraction or a generation runs (`clear_cache_busy` in the status bar), the Enhancements tab is refreshed afterwards, a failure is listed in the summary and logged once at WARNING (an ERROR record opened a second box), and every text goes through `tr()`. A channel switch and a data-folder change (`_sync_canonical_source_paths`, through `AppSettings.sync_global_source_path`) and a successful global.ini extraction (`_on_p4k_extract_finished`) keep the `global` source on the selected language's base.ini (`AppSettings.get_global_source_base_ini()`, English when this channel has none yet); they used to point every language at the English one (#502).
- `workers.py` — every `QThread` background worker plus the shared `AnimatedProgressDialog` (its `set_close_guard(guard)` asks before Esc or the title-bar X dismisses it, never on a programmatic `close()`, and only for a dialog without a cancel button, #471; its `set_progress` shows the moving busy bar for a total of 0 and for nothing counted yet, 0 of N, until the first count, #507: a bar standing at 0% looked hung, as the generator's first lookups did for seconds, and the string loader and the update download start at 0 too) and `SelectAllDelegate`. Workers: `FileLoaderWorker` (sources → `StringEntry` list + sort keys), `AppliedStateWorker` (#398 review: runs the already-applied comparison off the GUI thread; takes an injected `compute(snapshot, should_stop)` instead of importing it, because the merge it shares with Apply to Game lives in `main_window.py` and importing that here would be a gui-to-gui cycle; always emits `finished(bool)` once, False being the safe "not applied" answer), `StartupSyncWorker` (refresh URL-backed sources at startup), `EnhancementsGeneratorWorker` (run `scripts/generate_enhancements_ini.py` in-process via `importlib.util`; takes a `language` param so output lands in that language's enhancements dir while annotation paths still parse the English base.ini), `P4kExtractWorker` (unp4k extract of `global.ini`, working beside the DataForge cache it is handed as `scratch_near`), `DataForgeExtractWorker` (unp4k + unforge + post-extract patches; both stop on `requestInterruption()`, record it in `stopped` and then end with `finished(False)`, no `error` and nothing at ERROR, #471), `LanguageBaseDownloadWorker` (2.0: fetch a non-English language's global.ini from its mapped URL into `cache\lang\{language}\base.ini`), `LiveBlueprintLogWorker` (SCO, 2.5.0: polls `blueprint_log_scanner.GameLogTail` on the active channel's `Game.log` every `POLL_MS` while the overlay runs, LIVE and HOTFIX only, and emits `blueprints_found(raw names, newest)`; read-only like the Scan, the main thread updates the owned set; stopped with `requestInterruption()` + `_reap_worker`; a lasting poll fault logs one traceback, then debug), `BlueprintLogScanWorker` (#222: scan a channel dir for "Received Blueprint" notifications via `blueprint_log_scanner.scan_channel`, watermark-aware — takes `(channel_dir, since)`, emits a `ScanResult`; stays read-only, all owned-set/watermark mutation happens on the main thread in `MainWindow._on_blueprint_log_scan_finished`). Each emits `progress` (str) and `progress_pct` (completed, total, message); `AnimatedProgressDialog.set_progress` consumes the latter. Exception: `AppUpdateCheckWorker` and `AppUpdateDownloadWorker` live in `src/utils/app_updater.py` because the workers, version comparison, and installer-asset picking belong together (#211).

Crafting rows lead back to their compendium mineral through `_mineral_by_material`, built in `set_catalog()` with `CraftingIndex.material_key_for`, the same link the mineral tooltips use, so CIG's spelling differences (Pressurized Ice / Ice, Aluminum / Aluminium, ...) resolve both ways. Minerals, locations and items carry tooltips (`mineral_tooltip`, `location_tooltip`, `_item_tooltip`). `BlueprintDrawer.retranslate_ui()` sets every fixed text and redraws the list and trees; it runs at construction and from `MainWindow.retranslate_ui()` after a language switch. The guided tour's `overlay` step (`assets/tutorial.json`, after `blueprint_tracker`) points at the Overlay tab's start button. `MainWindow._refresh_sco_catalog` feeds `set_catalog()` from the English base.ini's Mining Compendium and the `crafting_index.json` the generator writes (see `src/utils/mining_catalog.py`), re-reading only when either file changed. A new reading only replaces the label after `READINGS_TO_CHANGE` identical captures in a row (`_on_reading`; any accepted or steady reading clears the pending candidate, so a misread that comes back later still has to repeat back to back), so a one-frame misread can't flash "Unidentified" over a steady signature. The confirming capture runs at once (`QTimer.singleShot(0, _capture_once)` on a first sighting) instead of waiting for the next tick, so a new signal shows up to a tick sooner; `_capture_once` drops a queued one once the timer has stopped. The label sits `LABEL_GAP` px below the readout, and `_mask_own_label` blacks it out of each capture so its own text is never read. Each distinct reading's crop is saved once per session to `{logs_dir}/sco_samples/<time>_<value>.png` (capped by `MAX_SAMPLES_PER_SESSION`; on in every build by default) so misreads can become new reference glyphs (`scripts/add_sco_sample.py`). The PNG is written by `_SaveSampleTask` on the reader's pool thread, never the GUI thread, and a session's first save prunes the folder to the newest `MAX_SAMPLES_KEPT` (`prune_samples`). Owned edits go out via `owned_toggled` to `MainWindow._on_sco_owned_toggled`, so MainWindow stays the one owned-set writer. While running, `LiveBlueprintLogWorker` (`workers.py`) tails the active channel's `Game.log`, only when that channel is LIVE or HOTFIX (`_start_sco_log_watcher` checks `_SCANNED_CHANNELS`, the #446 rule; `test_blueprint_scan_channels.py` guards it), and `_on_channel_changed` restarts it for a new channel without closing the windows. `_on_sco_blueprints_found` folds names through `_owned_names_from_log` (shared with the Scan button) but leaves the persisted watermark to the Scan: the tail reads only the current `Game.log`, so advancing the mark from it would make the next Scan skip sessions rotated into `logbackups` meanwhile. The capture timer only grabs the screen; `read_signature` (pure Python: 6-47 ms on a real scene, about 150 ms at worst on a 4K capture of noise) runs on a one-thread `QThreadPool` (`_ReadTask`), a tick is skipped while a read is in flight, and the result comes back through `_read_done` (a token bumped on `stop()` drops a late one). A reader that raises stops the capture, hides the label and emits `decoder_failed`, which MainWindow shows in the status bar (`sco.decoder_stopped`); stopping and starting the overlay tries again. The samples folder is resolved per save and per Open Samples Folder click, so a data-folder move is followed. Anti-cheat constraint: no injection/hooks, no handle to the game process, no memory reads, no input. Only plain windows, desktop pixel capture and log reads.

## Design decisions

### Sortable columns require indirect row lookup
The table is a `QTableView` backed by `StringTableModel` (`string_table_model.py`), which holds a filtered/sorted list of indices into `self.entries`. Row index ≠ entry index when sorted or filtered. **All row→entry lookups go through `_entry_index_for_row(row)`** on `MainWindow` (which delegates to `self._model.entry_index_for_row(row)`). Direct indexing into `self.entries` by row number gives wrong results. Use the `COL_*` constants from `string_table_model.py`, not hard-coded column numbers.

### Frontend version stamp on apply
At apply-to-game time, `main_window._stamp_frontend_version(merged)` appends `\nLocalizations Enhanced with Smart Citizen v{VERSION}` (a literal `\n` — the loc-string line-break convention, same as the journal stamp) to the launcher's `Frontend_PU_Version` loc-key, putting the watermark on its own second line rather than crowding the build-info line. `_FRONTEND_VERSION_STAMP_RE` strips any prior stamp before re-applying — including the original " | "-separated form pre-2.3.0 installs have on disk — so the suffix doesn't pile up across applies or version upgrades. If the key is absent from the merge (older patches, custom configs), the stamp is skipped — never inserted. `tests/test_frontend_version_stamp.py` locks the no-double-stamp guarantee.

### An anticipated extraction failure opens one box (#482)
`P4kExtractWorker` and `DataForgeExtractWorker` report a failure from one `except Exception` branch, after the stop check, so a failure that races a Stop is reported as the stop. A failure in `pak_extractor.ANTICIPATED_EXTRACTION_ERRORS` (a locked Data.p4k, an unforge timeout, a drive without enough free space, a working folder Windows refused (#490), and for a DataForge run in `%TEMP%` a folder where the cache folder could not be made again after the wipe (#494), and a DataForge cache folder that is a junction or a symbolic link (#491)) carries its own translated message and was logged at WARNING where it was raised, so the worker logs it at WARNING too and emits `error`. Anything else goes to `logger.exception`, which opens the global error dialog. `_on_dataforge_extract_error` logs the message at WARNING, never ERROR, before its own box: an ERROR record there opened a second box on top of an anticipated failure's, or added a stray "(+1 suppressed)" to an unexpected one's. `tests/test_extraction_stop.py` locks both, and `TestRefusedWorkingFolderReachesTheUser` follows a refused working folder from the real extraction to one box, as `TestLinkedCacheFolderReachesTheUser` does a cache folder that is a junction.

### Status checks never create the DataForge cache folder (#494)
`get_dataforge_cache_dir()` creates the cache folder, so a status check that called it raised when Windows refused the folder (its permissions, Controlled folder access) or its drive was gone. Building the Enhancements tab is such a check, so Smart Citizen could not open, and a channel or language switch, a data folder change and the Enhancements Apply stopped halfway with the crash dialog. The tab's `refresh_forge_status` and `_compute_initial_enhancements_dirty`, the window's freshness checks, Clear Cache (#479) and `EnhancementsGeneratorWorker` read `get_dataforge_cache_leaf()`, which creates nothing; a missing folder has no stamp, so it reads as not extracted. `_run_dataforge_extraction` creates it, because it is about to write the cache (`_run_p4k_extraction` also makes it, only so the global.ini extraction can work beside it, and works in `%TEMP%` when it cannot). When that fails it reports the folder in one box before any worker or progress dialog is built, the text picked by `settings.cache_folder_failure` (`extract.cache_folder_refused` with the cache advice for a refusal, `extract.cache_folder_unreachable` for a folder or drive that is not there, a drive that is not ready included, and `extract.cache_folder_unusable` with Windows' own reason for anything else), logs the Windows error at WARNING, ends a Simple run, lights Generate again and returns False. Just before that getter it asks `pak_extractor.linked_cache_folder_error` about the cache folder (#491): one that is a junction or a symbolic link is refused in the same one box, with `extract.cache_folder_is_link`, because the extraction deletes nothing through a link, and a link whose target is gone would fail the getter with Windows' "file already exists" and get the could-not-use text instead. A cache folder that is already there passes that call even when the folder holding it refuses new folders. A run working beside the cache is then refused by #490's working-folder check, and a run working in `%TEMP%` (a OneDrive, network, removable or deep cache) by `pak_extractor`'s check that the cache folder can be made again after the wipe, both before any tool runs and with the old cache kept; that run used to wipe the old cache first and then fail with three boxes: the global error box, the error slot's and the crash dialog. The Config tab's `_maybe_apply_cache_change` reads the old cache folder through the leaf too, so a saved folder Windows refuses, or one on a drive that is gone, can be left with Reset or another folder. It still saves the new folder before making its cache folder (the resolved path comes from the same code production uses), but undoes the save on an `OSError` exactly as Cancel does and raises it again; `_save_cache_dir` and `_reset_cache_dir` then report through `_report_cache_folder_error`: one box titled `config.invalid_cache_folder_title` naming the folder that was tried (the typed or picked folder resolved, or `AppSettings.get_default_dataforge_cache_base()` for a reset or a cleared field), the text picked by the same `cache_folder_failure`, so the two places cannot disagree: `config.cache_folder_refused` with #490's `extract.folder_refused_fix` for a refusal (not the advice to choose another cache folder, which the user is doing), `config.cache_folder_unreachable` for a folder or drive that is not there, and `config.cache_folder_unusable` with Windows' own reason for anything else (a typed name Windows does not take, a path through a file), the Windows error at WARNING, and the field back on the folder that is saved. A file gets `config.cache_folder_is_file`. Nothing is emitted for a change that did not happen. The field's `editingFinished` reaches `_save_cache_dir` through `_cache_dir_edited`, and only when the user typed in the field (`isModified()`, which typing sets and `setText` clears). Qt also sends that signal when the field loses focus after a `setText`, and the field is filled that way when the tab is built and after every box, so a click into the field and out again used to try the saved folder again: with a saved folder that cannot be used it opened a box for a change nobody asked for, and the click away after a failed change opened a second one naming the saved folder. Enter with nothing typed does nothing either (`hasFocus()` cannot tell it apart, because a menu that opens while the field has the focus sends the same signal with `hasFocus()` still true), while the saved folder typed again is a change and gets its one box. Browse calls `_save_cache_dir` itself. `tests/test_extraction_stop.py`, `tests/test_refused_cache_window_paths.py`, `tests/test_enhancements_tab_refused_cache.py`, `tests/test_startup_refused_cache.py`, `tests/test_config_tab_cache_folder.py`, `tests/test_cache_folder_strings.py`, `tests/test_generator_refused_cache.py` (the generator worker) and, for the `%TEMP%` check, `tests/test_extraction_working_folder.py` lock this.

### Apply button turns green when nothing has changed (#387, #397, #398)
After every reload, `_on_loading_finished` calls `_refresh_apply_dirty_after_reload`, which starts an `AppliedStateWorker` (a background thread, so the seconds of re-reading and re-merging never block the GUI) that compares what a real apply would write against the game's on-disk `global.ini`. It runs on every reload, not only the first, because Simple mode applies and then reloads, and `_recompute_owned` marks every reload dirty, so only an authoritative check can settle the button afterward. `_merge_for_apply` is the one merge shared by `apply_to_game` and the check (so they can never compute different content), and `_compute_already_applied` does the comparison on a plain-data `_AppliedStateSnapshot` that `_apply_merge_inputs` captures on the main thread. The check drops the on-disk `user` source that `load_sources_from_settings` returns and merges only the snapshot's overrides: Apply saves `user.ini` from the loaded entries before it reloads the sources, and the copy on disk can still hold an override the user has since cleared. The comparison walks the stock `base.ini` key set specifically: `merge_ini_files` only ever overwrites a key present in its structure-preservation source file, so a merged key `base.ini` lacks is never written and must be excluded, or any profile with such a key would read dirty even right after a genuine apply. It also requires `user.cfg`'s `g_language` to match the selected language, since switching language in the UI never touches `user.cfg`. The applied file is parsed with `strip_values=False`: the writer puts every merged value in verbatim, and a user override can start or end with a space (a space favourite prefix, #100), so stripping that side made such an override read red after every real apply. Any doubt (no applied file, no stock `base.ini`, an error, an interruption) reads as "not applied": wrongly showing green would hide a real pending change. `_set_apply_btn_dirty` forwards every state change to the Simple-mode page's button too. That one stays clickable when green, because a click still regenerates and re-applies (after a game patch, for example).

Because the verdict arrives later, `_applied_check_token` guards it. An edit (`_mark_apply_dirty`), Apply's write (`_invalidate_applied_check`, just before `merge_ini_files`), a successful apply (`_mark_applied`), the game file changing outside Apply (`_mark_game_file_changed`) or a newer reload bumps the token, and a verdict computed from an older snapshot is dropped instead of overwriting the state those events set. One check runs at a time; a reload that lands mid-check interrupts it and queues a single rerun that snapshots the newer state. `closeEvent` calls `_settle_applied_state_check`, which waits for a running check and applies its verdict: the thread must be gone before exit, and a reload sets `_session_has_unapplied_edit` provisionally, so closing right after a clean apply would otherwise warn about changes that don't exist. Cancelling that close prompt, or choosing Apply Now when the apply stops before it touches the button (a declined prompt, a failed `user.ini` save), re-runs the check, since settling may have dropped a verdict or a queued rerun to close quickly.

`apply_to_game` returns True only for a written and validated apply. It invalidates any in-flight check right before it writes the game file, because a dialog later in the apply runs the event loop and could deliver a verdict about the file being replaced. A failed write or failed validation marks the button dirty before its error dialog, for the same reason. Deleting the game file (`clear_localization`) or restoring a backup (`restore_backup`) turns the button red through `_mark_game_file_changed`, which also clears `_session_has_unapplied_edit` (Restore clears it again after its own reload, where `_recompute_owned` sets it). So closing after a deliberate revert does not offer to re-apply over it, while the red button still says an apply is due. Clearing rather than keeping the flag is deliberate: a reload sets it provisionally until its check answers, and a revert drops that answer, so a kept flag could be a placeholder nothing would ever clear. Both mark only once the file really changed: a failed restore is no revert, so it keeps the close reminder. It re-runs the check before its error dialog instead, which drops any verdict about the old file and reads whatever a part-way copy left on disk. The synchronous reload in `perform_merge_and_reload` starts the check just like the async loader does. `_reload_follows_clean_apply` is a one-shot set by Simple mode's apply-then-reload so that reload doesn't paint the button red while the check re-confirms it. It is set only when `apply_to_game` returned True, and a failed reload clears it.

### Closing stops a running extraction (#471)
`closeEvent` used to leave a running extraction alone, and a closed app left unp4k or unforge running on its own (measured: unforge carried on ~23 s past the exit while Python's exit-time cleanup failed under it, and its ~2 GB stayed in `%TEMP%`). Once every prompt that could call the close off has been answered, `closeEvent` sets `_close_committed` and calls `_request_extraction_stops()` ahead of the unbounded loader wait, so the tool dies at once; last, after the window state is saved, `_stop_extractions_for_close()` hides the window and waits (one 180 s deadline for both workers, like `_settle_applied_state_check`) while the worker deletes its working folder. Past the deadline the reference is kept so Qt doesn't destroy a live thread, and the next extraction's sweep removes what is left. It detaches each progress dialog from its worker (`_detach_progress_dialog`) and dismisses it with `cancel()`: a hidden `QProgressDialog` shows itself again while progress keeps arriving, and a plain `hide()` (what Esc does) is undone by its own show timer when the dialog is under 4 s old (measured: back 3.5 s after an Esc at 0.5 s). The extraction slots are bound to their worker (as `_launch_applied_state_check` does) and ignore a released one, and `_close_committed` keeps `_run_dataforge_extraction`, `_run_p4k_extraction`, `_run_enhancements_generation`, `_check_enhancements_freshness` and `_maybe_prompt_dataforge_refresh` from starting anything new: Qt still delivers queued signals after `closeEvent` returns. The stop is silent by design (no prompt), so the update installer and Import Settings relaunches, which ignore `close()`'s result, need nothing special.

Esc or the X on the DataForge progress dialog used to hide it while the extraction carried on unseen, which is how a user got to close the window mid-run. The dialog's close guard now asks whether to stop (`_confirm_stop_dataforge_extraction`: Stop or Cancel, Cancel being the default and what Esc picks). The dialog stays modal while the run goes on, so nothing it depends on (the channel, the language, the data or cache folder) can change under it; a Run in Background choice was tried and dropped for that reason before 2.4.0. **Stop** requests the stop, and the finished slot reports "stopped" rather than "failed" (it reads the worker's own `stopped` record: QThread reports no interruption once a thread has finished, and the slot waits for the thread first). A Simple-mode run can no longer apply, but its page stays busy until the stop has finished and the finished slot ends the run, so the button never looks ready while a click would be turned away. Stop dismisses the dialog for good: `_detach_progress_dialog` disconnects the worker's progress from it and it is deleted, because a hidden `QProgressDialog` shows itself again while progress keeps arriving (measured within a second of Esc or the X; `TestDismissedDialogStaysHidden` keeps the control that shows it). If the run finishes while the question is open, its slot has already moved on to generation, so Stop has nothing to stop, but it still ends a Simple-mode run so nothing is applied to the game (and `_on_enhancements_generation_finished` releases the page whether or not a Simple run is active). The same dialog is handed to enhancement generation, so `_run_enhancements_generation` clears the guard at the hand-off; generation keeps the old hide-and-continue. Esc or the X on the global.ini dialog stops that extraction without asking (`_stop_p4k_extraction_from_dialog`, also a close guard): it is a short job that writes `base.ini` only at its very end, so a stop leaves the old one as it was, and the status bar says "global.ini extraction stopped". It used to hide the dialog while unp4k carried on unseen, and Extract then started a second run that replaced `_p4k_worker`, so closing stopped only the second and left the first unp4k running. `_run_p4k_extraction` now starts nothing while `_p4k_worker` is set, and the stop makes sure that never leaves Extract waiting on a run the user cannot see. Startup, a channel switch and a data-folder change leave their reload to the extraction `_check_p4k_freshness` starts, and only a success used to reload, so they now pass what they do when it is declined (`if_unfinished`: `_finish_startup_load`, `_reload_after_channel_switch`, `_reload_after_data_dir_change`) and the finished slot runs it after a stop or a failure, instead of leaving no strings or the old channel's. A success reloads by itself and drops the follow-up, so when there is one it first asks `_maybe_prompt_dataforge_refresh`, the question each of those callers asks before its own reload (#478): dropping the follow-up used to drop that question too, so right after a game patch an outdated DataForge cache went unmentioned until the next launch. A Yes runs the DataForge extraction beside the reload, as at startup. The Config tab's Extract button starts a run with no follow-up and asks nothing. A failure shows its error box first, and the finished slot usually runs inside that box's own event loop, so it parks the follow-up (`_p4k_follow_up_after_error`) for `_on_p4k_extract_error` to run once the box has closed rather than stacking a reload or a prompt on top of it. `_run_p4k_extraction` returns whether it started, so a Yes while one is already running carries on as declined at once. A run cut off between the cache wipe and the stamps (a crash, or a close that outlasted its 180 s wait) leaves content with no `.p4k_mtime`; `_maybe_prompt_dataforge_refresh` treats that as stale and prompts, instead of letting it pass for "never extracted". `tests/test_extraction_stop.py` locks this.
