# src/gui/CLAUDE.md

GUI layer (PyQt6). See the root `CLAUDE.md` for project context and cross-cutting design decisions.

## Files

- `main_window.py` — main window with table, toolbar, filters, backup/restore, DataForge extraction trigger, worker orchestration. The largest file in the repo; runs the core workflow load→merge→edit→apply. Workers live in `workers.py`; pure-Python helpers (`validate_applied_file`, `filter_entry_indices`, `markdown_to_html`) live in their own modules and are wrapped by thin `MainWindow` methods. Owns `_stamp_frontend_version` — see *Frontend version stamp on apply* below. Less-frequent toolbar actions (restore backup, clear localization/cache, import/export INI, open loc dir) live under a **More** overflow `QMenu` (2.0). `_on_language_changed(language)` runs the language-switch pipeline (2.0, #30): cancel any in-flight loader, `i18n.set_language()` + `retranslate_ui()`, then `_apply_language_base_source()` repoints the `global` source at that language's base.ini (downloading it via `LanguageBaseDownloadWorker` when a URL is mapped; falling back to a cached copy, then to English), and `_reload_with_language_enhancements()` regenerates that language's enhancements first when the `.dataforge_stamp` is stale (skipped if no DataForge cache: prose loads without stat overlays). English goes through it too whenever its base.ini exists, because a re-extraction made while another language was selected regenerated only that language. That regeneration is the switch's launch: it clears the Generate button first, as `_run_enhancements_pipeline` does (#292), and leaves the switch's reload to the run. A run that fails still loads the language picked, with the stats it has: `_run_enhancements_generation` keeps its `if_unfinished` in `_after_unfinished_generation`, and the finished slot runs it once the run's error dialog has closed (parked in `_after_error_dialog`, which `_show_error_dialog` runs as it closes). `_run_enhancements_generation` returns whether it started, like `_run_p4k_extraction`, and a start refused because a generation is already running loads the language at once. user.cfg's `g_language` is NOT set here; that happens at window init and apply-to-game time. Its DataForge cache status and freshness checks read the cache folder without creating it, and `_run_dataforge_extraction` reports a cache folder it cannot create in one box before any worker starts (see *Status checks never create the DataForge cache folder* below, #494), as it does a cache folder that is a link (#491). More > Clear Cache (`clear_cache`, #479) deletes the active channel's cached `*.ini` and `*.txt` and, when the user agrees, the DataForge cache in use: the folder `get_dataforge_cache_leaf()` names (the default, the portable build's or a cache folder override), offered only when it holds a cache (its `.p4k_mtime` stamp or its records). It used to look in the data folder's `cache\dataforge`, where the cache lived before 1.x, so the real one was never offered; a leftover there is the queued old-cache cleanup's. A cache folder on a drive or share that is not there is named in the summary and the rest still clears, the file question is skipped when there are no files (a No to the DataForge question then changes nothing, just as a No to the file question), nothing is cleared while an extraction or a generation runs (`clear_cache_busy` in the status bar), the Enhancements tab is refreshed afterwards, a failure is listed in the summary and logged once at WARNING (an ERROR record opened a second box), and every text goes through `tr()`. A channel switch and a data-folder change (`_sync_canonical_source_paths`, through `AppSettings.sync_global_source_path`) and a successful global.ini extraction (`_on_p4k_extract_finished`) keep the `global` source on the selected language's base.ini (`AppSettings.get_global_source_base_ini()`, English when this channel has none yet); they used to point every language at the English one (#502).
- `workers.py` — every `QThread` background worker plus the shared `AnimatedProgressDialog` (its `set_close_guard(guard)` asks before Esc or the title-bar X dismisses it, never on a programmatic `close()`, and only for a dialog without a cancel button, #471; its `set_progress` shows the moving busy bar for a total of 0 and for nothing counted yet, 0 of N, until the first count, #507: a bar standing at 0% looked hung, as the generator's first lookups did for seconds, and the string loader and the update download start at 0 too) and `SelectAllDelegate`. Workers: `FileLoaderWorker` (sources → `StringEntry` list + sort keys), `AppliedStateWorker` (#398 review: runs the already-applied comparison off the GUI thread; takes an injected `compute(snapshot, should_stop)` instead of importing it, because the merge it shares with Apply to Game lives in `main_window.py` and importing that here would be a gui-to-gui cycle; always emits `finished(bool)` once, False being the safe "not applied" answer), `StartupSyncWorker` (refresh URL-backed sources at startup), `EnhancementsGeneratorWorker` (run `scripts/generate_enhancements_ini.py` in-process via `importlib.util`; takes a `language` param so output lands in that language's enhancements dir while annotation paths still parse the English base.ini; captures that folder, the DataForge build key and the tag fingerprint when its run starts, empties `.dataforge_stamp` just before the generator's `main()` and writes the tag stamp and then the DataForge stamp after it returns, see *A cut-off generation is offered again at the next start* below; `requestInterruption()`, which only closing the window sends, stops it before its patches, its module load or `main()`, and inside `main()` at the next job boundary, never during the writes, records it in `stopped` and ends with `finished(False)`, no `error` and nothing at ERROR), `P4kExtractWorker` (unp4k extract of `global.ini`, working beside the DataForge cache it is handed as `scratch_near`), `DataForgeExtractWorker` (unp4k + unforge + post-extract patches; both stop on `requestInterruption()`, record it in `stopped` and then end with `finished(False)`, no `error` and nothing at ERROR, #471), `LanguageBaseDownloadWorker` (2.0: fetch a non-English language's global.ini from its mapped URL into `cache\lang\{language}\base.ini`), `LiveBlueprintLogWorker` (SCO, 2.5.0: polls `blueprint_log_scanner.GameLogTail` on the active channel's `Game.log` every `POLL_MS` while the overlay runs, LIVE and HOTFIX only, and emits `blueprints_found(raw names, newest)`; read-only like the Scan, the main thread updates the owned set; stopped with `requestInterruption()` + `_reap_worker`; a lasting poll fault logs one traceback, then debug), `BlueprintLogScanWorker` (#222: scan a channel dir for "Received Blueprint" notifications via `blueprint_log_scanner.scan_channel`, watermark-aware — takes `(channel_dir, since)`, emits a `ScanResult`; stays read-only, all owned-set/watermark mutation happens on the main thread in `MainWindow._on_blueprint_log_scan_finished`). Each emits `progress` (str) and `progress_pct` (completed, total, message); `AnimatedProgressDialog.set_progress` consumes the latter. Exception: `AppUpdateCheckWorker` and `AppUpdateDownloadWorker` live in `src/utils/app_updater.py` because the workers, version comparison, and installer-asset picking belong together (#211).
- `markdown_renderer.py` — `markdown_to_html(text, text_color, base_color, link_color)` for About/Help. Pure-Python; the Qt caller passes palette colours so the converter has no Qt dep. Stash-and-restore code-span handling keeps `**` and `_` inside backticks literal (loc keys like `vehicle_Name*` shouldn't sprout `<em>` tags).
- `config_tab.py` — **Config Tab**: source management, drag-drop merge hierarchy, SC install path, DataForge extraction trigger. Also the language selector (2.0): emits `language_changed(str)` for `MainWindow._on_language_changed`, and hosts `LanguageSourceDialog` (the *Map Language File* button) for per-language base.ini URL overrides. Changing the data folder migrates existing data via `migrate_user_data_dir(move=True)`. A DataForge cache folder change whose cache folder cannot be made (Windows refuses it, cannot reach it or rejects it) is undone as Cancel undoes it, with one box (`_report_cache_folder_error`, #494, see below). The cache folder field saves only a folder the user typed (`_cache_dir_edited`), so a click into it and out again, or Enter with nothing typed, tries nothing. While an extraction or a generation runs, `set_data_locations_locked` locks the folders, the channel, the language, Extract, Import Settings and Check for Updates, with the reason shown (#483, see *Run in Background and the job lock* below).
- `enhancements_tab.py` — **Enhancements Tab**: stats-overlay toggles, ship favorites prefix, DataForge extraction trigger, per-field mission-detail show/hide toggles (#121, persisted via `AppSettings._MISSION_FIELD_SETTING`). Emits `merge_requested`, `enhancements_pipeline_requested`, `favorite_prefix_changed` and `category_ticks_changed`. Apply Category Changes, Save Tag Changes and Generate Enhancements are locked while an extraction or a generation runs (`set_changes_locked`, #483). Its DataForge status (`refresh_forge_status`, run while the tab is built) reads the cache folder without creating it, so a folder Windows refuses or a drive that is gone reads as not extracted instead of stopping Smart Citizen opening (#494, see below). The whole tab sits in a `QScrollArea` so a small window squishes nothing (#145). Its dropdowns are `combo_box.NoScrollComboBox`. A category tick is pending until the category Apply button under the checkboxes saves it (`_apply_category_changes`: the settings, the `.disabled` renames and a reload), and pending ticks count (#532): generation (`MainWindow._run_enhancements_generation` when no categories are passed, which none of its callers do), Apply Enhancements (once it has saved `user.ini`, so the reload reads the table's own overrides back), Export Settings (once a file is picked, so a cancelled export saves no tick) and the Config tab's Preview Apply (its button sends `ConfigTab.preview_starting` before `preview_merge` runs) call `apply_pending_category_changes` first, the same rule #215 gave Generate for the Tag Builder, so they build, write, back up and preview what the checkboxes show. Generation passes `reload=False`: a successful run reloads, and a failed one that saved ticks reloads through its `if_unfinished` unless its caller gave one (a language switch's reload). A launch that saved ticks also marks Apply Enhancements dirty, so an already-applied check that read the old set cannot turn it green during the run. Apply Enhancements' reload is synchronous, so its merge and the table both use the saved ticks. While a tick is pending, Apply Enhancements is red and enabled (`category_ticks_changed` to `MainWindow._on_category_ticks_changed`, which marks it dirty, so closing offers Apply Now unless a revert of the game file has cleared that reminder since), and an already-applied verdict cannot turn it green (`_apply_applied_state_verdict`), because the check merges the saved set. Ticks put back re-run the check, except while closing, with nothing loaded or with a load running, as after a blueprint scan. While a job runs (#483) the category Apply button is locked, and so is every other way to save a tick: `apply_pending_category_changes` saves nothing then, so Apply Enhancements, Export Settings and Preview Apply leave the tick pending (the renames would land in the folder a generation writes), and `_mark_applied` keeps Apply Enhancements red for it. A generation's own launch is not a job yet, so it always saves. Locking and unlocking refresh the button through `_refresh_category_apply_btn`, not the tick handler, so they tell MainWindow nothing and leave Generate's record alone. A tick lights Generate too, and ticks put back put Generate back as it was before the first one, unless another change lit it meanwhile (`_generate_dirty_without_ticks`, which `_mark_enhancements_dirty`, `mark_enhancements_clean`, `set_operation_idle` and `refresh_enhancements_dirty_state` keep up to date): it used to stay lit as if something had changed. Saving the ticks (`_save_category_state`) does the same when they only turned categories off, whose files are just set aside, and keeps Generate lit when one was turned on, whose files may be missing or set aside from an older run. A generation that saves the ticks builds them, so its launch leaves Generate clean. A tick counts once Generate or Apply Enhancements has used it, so closing without either drops pending ticks and the next start shows the saved set. Leaving the tab keeps pending ticks and the category Apply button stays lit. `revert_category_checkboxes` resets every box after Import Settings, and only the offered ones after the enhancement category question, which can also come after a channel switch or a global.ini extraction, so a tick pending on another category stays. The question (`_check_enhancements_freshness`) leaves out of its offer a category the tab has unticked and not saved (`pending_unticked_file_keys`): it ticks what it offers, so its Generate built a category the user had just unticked, and left out, the run's own save turns it off with its files.
- `combo_box.py` — `NoScrollComboBox` (#197: a `QComboBox` that lets the mouse wheel scroll the page instead of changing the selection when not focused, and opens its list below the box where it fits) and `reposition_combo_popup_below_if_it_fits` (#388). Used by the Enhancements, Blueprint Tracker (`_NoWheelComboBox` subclasses it) and Overlay tabs; it moved out of `enhancements_tab.py` when the third tab needed it.
- `blueprint_tracker_tab.py` — **Blueprint Tracker Tab** (#157; split out of the Enhancements tab into its own tab in 2.2.x, #222): the Available/Owned shuttle for blueprints that appear in missions' POTENTIAL BLUEPRINTS rewards, with search + Mission/Type/Class/Size/Grade filters. Owned items get an `[Owned]` tag woven into blueprint bullets wherever they appear (`src/utils/owned_items.py`). `set_blueprint_items(meta)` receives `{name: BlueprintItem}` from `MainWindow._recompute_owned` (computed by `src/utils/blueprint_meta.py::build_blueprint_metadata` from the loaded strings, which this tab can't see directly). Emits `owned_items_changed`, consumed by `MainWindow._recompute_owned`. The "Show tags on blueprint names" checkbox (#221, `AppSettings.get_/set_blueprint_show_tags`) toggles between `BlueprintItem.name` (bare, the stable matching identity) and `BlueprintItem.tagged_name` (the item's live item_Name value, tag and all) for display only — matching/filtering/Owned-tracking always use the bare name. Most of its i18n strings still live under the `enhancements.blueprints_*` namespace in `languages/*/ui.json` (unchanged on purpose — only the tab housing moved, not the strings' meaning); the tab's own title is `tabs.blueprint_tracker` / `blueprint_tracker.title`. The "Scan Logs for Owned Blueprints" button (#223 tab move; scanning itself is #222) emits `scan_logs_requested`; `MainWindow._run_blueprint_log_scan` validates the install root (`AppSettings.get_sc_install_root()`), queues the channels from `_scan_queue_for_root` (LIVE, plus HOTFIX when its folder is present; there is no checkbox, the Config channel makes no difference, and PTU/EPTU/TECH-PREVIEW are never scanned, enforced by the `_SCANNED_CHANNELS` allow-list in `_channels_to_scan` and again where `_start_next_blueprint_scan` starts each worker, #446) and reads each channel's own watermark (`AppSettings.get_blueprint_log_watermark()`), runs `BlueprintLogScanWorker` (`workers.py`, wrapping `src/utils/blueprint_log_scanner.py`'s `scan_channel`) with a progress dialog, and `_on_blueprint_log_scan_finished` normalizes the returned raw names (running the #372 foreign-name recovery only when the Config channel is LIVE or HOTFIX, because the item list it matches against is the Config channel's, #446), merges new ones into `AppSettings.set_owned_items()`, and advances the watermark (monotonically, even when nothing new was found) so a re-scan only re-reads log growth since the last run. `_finish_blueprint_scan_queue` also calls `_seed_default_owned_blueprints` (#416), which adds each starter blueprint every player owns (`blueprint_meta.DEFAULT_OWNED_BLUEPRINTS`, never logged and never a mission reward) to the Owned set once, recorded by loc key in `AppSettings.get_/set_default_blueprints_seed()`, and lists them in that scan's summary. A scan that adds blueprints then hands Apply's verdict to the background already-applied check (`_refresh_apply_dirty_after_reload`), because a starter is in no mission list and changes nothing in the game file, except while closing, with nothing loaded or with a load running (that load checks after its own re-weave). `closeEvent` settles the check again after its unapplied-changes prompt, whose event loop can deliver a scan finish. The names come from the loaded strings, so a scan that finishes before any have loaded (the startup auto-scan can) marks the seed pending and `_rebuild_blueprint_metadata` finishes it after the next load, then reports what it added the way a silent auto-scan does (`_report_blueprints_added`, shared with the scan finish). The load keeps the names and queues the report as its last step but one (`_queue_deferred_starter_report`, followed only by `_queue_asks_after_the_job`, #483, whose flush waits while any modal box is open), because an earlier modal step such as the enhancement categories prompt would run a sooner queued call inside its own event loop, and `_flush_deferred_starter_report` waits while an extraction, generation, Simple-mode run or load is going (each normally ends in a reload that queues it again, and after a failed or stopped one the report waits for the next load) and never runs while closing. It is one-shot per item: a starter moved back to Available stays there, one declared in a later release reaches Owned on the next scan, and it never raises (a failure is logged and retried on the next scan). The "Auto-scan logs on startup" checkbox (#386, `AppSettings.get_/set_auto_scan_blueprints_enabled`, off by default) drives `MainWindow._maybe_auto_scan_blueprints`, called from `_continue_startup_after_update_gate`: reuses the same channel-queue/worker pipeline as a manual click (the same LIVE-plus-HOTFIX coverage, #446), but sets `_bp_scan_silent = True` so `_finish_blueprint_scan_queue` reports through the status bar instead of the manual scan's modal summary dialogs, and shows no progress dialog either — a launch isn't the place for a popup, especially once most runs find nothing new. Silently skips (no warning dialog, unlike the manual scan) when no LIVE or HOTFIX folder is found under the install path yet. The sibling "Show popup for new blueprints found by auto-scan" checkbox (#386 follow-up, `AppSettings.get_/set_auto_scan_show_popup_enabled`, also off by default) opts a silent run's "found something new" case back into the manual scan's own modal summary dialog instead of the status bar message — checked in `_finish_blueprint_scan_queue` only on that branch; a quiet run (nothing new) ignores it and stays silent either way.
- `log_tab.py` — **Log Tab**: in-app log viewer. Bridges Python `logging` to Qt via `_LogEmitter` (thread-safe). Level filtering, auto-scroll, export.
- `error_dialog.py` — `ErrorDialogHandler` + `_ErrorDialogEmitter` bridge `logger.error(...)` / `logger.critical(...)` to a Qt modal so users see failures without opening the Log tab. - `theme.py` — palette swap on `QApplication` plus branded font loading (`load_application_fonts()` registers the Hyperspace Race OTF from `assets/fonts/`). Theme-aware widgets rely on palette `WindowText`/`Text`; dim/secondary labels mark themselves with `setProperty("role", "secondary")` and the app-level QSS rule in `apply_theme()` recolors them on live theme swap. Progress-bar contrast uses the palette's `Highlight` role (Fusion's native chunk color) — do not add `QProgressBar::chunk` QSS, it switches Qt to a styled path that stops animating in indeterminate mode. `needs_apply_style()` is the stylesheet for a button the dirty-tracking system lights up: the theme's `needs_apply` red, dimmed while the button is disabled (#483), because a stylesheet colour outlives `setEnabled(False)` and a locked button otherwise looked ready to click. `dimmed_color()` gives any stylesheet colour at `DISABLED_ALPHA` for a `:disabled` rule; it dims that red and the Simple page's button.

- `overlay_tab.py` — **Overlay Tab** (2.5.0): Start/Stop Overlay button plus one checkbox per `AppSettings.SCO_OPTION_SETTING` switch (names are `AppSettings.SCO_*` constants; a drawer section's switch is `SCO_DRAWER_SECTION_PREFIX` plus its `sco_overlay.SECTION_ICONS` name) (scan decoder, drawer, its Blueprints / Minerals / Crafting sections indented under it and greyed out while the drawer is off (names starting `drawer_`), mark new blueprints owned from Game.log, save scan samples), a drawer position picker under the drawer switch (`AppSettings.SCO_DRAWER_POSITIONS`, default middle right, greyed out with the drawer) and an Open Samples Folder button (`AppSettings.get_sco_samples_dir()`). #523 added, under the scan decoder switch and greyed out with it, a **Scan text size** picker (`AppSettings.SCO_LABEL_SIZES`, `get_/set_sco_label_size`, default medium) and, under an `overlay.alerts_title` line, one switch per watched-target alert (names `SCO_ALERT_PREFIX` plus a `sco_overlay.ALERTS` name: glow and flash on by default, color, bigger and sound off), and under the drawer's position picker, greyed out with the drawer, a **Drawer hotkey** box (`HotkeyEdit`, saved through `get_/set_sco_drawer_hotkey` as portable text; its hint's example is Alt+8 because Star Citizen's default bindings, `Data/Libs/Config/defaultProfile.xml` in Data.p4k, use every letter, F1 to F12, Home, End, Page Up and Down, Pause, Tab, Space, the arrows and `/`, and Left Ctrl and both Shifts on their own, but never 8, Insert, Delete or Alt on its own, read on LIVE 2026-10-23). Since #523 the tab is in four titled boxes like the Config and Enhancements tabs (`_group`, titles `overlay.scan_group`, `drawer_group`, `blueprint_watch_group`, `samples_group`): each part's switch first with its hint under it (`_add_switch`), what hangs under it set in (`_indented`), and the alerts and the drawer's sections side by side (`_switch_row`) with their hints as tooltips; Open Samples Folder sits beside its switch. `HotkeyEdit` (a `QLineEdit` nothing can be typed or pasted into, with a **Clear** button to its right, `clear_hotkey`, lit only while a hotkey is saved, since every key pressed in the box is taken as the hotkey) records one key combination from the Windows virtual key each press reports (`nativeVirtualKey`, through `global_hotkey.hotkey_text`), not from the character the keyboard layout makes of it: where Ctrl+Alt is AltGr, Ctrl+Alt+O makes a character such as "ó", which a `QKeySequenceEdit` takes for the key (so the combination could not be registered; found in testing), and Shift+1 makes "!". A press with no virtual key (another platform, a press sent by code) falls back to Qt's key. While only modifiers are held it shows them ("Ctrl+Alt+"; Qt leaves a modifier key's own modifier out of its press, so `_MODIFIER_KEYS` adds it back), it takes Tab and every key an app shortcut would (it accepts `ShortcutOverride`), and a combination `windows_hotkey` does not take (a key Windows has no code for, a dead key, a symbol another key also types, or a letter, digit, symbol, Space, Tab or navigation key without Ctrl, Alt or Win) is not saved: the box goes back to the saved one and says why (`refused`). `set_hotkey_problem()` shows why the hotkey is not in use (`global_hotkey.HOTKEY_TAKEN` or `HOTKEY_UNSUPPORTED`, worded by `hotkey_problem_text()` as `overlay.hotkey_taken` or `overlay.hotkey_unsupported`), which `MainWindow._on_sco_hotkey_problem` passes on from `ScoOverlay.hotkey_problem` along with the same text in the status bar. The text size and position pickers are both built by `_picker_row`, and their settings read and saved through `AppSettings._get_choice` / `_set_choice` (a value outside the choices reads, and saves, as the default). Checkboxes save straight to settings and emit `options_changed` → `MainWindow._apply_sco_options` (pushes them to `ScoOverlay.set_options` and starts/stops the live log watcher); the start button emits `overlay_toggled`, which drives the toolbar Overlay button so both go through `_toggle_sco_overlay`, and `set_running()` mirrors the overlay back without re-emitting; `set_option()` likewise mirrors a switch the SCO drawer changed. `refresh_styles()` re-applies the start button's theme colour; `MainWindow.refresh_action_buttons()` calls it on a live theme swap, with the toolbar's Overlay and Tutorial buttons.
- `sco_overlay.py` — **Smart Citizen Overlay (SCO)** (2.5.0): always-on-top windows over the game, toggled by the toolbar's **Overlay** button (`MainWindow._toggle_sco_overlay`). `ScanLabelWindow` is click-through and shows the decoded mining signature centred under the scanner readout, always in the ODW colours (`ODW_OVERLAY_COLORS`, see-through at `DRAWER_ALPHA`) whatever the app theme; `BlueprintDrawer` is a stack of three tapered icon tabs (`SectionTabBar`, one per section, icons from `SECTION_ICONS` painted as `QPainterPath`s and kept upright on every edge) docked at one of eight positions (`set_position()`; `drawer_edge()` maps a corner or middle position to its side edge and top/bottom centre to the top or bottom edge, and `SectionTabBar.set_edge()` turns the stack to match). Neighbouring tabs overlap by their taper (`DRAWER_HANDLE_OVERLAP`), like browser tabs; the open section's tab is painted last and near-solid so it sits in front, and `tab_at()` hit-tests front to back so a click in an overlap goes to the tab you see. A tab click (`open_section()`) opens the see-through (`DRAWER_ALPHA`) panel, a `QStackedWidget`, straight to that section, another tab switches section, and the open section's own tab closes it. A section switched off on the Overlay tab hides its tab (closing the drawer if it was open), and with all three off the drawer is hidden (`has_sections()`). The panel takes clicks and focus, but only a search box (`DrawerSearch`, focus on a click only) ever takes the keyboard: every other widget in the panel is `NoFocus`, and a search box ignores a held key's printable repeats. In game F is held to move the mouse, and a tab click gave the Blueprints or Crafting search focus, which then filled with "ffff" (#523). - `global_hotkey.py` — the SCO drawer's system-wide hotkey (#523). `GlobalHotkey.register(sequence)` registers one key combination (QKeySequence portable text) with Windows' `RegisterHotKey` on the GUI thread, with `MOD_NOREPEAT` and its own id, and installs a `QAbstractNativeEventFilter` that turns this thread's `WM_HOTKEY` for that id into `activated`; it returns "" or why not (`HOTKEY_UNSUPPORTED`, `HOTKEY_TAKEN` with Windows' error at WARNING), and `unregister()` removes both. `RegisterHotKey` is not a keyboard hook, and the app with focus does not get the combination. A game that reads the keyboard through raw input can switch registered hotkeys off while it has focus (`RIDEV_NOHOTKEYS`), and in Star Citizen the hotkey never arrived, so while one is held `register()` also opens a message-only window (`CreateWindowExW` with `HWND_MESSAGE`, kept in `sink_hwnd`) and has the keyboard's raw input sent to it with `RIDEV_INPUTSINK`, which Windows does whatever has focus. That is read-only: nothing is held up, changed or sent, and the game still gets the keys. The filter hands `WM_INPUT` for that window to `raw_message` (read once, then left to Windows' default handling, which frees it), and `RawCombination` turns the ordered stream of presses and releases into the moment the key goes down with exactly the combination's modifiers: a key repeat does not count, and a modifier held past `STALE_AFTER` is checked with `GetAsyncKeyState`, so a release lost to a lock screen does not leave it held. Outside a game one press arrives both ways, so a raw sighting waits `RAW_GRACE_MS` for its `WM_HOTKEY` (which can bring the drawer to the front where raw input may not), and a press toggles once within `SAME_PRESS_S` however it came. Raw input Windows refuses leaves the plain hotkey, with an INFO line. `windows_hotkey()` maps a combination to Windows' modifiers and virtual key: letters, digits (numpad digits too), F1 to F24 and the layout-independent named keys in `_NAMED_KEYS`; a symbol key (an OEM key in `_SYMBOL_VKS`) types what the keyboard layout says, so it is saved as the symbol it types unshifted ("Ctrl+/", by `layout_symbol`, MapVirtualKeyW) and found again through the layout (`layout_symbol_key`, VkKeyScanW, checked against the key's own unshifted symbol, so a symbol that needs Shift, a dead key or one the layout has no key for gives None). Any key but an F key or Pause held without one of `MODIFIERS_NEEDED` (Ctrl, Alt or Win; Shift alone is not enough) gives None too: alone it would toggle the drawer on every press in game, and Windows would take it from every other program while the overlay runs. `hotkey_text()` is its inverse for the Overlay tab's box: Qt modifiers and a Windows virtual key to the portable text it saves (None for a key `windows_hotkey` does not take), every supported key and modifier mix reading back the same. `foreground_window()` and `give_focus_back()` wrap `GetForegroundWindow` and `IsWindow` + `SetForegroundWindow` on a private copy of user32.

## Design decisions

### Sortable columns require indirect row lookup
The table is a `QTableView` backed by `StringTableModel` (`string_table_model.py`), which holds a filtered/sorted list of indices into `self.entries`. Row index ≠ entry index when sorted or filtered. **All row→entry lookups go through `_entry_index_for_row(row)`** on `MainWindow` (which delegates to `self._model.entry_index_for_row(row)`). Direct indexing into `self.entries` by row number gives wrong results. Use the `COL_*` constants from `string_table_model.py`, not hard-coded column numbers.

### A reload keeps the edits user.ini does not have (#531)
Every reload (`perform_merge_and_reload`, and `_on_loading_finished` for the async loader) builds the entries from disk, so `custom_value` comes only from user.ini, and `_snapshot_pending_user_edits` / `_restore_pending_user_edits` put the user's unsaved edits back on top. An unsaved edit is a value that differs from what user.ini held when the table was last loaded or saved: `_record_reloaded_overrides` records that from the fresh entries before the restore, and `_remember_saved_overrides` records what `save_user_ini` wrote once `apply_to_game` has saved (only the overrides that differ from their original, as it writes them). A cleared override ("") counts too, so a Reset to Original, an emptied Custom cell or a removed favourite stays cleared through a reload. Taking every non-empty value, as the snapshot used to, brought such an override back from the old user.ini, and the next Apply or the close-time autosave saved it again. Values the user did not touch are left to the file, so Restore user.ini and Import INI, which write user.ini and then reload, win over the table's old values instead of losing every key the table already had. Import first puts the values it changed into the table, so an unapplied change to the same key does not win over them either. A conflict kept as it is (Keep Current) changed nothing, so the table's own change of that key stays. Restore user.ini and Import Settings with Restart Later put the user.ini they wrote into the table (`_take_replaced_user_ini`): its values win over unapplied changes to the keys it holds, an override the user had not changed goes with the old file, and other unapplied changes stay. What was written is recorded, so a user.ini with no override is not taken for one the reload could not read, and a reload that fails leaves the table as the new file says. Each parses what it writes, Restore the picked snapshot before restoring it and Import Settings the backup's own text (`ini_parser.parse_ini_text`), not a second read of the user.ini just written, which another program can block for a moment. Import Settings' table used to keep its old overrides and save them over the import at the next close or Apply. Every backup carries its active channel, so an import made on another channel switches channel under the window, and then only Restart Now is offered: carrying on saved the old channel's table into the new channel's user.ini. Reset user.ini records user.ini as empty, by the user's choice, so its reload is not taken for a file that could not be read, and a later Restore or the backup renamed back is not cleared again. It also saves a snapshot first (`reset_user_ini`), so Restore user.ini can undo it, and an empty user.ini, which holds no override and leaves no snapshot, gets the same nothing-to-reset box as a missing one. A reload that reads no override at all from the user.ini the record says held some is not trusted: that file could not be read (another program held it, a share dropped for a moment), so every override in the table is restored, the record is kept and a WARNING is logged. A reload that reads another user.ini than the one recorded (a channel switch or a data-folder change repoints the user source) still restores every non-empty override in the table, on purpose: the overrides follow the user to the new channel. A clear does not follow, so a reset not yet applied comes back from that user.ini after a data-folder Move or a channel switch and back, until it is applied. user.ini is written in one step through `atomic_io` (`user_ini_manager.write_user_ini_text`, which `save_user_ini`, `save_user_ini_dict`, Import Settings and the favourite prefix migration use, and Restore user.ini's copy), so a failed save keeps the old file and the record stays true. A cleared row reads as a load would show it (`ini_parser.status_without_override`: Enhanced, New or Unmodified) after the reload, Reset to Original, a removed favourite, an emptied Custom or Sort Order cell and an emptied editor dock. Reset to Original, a removed favourite and a cleared Sort Order used to say Unmodified, and an emptied cell or dock Modified, which also let a reset discovered item into the merge while Include discovered items is off, since Apply leaves out only New rows. `tests/test_reload_keeps_unsaved_edits.py` locks this.

### Frontend version stamp on apply
At apply-to-game time, `main_window._stamp_frontend_version(merged)` appends `\nLocalizations Enhanced with Smart Citizen v{VERSION}` (a literal `\n` — the loc-string line-break convention, same as the journal stamp) to the launcher's `Frontend_PU_Version` loc-key, putting the watermark on its own second line rather than crowding the build-info line. `_FRONTEND_VERSION_STAMP_RE` strips any prior stamp before re-applying — including the original " | "-separated form pre-2.3.0 installs have on disk — so the suffix doesn't pile up across applies or version upgrades. If the key is absent from the merge (older patches, custom configs), the stamp is skipped — never inserted. `tests/test_frontend_version_stamp.py` locks the no-double-stamp guarantee.

### An anticipated extraction failure opens one box (#482)
`P4kExtractWorker` and `DataForgeExtractWorker` report a failure from one `except Exception` branch, after the stop check, so a failure that races a Stop is reported as the stop. A failure in `pak_extractor.ANTICIPATED_EXTRACTION_ERRORS` (a locked Data.p4k, an unforge timeout, a drive without enough free space, a working folder Windows refused (#490), and for a DataForge run in `%TEMP%` a folder where the cache folder could not be made again after the wipe (#494), and a DataForge cache folder that is a junction or a symbolic link (#491)) carries its own translated message and was logged at WARNING where it was raised, so the worker logs it at WARNING too and emits `error`. Anything else goes to `logger.exception`, which opens the global error dialog. `_on_dataforge_extract_error` logs the message at WARNING, never ERROR, before its own box: an ERROR record there opened a second box on top of an anticipated failure's, or added a stray "(+1 suppressed)" to an unexpected one's. `tests/test_extraction_stop.py` locks both, and `TestRefusedWorkingFolderReachesTheUser` follows a refused working folder from the real extraction to one box, as `TestLinkedCacheFolderReachesTheUser` does a cache folder that is a junction.

### Status checks never create the DataForge cache folder (#494)
`get_dataforge_cache_dir()` creates the cache folder, so a status check that called it raised when Windows refused the folder (its permissions, Controlled folder access) or its drive was gone. Building the Enhancements tab is such a check, so Smart Citizen could not open, and a channel or language switch, a data folder change and the Enhancements Apply stopped halfway with the crash dialog. The tab's `refresh_forge_status` and `_compute_initial_enhancements_dirty`, the window's freshness checks, Clear Cache (#479) and `EnhancementsGeneratorWorker` read `get_dataforge_cache_leaf()`, which creates nothing; a missing folder has no stamp, so it reads as not extracted. `_run_dataforge_extraction` creates it, because it is about to write the cache (`_run_p4k_extraction` also makes it, only so the global.ini extraction can work beside it, and works in `%TEMP%` when it cannot). When that fails it reports the folder in one box before any worker or progress dialog is built, the text picked by `settings.cache_folder_failure` (`extract.cache_folder_refused` with the cache advice for a refusal, `extract.cache_folder_unreachable` for a folder or drive that is not there, a drive that is not ready included, and `extract.cache_folder_unusable` with Windows' own reason for anything else), logs the Windows error at WARNING, ends a Simple run, lights Generate again and returns False. Just before that getter it asks `pak_extractor.linked_cache_folder_error` about the cache folder (#491): one that is a junction or a symbolic link is refused in the same one box, with `extract.cache_folder_is_link`, because the extraction deletes nothing through a link, and a link whose target is gone would fail the getter with Windows' "file already exists" and get the could-not-use text instead. A cache folder that is already there passes that call even when the folder holding it refuses new folders. A run working beside the cache is then refused by #490's working-folder check, and a run working in `%TEMP%` (a OneDrive, network, removable or deep cache) by `pak_extractor`'s check that the cache folder can be made again after the wipe, both before any tool runs and with the old cache kept; that run used to wipe the old cache first and then fail with three boxes: the global error box, the error slot's and the crash dialog. The Config tab's `_maybe_apply_cache_change` reads the old cache folder through the leaf too, so a saved folder Windows refuses, or one on a drive that is gone, can be left with Reset or another folder. It still saves the new folder before making its cache folder (the resolved path comes from the same code production uses), but undoes the save on an `OSError` exactly as Cancel does and raises it again; `_save_cache_dir` and `_reset_cache_dir` then report through `_report_cache_folder_error`: one box titled `config.invalid_cache_folder_title` naming the folder that was tried (the typed or picked folder resolved, or `AppSettings.get_default_dataforge_cache_base()` for a reset or a cleared field), the text picked by the same `cache_folder_failure`, so the two places cannot disagree: `config.cache_folder_refused` with #490's `extract.folder_refused_fix` for a refusal (not the advice to choose another cache folder, which the user is doing), `config.cache_folder_unreachable` for a folder or drive that is not there, and `config.cache_folder_unusable` with Windows' own reason for anything else (a typed name Windows does not take, a path through a file), the Windows error at WARNING, and the field back on the folder that is saved. A file gets `config.cache_folder_is_file`. Nothing is emitted for a change that did not happen. The field's `editingFinished` reaches `_save_cache_dir` through `_cache_dir_edited`, and only when the user typed in the field (`isModified()`, which typing sets and `setText` clears). Qt also sends that signal when the field loses focus after a `setText`, and the field is filled that way when the tab is built and after every box, so a click into the field and out again used to try the saved folder again: with a saved folder that cannot be used it opened a box for a change nobody asked for, and the click away after a failed change opened a second one naming the saved folder. Enter with nothing typed does nothing either (`hasFocus()` cannot tell it apart, because a menu that opens while the field has the focus sends the same signal with `hasFocus()` still true), while the saved folder typed again is a change and gets its one box. Browse calls `_save_cache_dir` itself. `tests/test_extraction_stop.py`, `tests/test_refused_cache_window_paths.py`, `tests/test_enhancements_tab_refused_cache.py`, `tests/test_startup_refused_cache.py`, `tests/test_config_tab_cache_folder.py`, `tests/test_cache_folder_strings.py`, `tests/test_generator_refused_cache.py` (the generator worker) and, for the `%TEMP%` check, `tests/test_extraction_working_folder.py` lock this.

### Apply button turns green when nothing has changed (#387, #397, #398)
After every reload, `_on_loading_finished` calls `_refresh_apply_dirty_after_reload`, which starts an `AppliedStateWorker` (a background thread, so the seconds of re-reading and re-merging never block the GUI) that compares what a real apply would write against the game's on-disk `global.ini`. It runs on every reload, not only the first, because Simple mode applies and then reloads, and `_recompute_owned` marks every reload dirty, so only an authoritative check can settle the button afterward. `_merge_for_apply` is the one merge shared by `apply_to_game` and the check (so they can never compute different content), and `_compute_already_applied` does the comparison on a plain-data `_AppliedStateSnapshot` that `_apply_merge_inputs` captures on the main thread. The check drops the on-disk `user` source that `load_sources_from_settings` returns and merges only the snapshot's overrides: Apply saves `user.ini` from the loaded entries before it reloads the sources, and the copy on disk can still hold an override the user has since cleared. The comparison walks the stock `base.ini` key set specifically: `merge_ini_files` only ever overwrites a key present in its structure-preservation source file, so a merged key `base.ini` lacks is never written and must be excluded, or any profile with such a key would read dirty even right after a genuine apply. It also requires `user.cfg`'s `g_language` to match the selected language, since switching language in the UI never touches `user.cfg`. The applied file is parsed with `strip_values=False`: the writer puts every merged value in verbatim, and a user override can start or end with a space (a space favourite prefix, #100), so stripping that side made such an override read red after every real apply. Any doubt (no applied file, no stock `base.ini`, an error, an interruption) reads as "not applied": wrongly showing green would hide a real pending change. `_set_apply_btn_dirty` forwards every state change to the Simple-mode page's button too. That one stays clickable when green, because a click still regenerates and re-applies (after a game patch, for example).

Because the verdict arrives later, `_applied_check_token` guards it. An edit (`_mark_apply_dirty`), Apply's write (`_invalidate_applied_check`, just before `merge_ini_files`), a successful apply (`_mark_applied`), the game file changing outside Apply (`_mark_game_file_changed`) or a newer reload bumps the token, and a verdict computed from an older snapshot is dropped instead of overwriting the state those events set. One check runs at a time; a reload that lands mid-check interrupts it and queues a single rerun that snapshots the newer state. `closeEvent` calls `_settle_applied_state_check`, which waits for a running check and applies its verdict: the thread must be gone before exit, and a reload sets `_session_has_unapplied_edit` provisionally, so closing right after a clean apply would otherwise warn about changes that don't exist. Cancelling that close prompt, or choosing Apply Now when the apply stops before it touches the button (a declined prompt, a failed `user.ini` save), re-runs the check, since settling may have dropped a verdict or a queued rerun to close quickly.

`apply_to_game` returns True only for a written and validated apply. It invalidates any in-flight check right before it writes the game file, because a dialog later in the apply runs the event loop and could deliver a verdict about the file being replaced. A failed write or failed validation marks the button dirty before its error dialog, and a successful one marks it applied before its success dialog, for the same reason: a change that dialog's event loop delivers (a blueprint scan finishing, #416) then stands, rather than being painted over afterwards. Deleting the game file (`clear_localization`) or restoring a backup (`restore_backup`) turns the button red through `_mark_game_file_changed`, which also clears `_session_has_unapplied_edit` (Restore clears it again after its own reload, where `_recompute_owned` sets it). So closing after a deliberate revert does not offer to re-apply over it, while the red button still says an apply is due. Clearing rather than keeping the flag is deliberate: a reload sets it provisionally until its check answers, and a revert drops that answer, so a kept flag could be a placeholder nothing would ever clear. Both mark only once the file really changed: a failed restore is no revert, so it keeps the close reminder. It re-runs the check before its error dialog instead, which drops any verdict about the old file and reads whatever a part-way copy left on disk. The synchronous reload in `perform_merge_and_reload` starts the check just like the async loader does. `_reload_follows_clean_apply` is a one-shot set by Simple mode's apply-then-reload so that reload doesn't paint the button red while the check re-confirms it. It is set only when `apply_to_game` returned True, and a failed reload clears it.

### Closing stops a running extraction (#471)
`closeEvent` used to leave a running extraction alone, and a closed app left unp4k or unforge running on its own (measured: unforge carried on ~23 s past the exit while Python's exit-time cleanup failed under it, and its ~2 GB stayed in `%TEMP%`). Once every prompt that could call the close off has been answered, `closeEvent` sets `_close_committed` and calls `_request_stops_for_close()` ahead of the unbounded loader wait, so the tool dies at once; last, after the window state is saved, `_stop_workers_for_close()` hides the window and waits (one 180 s deadline for every worker, like `_settle_applied_state_check`) while the worker deletes its working folder. Past the deadline the reference is kept so Qt doesn't destroy a live thread, and the next extraction's sweep removes what is left. It detaches each progress dialog from its worker (`_detach_progress_dialog`) and dismisses it with `cancel()`: a hidden `QProgressDialog` shows itself again while progress keeps arriving, and a plain `hide()` (what Esc does) is undone by its own show timer when the dialog is under 4 s old (measured: back 3.5 s after an Esc at 0.5 s). The extraction slots are bound to their worker (as `_launch_applied_state_check` does) and ignore a released one, and `_close_committed` keeps `_run_dataforge_extraction`, `_run_p4k_extraction`, `_run_enhancements_generation`, `_check_enhancements_freshness` and `_maybe_prompt_dataforge_refresh` from starting anything new: Qt still delivers queued signals after `closeEvent` returns. Enhancement generation's slots are bound and guarded the same way: a finished that arrives after the close committed only reaps the worker and ends a Simple run, so it neither applies to the game nor starts a reload with its modal dialog during exit, and an error then is logged at WARNING with no dialog. Generation is the third worker closing stops (`_WORKERS_STOPPED_ON_CLOSE`): it is asked with the extractions ahead of the loader wait, its dialog is detached and cancelled, and it is waited for under the same 180 s deadline with the window hidden. The generator's `main()` takes `should_cancel` and raises `GenerationStopped` at its next job boundary (after each parse and the XML path index, before each lookup and each generator, and just before the write phase), never during its writes, so every INI is whole: all old if it stopped before writing, all new once the writes began, in which case the run also certifies the set. A stop after `main()` began leaves `.dataforge_stamp` empty, so the next start offers to generate again. Past the deadline the reference is kept, with its own warning. The stop is silent by design (no prompt), so the update installer and Import Settings relaunches, which ignore `close()`'s result, need nothing special.

Esc or the X on the DataForge progress dialog used to hide it while the extraction carried on unseen, which is how a user got to close the window mid-run. The dialog's close guard now asks what to do (`_confirm_stop_dataforge_extraction`: Stop, Run in Background or Cancel, Cancel being the default and what Esc picks). Run in Background (#483) and the lock that makes it safe are under *Run in Background and the job lock* below. **Stop** requests the stop, and the finished slot reports "stopped" rather than "failed" (it reads the worker's own `stopped` record: QThread reports no interruption once a thread has finished, and the slot waits for the thread first). A Simple-mode run can no longer apply, but its page stays busy until the stop has finished and the finished slot ends the run, so the button never looks ready while a click would be turned away. Stop dismisses the dialog for good: `_detach_progress_dialog` disconnects the worker's progress from it and it is deleted, because a hidden `QProgressDialog` shows itself again while progress keeps arriving (measured within a second of Esc or the X; `TestDismissedDialogStaysHidden` keeps the control that shows it). If the run finishes while the question is open, its slot has already moved on to generation, so Stop stops that generation instead when it took this dialog over (#483), and still ends a Simple-mode run so nothing is applied to the game (and `_on_enhancements_generation_finished` releases the page whether or not a Simple run is active). The same dialog is handed to enhancement generation, so `_run_enhancements_generation` swaps in generation's own guard at the hand-off, and a generation started on its own (Generate, Save Tag Changes) gets a dialog with the same guard: `_confirm_stop_generation` asks Stop, Run in Background or Cancel too, with generation's own wording (`extract.generation_running_*`), because a plain hide came back as soon as more progress arrived. Its Stop (`_stop_generation_from_dialog`) ends the run at its next job boundary, never during its writes, applies nothing after it in Simple mode, and the finished slot says "stopped" (`status_bar.enhancement_generation_stopped`, read from the worker's `stopped`) rather than "failed". Its Run in Background (`_send_generation_to_background`, also what the DataForge question uses when generation took its dialog over) dismisses the dialog for good and the status bar reports. Closing the window still stops a generation, as before. Esc or the X on the global.ini dialog stops that extraction without asking (`_stop_p4k_extraction_from_dialog`, also a close guard): it is a short job that writes `base.ini` only at its very end, so a stop leaves the old one as it was, and the status bar says "global.ini extraction stopped". It used to hide the dialog while unp4k carried on unseen, and Extract then started a second run that replaced `_p4k_worker`, so closing stopped only the second and left the first unp4k running. `_run_p4k_extraction` now starts nothing while `_p4k_worker` is set, and the stop makes sure that never leaves Extract waiting on a run the user cannot see. Startup, a channel switch and a data-folder change leave their reload to the extraction `_check_p4k_freshness` starts, and only a success used to reload, so they now pass what they do when it is declined (`if_unfinished`: `_finish_startup_load`, `_reload_after_channel_switch`, `_reload_after_data_dir_change`) and the finished slot runs it after a stop or a failure, instead of leaving no strings or the old channel's. A success reloads by itself and drops the follow-up, so when there is one it first asks `_maybe_prompt_dataforge_refresh`, the question each of those callers asks before its own reload (#478): dropping the follow-up used to drop that question too, so right after a game patch an outdated DataForge cache went unmentioned until the next launch. A Yes runs the DataForge extraction beside the reload, as at startup. The Config tab's Extract button starts a run with no follow-up and asks nothing. A failure shows its error box first, and the finished slot usually runs inside that box's own event loop, so it parks the follow-up (`_p4k_follow_up_after_error`) for `_on_p4k_extract_error` to run once the box has closed rather than stacking a reload or a prompt on top of it. `_run_p4k_extraction` returns whether it started, so a Yes while one is already running carries on as declined at once. A run cut off between the cache wipe and the stamps (a crash, or a close that outlasted its 180 s wait) leaves content with no `.p4k_mtime`; `_maybe_prompt_dataforge_refresh` treats that as stale and prompts, instead of letting it pass for "never extracted". `tests/test_extraction_stop.py` locks this.

### Run in Background and the job lock (#483)
Run in Background dismisses the DataForge dialog for good (`_send_dataforge_run_to_background`: detached from the worker as Stop does, since a hidden `QProgressDialog` comes back while progress keeps arriving), marks the worker `in_background`, and the status bar reports. The finished slot hands that on to `_run_enhancements_generation(background=True)`, which makes no dialog and connects the worker's progress to the status bar only. If the run finished while the question was open, generation has already taken the same dialog over, so Run in Background detaches it from generation instead and the answer still holds. It was tried and dropped before 2.4.0 because the window can be used while the run goes on, which was already true of a generation whose dialog Esc had hidden. So one job runs at a time, and what a job depends on is locked while any job runs, shown or not. The jobs are the three closing stops (`_WORKERS_STOPPED_ON_CLOSE`): a global.ini extraction, a DataForge extraction and a generation. `_job_running()` says whether one runs. `_run_p4k_extraction`, `_run_dataforge_extraction`, `_run_enhancements_generation` (beside an extraction), `_run_enhancements_pipeline` and `_run_simple_apply` start nothing while one does, `_check_enhancements_freshness` asks nothing, and a refused extraction or pipeline says why in the status bar. Two startup questions come right after the startup sync, which can start a global.ini extraction, so a job can be running when they are asked or start while they are open: the post-import Apply Now (`_maybe_prompt_post_import_apply`, whose pipeline would be refused) and the OneDrive warning (`_maybe_warn_onedrive_data_dir`, whose Move would change the data folder under the job). Each is put off with `_ask_after_the_job`, before it is shown or after an answer that a job started under, and asked again after the load that ends the job: `_queue_asks_after_the_job` is the last step of both load paths, after `_queue_deferred_starter_report` and for its reason, and `_flush_asks_after_the_job` waits, like that report, while a load, a job or a Simple run is going, never runs while closing, and while any modal box is open looks again every `_ASK_AFTER_MODAL_RETRY_MS` (that report's own summary box can be open then, and so can closeEvent's unapplied-changes prompt before the close is final, where an Apply Now would start a run the exit stops). A failed or stopped job that ends in a load (the global.ini extraction's follow-up for startup, a channel switch or a data folder change) asks them after it as usual; one that ends in no load (a DataForge run, a generation with no follow-up) leaves them waiting for the next load, and each is asked at the next start anyway. Nothing is lost meanwhile: Import Settings' flag is kept (put back after a refused Apply Now), the OneDrive warning comes at every start until it is answered, and a Move put off does not keep its "don't warn again". `_refresh_job_lock()`, called wherever a job's worker is set or cleared and when a Simple run starts or ends, locks with one reason (`extract.locked_while_job_runs`): the Config tab's game, data and cache folders, channel, language and Map Language File, its global.ini Extract, the install scan (Verify Install Location, which can save a game folder), Import Settings (whose restart starts the new copy before this one closes) and Check for Updates (the installer relaunches the app), through `ConfigTab.set_data_locations_locked`, which shows the reason in a label under the tab's instructions. The install scan and the update check keep their own busy state, so unlocking leaves either button off while it runs. It also locks the Enhancements tab's Apply Category Changes, Save Tag Changes and Generate Enhancements (`set_changes_locked`: the first renames INIs in the folder a generation writes and starts a reload, the second saves the tags and asks for a regeneration one job at a time would refuse, and the third would start that refused run; the checkboxes and the Tag Builder stay free and the change waits for the button, and a change made meanwhile keeps Generate off, with the running job's own message as its tooltip when it set one) and the Simple page's button, busy with the reason as its tooltip and its fill and text dimmed (`_end_simple_run` no longer frees it while a job still runs). A lit button the lock or a running job disables (Generate Enhancements, Save Tag Changes, the Config tab's Extract) keeps a dimmed red (`theme.needs_apply_style`), so a pending change still shows without the button looking clickable. Both dim through `theme.dimmed_color` (`DISABLED_ALPHA`), because a stylesheet colour outlives `setEnabled(False)`. Nets behind the lock: the finished slot checks the run still matches the settings (`_dataforge_run_matches_settings`, the channel and the cache base the worker recorded when it started, compared without making any folder) before it drains `_cleanup_pending_old_cache()` or chains generation, and says why when not (`extract.dataforge_settings_changed`); a language switch during an extraction loads the prose and leaves generation to the extraction's own chain; `ConfigTab._save_game_path` refuses while locked, and `_use_install_root` says why before it touches the field (an install scan finishing during a job could otherwise save one through its results dialog, and its failure box blamed a disconnected drive); `ConfigTab._save_data_dir` refuses while locked and puts the field back (`change_data_dir_to`, the OneDrive warning's Move, reaches it without the locked field); a scan that finishes during a job leaves its button locked (`_refresh_locked_controls`); Import Settings and an update's install refuse while a job runs. `restart_app` (the font size) closes first, so it needs nothing. `tests/test_run_in_background.py` locks this.

### A cut-off generation is offered again at the next start (#476)
The startup check (`_check_enhancements_freshness`) used to ask only whether each enabled enhancement INI existed. A generation cut off part-way (the window closed, the app crashed, a write failed) left every INI there, each whole but the set a mix of old and new, and the next start stayed quiet. Now `EnhancementsGeneratorWorker` empties the `.dataforge_stamp` of the language it generates just before the generator's `main()` (after the patches and the module load, so a failure there keeps a good stamp) and writes it only once `main()` has returned. The check also asks when every file is there but `AppSettings.enhancements_built_from_current_dataforge()` says the set was not built from the current DataForge build: the last run was cut off or failed, or the set came from older game data. It asks that only when the DataForge cache is fresh (`_out_of_date_build_key`): an outdated cache is `_maybe_prompt_dataforge_refresh`'s question, so this one would stack on it or ask again after it was declined, and a cut-off extraction or a cache never extracted has nothing to generate from. In that case the category dialog offers every enabled category (less any the Enhancements tab has unticked and not saved), ticked with its plain label, under `extract.outdated_categories_body` ("out of date", with no count: the count's noun says "missing" in several languages). The answer holds for the rest of the session (`_enhancements_prompt_answer`, reset by a channel or data-folder change). Skip is never turned into a run by a later call, such as the one after a global.ini extraction, which used to run the pipeline silently, possibly a DataForge extraction the user had just declined. It is recorded before the dialog opens, because the dialog's event loop can deliver another load, and that call must start nothing. Nothing about the answer is kept on disk, so the question comes back at every start until the set is generated, like the missing-files question. The Generate button stays lit while a ticked category's set is not current, and the language switch (`_language_enhancements_fresh`, English included) uses the same test, so the three never disagree. A run that finishes re-reads this from disk (`set_operation_idle`), so one whose final stamp write failed (`set_enhancements_stamp` only logs that, and the run still succeeds) leaves the button lit over the set the next start will ask about. The worker also captures its folder, the build key and the tag fingerprint when its run starts: reading them when it ended let a channel, data-folder or cache-folder change during a hidden run stamp a set the run never wrote. Closing the window during a generation stops it at its next job boundary (see *Closing stops a running extraction* above), which after `main()` began is one of these cut-off runs, so the next start asks. `tests/test_enhancements_stale_startup.py` locks this.
