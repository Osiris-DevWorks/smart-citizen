# src/gui/CLAUDE.md

GUI layer (PyQt6). See the root `CLAUDE.md` for project context and cross-cutting design decisions.

## Files

- `main_window.py` — main window with table, toolbar, filters, backup/restore, DataForge extraction trigger, worker orchestration. The largest file in the repo; runs the core workflow load→merge→edit→apply. Workers live in `workers.py`; pure-Python helpers (`validate_applied_file`, `filter_entry_indices`, `markdown_to_html`) live in their own modules and are wrapped by thin `MainWindow` methods. Owns `_stamp_frontend_version` — see *Frontend version stamp on apply* below. Less-frequent toolbar actions (restore backup, clear localization/cache, import/export INI, open loc dir) live under a **More** overflow `QMenu` (2.0). `_on_language_changed(language)` runs the language-switch pipeline (2.0, #30): cancel any in-flight loader, `i18n.set_language()` + `retranslate_ui()`, then `_apply_language_base_source()` repoints the `global` source at that language's base.ini (downloading it via `LanguageBaseDownloadWorker` when a URL is mapped; falling back to a cached copy, then to English), and `_reload_with_language_enhancements()` regenerates that language's enhancements first when the `.dataforge_stamp` is stale (skipped if no DataForge cache: prose loads without stat overlays). English goes through it too whenever its base.ini exists, because a re-extraction made while another language was selected regenerated only that language. That regeneration is the switch's launch: it clears the Generate button first, as `_run_enhancements_pipeline` does (#292), and leaves the switch's reload to the run. A run that fails still loads the language picked, with the stats it has: `_run_enhancements_generation` keeps its `if_unfinished` in `_after_unfinished_generation`, and the finished slot runs it once the run's error dialog has closed (parked in `_after_error_dialog`, which `_show_error_dialog` runs as it closes). `_run_enhancements_generation` returns whether it started, like `_run_p4k_extraction`, and a start refused because a generation is already running loads the language at once. user.cfg's `g_language` is NOT set here; that happens at window init and apply-to-game time.

## Design decisions

### Sortable columns require indirect row lookup
The table is a `QTableView` backed by `StringTableModel` (`string_table_model.py`), which holds a filtered/sorted list of indices into `self.entries`. Row index ≠ entry index when sorted or filtered. **All row→entry lookups go through `_entry_index_for_row(row)`** on `MainWindow` (which delegates to `self._model.entry_index_for_row(row)`). Direct indexing into `self.entries` by row number gives wrong results. Use the `COL_*` constants from `string_table_model.py`, not hard-coded column numbers.

### Frontend version stamp on apply
At apply-to-game time, `main_window._stamp_frontend_version(merged)` appends `\nLocalizations Enhanced with Smart Citizen v{VERSION}` (a literal `\n` — the loc-string line-break convention, same as the journal stamp) to the launcher's `Frontend_PU_Version` loc-key, putting the watermark on its own second line rather than crowding the build-info line. `_FRONTEND_VERSION_STAMP_RE` strips any prior stamp before re-applying — including the original " | "-separated form pre-2.3.0 installs have on disk — so the suffix doesn't pile up across applies or version upgrades. If the key is absent from the merge (older patches, custom configs), the stamp is skipped — never inserted. `tests/test_frontend_version_stamp.py` locks the no-double-stamp guarantee.

### Apply button turns green when nothing has changed (#387, #397, #398)
After every reload, `_on_loading_finished` calls `_refresh_apply_dirty_after_reload`, which starts an `AppliedStateWorker` (a background thread, so the seconds of re-reading and re-merging never block the GUI) that compares what a real apply would write against the game's on-disk `global.ini`. It runs on every reload, not only the first, because Simple mode applies and then reloads, and `_recompute_owned` marks every reload dirty, so only an authoritative check can settle the button afterward. `_merge_for_apply` is the one merge shared by `apply_to_game` and the check (so they can never compute different content), and `_compute_already_applied` does the comparison on a plain-data `_AppliedStateSnapshot` that `_apply_merge_inputs` captures on the main thread. The check drops the on-disk `user` source that `load_sources_from_settings` returns and merges only the snapshot's overrides: Apply saves `user.ini` from the loaded entries before it reloads the sources, and the copy on disk can still hold an override the user has since cleared. The comparison walks the stock `base.ini` key set specifically: `merge_ini_files` only ever overwrites a key present in its structure-preservation source file, so a merged key `base.ini` lacks is never written and must be excluded, or any profile with such a key would read dirty even right after a genuine apply. It also requires `user.cfg`'s `g_language` to match the selected language, since switching language in the UI never touches `user.cfg`. The applied file is parsed with `strip_values=False`: the writer puts every merged value in verbatim, and a user override can start or end with a space (a space favourite prefix, #100), so stripping that side made such an override read red after every real apply. Any doubt (no applied file, no stock `base.ini`, an error, an interruption) reads as "not applied": wrongly showing green would hide a real pending change. `_set_apply_btn_dirty` forwards every state change to the Simple-mode page's button too. That one stays clickable when green, because a click still regenerates and re-applies (after a game patch, for example).

Because the verdict arrives later, `_applied_check_token` guards it. An edit (`_mark_apply_dirty`), Apply's write (`_invalidate_applied_check`, just before `merge_ini_files`), a successful apply (`_mark_applied`), the game file changing outside Apply (`_mark_game_file_changed`) or a newer reload bumps the token, and a verdict computed from an older snapshot is dropped instead of overwriting the state those events set. One check runs at a time; a reload that lands mid-check interrupts it and queues a single rerun that snapshots the newer state. `closeEvent` calls `_settle_applied_state_check`, which waits for a running check and applies its verdict: the thread must be gone before exit, and a reload sets `_session_has_unapplied_edit` provisionally, so closing right after a clean apply would otherwise warn about changes that don't exist. Cancelling that close prompt, or choosing Apply Now when the apply stops before it touches the button (a declined prompt, a failed `user.ini` save), re-runs the check, since settling may have dropped a verdict or a queued rerun to close quickly.

`apply_to_game` returns True only for a written and validated apply. It invalidates any in-flight check right before it writes the game file, because a dialog later in the apply runs the event loop and could deliver a verdict about the file being replaced. A failed write or failed validation marks the button dirty before its error dialog, for the same reason. Deleting the game file (`clear_localization`) or restoring a backup (`restore_backup`) turns the button red through `_mark_game_file_changed`, which also clears `_session_has_unapplied_edit` (Restore clears it again after its own reload, where `_recompute_owned` sets it). So closing after a deliberate revert does not offer to re-apply over it, while the red button still says an apply is due. Clearing rather than keeping the flag is deliberate: a reload sets it provisionally until its check answers, and a revert drops that answer, so a kept flag could be a placeholder nothing would ever clear. Both mark only once the file really changed: a failed restore is no revert, so it keeps the close reminder. It re-runs the check before its error dialog instead, which drops any verdict about the old file and reads whatever a part-way copy left on disk. The synchronous reload in `perform_merge_and_reload` starts the check just like the async loader does. `_reload_follows_clean_apply` is a one-shot set by Simple mode's apply-then-reload so that reload doesn't paint the button red while the check re-confirms it. It is set only when `apply_to_game` returned True, and a failed reload clears it.

### Closing stops a running extraction (#471)
`closeEvent` used to leave a running extraction alone, and a closed app left unp4k or unforge running on its own (measured: unforge carried on ~23 s past the exit while Python's exit-time cleanup failed under it, and its ~2 GB stayed in `%TEMP%`). Once every prompt that could call the close off has been answered, `closeEvent` sets `_close_committed` and calls `_request_stops_for_close()` ahead of the unbounded loader wait, so the tool dies at once; last, after the window state is saved, `_stop_workers_for_close()` hides the window and waits (one 180 s deadline for every worker, like `_settle_applied_state_check`) while the worker deletes its working folder. Past the deadline the reference is kept so Qt doesn't destroy a live thread, and the next extraction's sweep removes what is left. It detaches each progress dialog from its worker (`_detach_progress_dialog`) and dismisses it with `cancel()`: a hidden `QProgressDialog` shows itself again while progress keeps arriving, and a plain `hide()` (what Esc does) is undone by its own show timer when the dialog is under 4 s old (measured: back 3.5 s after an Esc at 0.5 s). The extraction slots are bound to their worker (as `_launch_applied_state_check` does) and ignore a released one, and `_close_committed` keeps `_run_dataforge_extraction`, `_run_p4k_extraction`, `_run_enhancements_generation`, `_check_enhancements_freshness` and `_maybe_prompt_dataforge_refresh` from starting anything new: Qt still delivers queued signals after `closeEvent` returns. Enhancement generation's slots are bound and guarded the same way: a finished that arrives after the close committed only reaps the worker and ends a Simple run, so it neither applies to the game nor starts a reload with its modal dialog during exit, and an error then is logged at WARNING with no dialog. Generation is the third worker closing stops (`_WORKERS_STOPPED_ON_CLOSE`): it is asked with the extractions ahead of the loader wait, its dialog is detached and cancelled, and it is waited for under the same 180 s deadline with the window hidden. The generator's `main()` takes `should_cancel` and raises `GenerationStopped` at its next job boundary (after each parse and the XML path index, before each lookup and each generator, and just before the write phase), never during its writes, so every INI is whole: all old if it stopped before writing, all new once the writes began, in which case the run also certifies the set. A stop after `main()` began leaves `.dataforge_stamp` empty, so the next start offers to generate again. Past the deadline the reference is kept, with its own warning. The stop is silent by design (no prompt), so the update installer and Import Settings relaunches, which ignore `close()`'s result, need nothing special.

Esc or the X on the DataForge progress dialog used to hide it while the extraction carried on unseen, which is how a user got to close the window mid-run. The dialog's close guard now asks what to do (`_confirm_stop_dataforge_extraction`: Stop, Run in Background or Cancel, Cancel being the default and what Esc picks). Run in Background (#483) and the lock that makes it safe are under *Run in Background and the job lock* below. **Stop** requests the stop, and the finished slot reports "stopped" rather than "failed" (it reads the worker's own `stopped` record: QThread reports no interruption once a thread has finished, and the slot waits for the thread first). A Simple-mode run can no longer apply, but its page stays busy until the stop has finished and the finished slot ends the run, so the button never looks ready while a click would be turned away. Stop dismisses the dialog for good: `_detach_progress_dialog` disconnects the worker's progress from it and it is deleted, because a hidden `QProgressDialog` shows itself again while progress keeps arriving (measured within a second of Esc or the X; `TestDismissedDialogStaysHidden` keeps the control that shows it). If the run finishes while the question is open, its slot has already moved on to generation, so Stop has nothing to stop, but it still ends a Simple-mode run so nothing is applied to the game (and `_on_enhancements_generation_finished` releases the page whether or not a Simple run is active). The same dialog is handed to enhancement generation, so `_run_enhancements_generation` clears the guard at the hand-off; generation keeps the old hide-and-continue, and closing the window stops it. Esc or the X on the global.ini dialog stops that extraction without asking (`_stop_p4k_extraction_from_dialog`, also a close guard): it is a short job that writes `base.ini` only at its very end, so a stop leaves the old one as it was, and the status bar says "global.ini extraction stopped". It used to hide the dialog while unp4k carried on unseen, and Extract then started a second run that replaced `_p4k_worker`, so closing stopped only the second and left the first unp4k running. `_run_p4k_extraction` now starts nothing while `_p4k_worker` is set, and the stop makes sure that never leaves Extract waiting on a run the user cannot see. Startup, a channel switch and a data-folder change leave their reload to the extraction `_check_p4k_freshness` starts, and only a success used to reload, so they now pass what they do when it is declined (`if_unfinished`: `_finish_startup_load`, `_reload_after_channel_switch`, `_reload_after_data_dir_change`) and the finished slot runs it after a stop or a failure, instead of leaving no strings or the old channel's. A failure shows its error box first, and the finished slot usually runs inside that box's own event loop, so it parks the follow-up (`_p4k_follow_up_after_error`) for `_on_p4k_extract_error` to run once the box has closed rather than stacking a reload or a prompt on top of it. `_run_p4k_extraction` returns whether it started, so a Yes while one is already running carries on as declined at once. A run cut off between the cache wipe and the stamps (a crash, or a close that outlasted its 180 s wait) leaves content with no `.p4k_mtime`; `_maybe_prompt_dataforge_refresh` treats that as stale and prompts, instead of letting it pass for "never extracted". `tests/test_extraction_stop.py` locks this.

### Run in Background and the job lock (#483)
Run in Background dismisses the DataForge dialog for good (`_send_dataforge_run_to_background`: detached from the worker as Stop does, since a hidden `QProgressDialog` comes back while progress keeps arriving), marks the worker `in_background`, and the status bar reports. The finished slot hands that on to `_run_enhancements_generation(background=True)`, which makes no dialog and connects the worker's progress to the status bar only. If the run finished while the question was open, generation has already taken the same dialog over, so Run in Background detaches it from generation instead and the answer still holds. It was tried and dropped before 2.4.0 because the window can be used while the run goes on, which was already true of a generation whose dialog Esc had hidden. So one job runs at a time, and what a job depends on is locked while any job runs, shown or not. The jobs are the three closing stops (`_WORKERS_STOPPED_ON_CLOSE`): a global.ini extraction, a DataForge extraction and a generation. `_job_running()` says whether one runs. `_run_p4k_extraction`, `_run_dataforge_extraction`, `_run_enhancements_generation` (beside an extraction), `_run_enhancements_pipeline`, `_run_simple_apply` and the post-import Apply Now (`_maybe_prompt_post_import_apply`) start nothing while one does, `_check_enhancements_freshness` asks nothing, and a refused extraction, pipeline or Apply Now says why in the status bar. `_refresh_job_lock()`, called wherever a job's worker is set or cleared and when a Simple run starts or ends, locks with one reason (`extract.locked_while_job_runs`): the Config tab's game, data and cache folders, channel, language and Map Language File, its global.ini Extract, the install scan (Verify Install Location, which can save a game folder), Import Settings (whose restart starts the new copy before this one closes) and Check for Updates (the installer relaunches the app), through `ConfigTab.set_data_locations_locked`, which shows the reason in a label under the tab's instructions. The install scan and the update check keep their own busy state, so unlocking leaves either button off while it runs. It also locks the Enhancements tab's Apply Category Changes and Save Tag Changes (`set_changes_locked`: the first renames INIs in the folder a generation writes and starts a reload, the second saves the tags and asks for a regeneration one job at a time would refuse; the checkboxes and the Tag Builder stay free and the change waits for the button) and the Simple page's button, busy with the reason as its tooltip (`_end_simple_run` no longer frees it while a job still runs). A lit button the lock or a running job disables (Generate Enhancements, Save Tag Changes, the Config tab's Extract) keeps a dimmed red (`theme.needs_apply_style`), so a pending change still shows without the button looking clickable. Nets behind the lock: the finished slot checks the run still matches the settings (`_dataforge_run_matches_settings`, the channel and the cache base the worker recorded when it started, compared without making any folder) before it drains `_cleanup_pending_old_cache()` or chains generation, and says why when not (`extract.dataforge_settings_changed`); a language switch during an extraction loads the prose and leaves generation to the extraction's own chain; `ConfigTab._save_game_path` refuses while locked (an install scan finishing during a job could otherwise save one through its results dialog); Import Settings and an update's install refuse while a job runs. `restart_app` (the font size) closes first, so it needs nothing. `tests/test_run_in_background.py` locks this.

### A cut-off generation is offered again at the next start (#476)
The startup check (`_check_enhancements_freshness`) used to ask only whether each enabled enhancement INI existed. A generation cut off part-way (the window closed, the app crashed, a write failed) left every INI there, each whole but the set a mix of old and new, and the next start stayed quiet. Now `EnhancementsGeneratorWorker` empties the `.dataforge_stamp` of the language it generates just before the generator's `main()` (after the patches and the module load, so a failure there keeps a good stamp) and writes it only once `main()` has returned. The check also asks when every file is there but `AppSettings.enhancements_built_from_current_dataforge()` says the set was not built from the current DataForge build: the last run was cut off or failed, or the set came from older game data. It asks that only when the DataForge cache is fresh (`_out_of_date_build_key`): an outdated cache is `_maybe_prompt_dataforge_refresh`'s question, so this one would stack on it or ask again after it was declined, and a cut-off extraction or a cache never extracted has nothing to generate from. In that case the category dialog offers every enabled category, ticked with its plain label, under `extract.outdated_categories_body` ("out of date", with no count: the count's noun says "missing" in several languages). The answer holds for the rest of the session (`_enhancements_prompt_answer`, reset by a channel or data-folder change). Skip is never turned into a run by a later call, such as the one after a global.ini extraction, which used to run the pipeline silently, possibly a DataForge extraction the user had just declined. It is recorded before the dialog opens, because the dialog's event loop can deliver another load, and that call must start nothing. Nothing about the answer is kept on disk, so the question comes back at every start until the set is generated, like the missing-files question. The Generate button stays lit while a ticked category's set is not current, and the language switch (`_language_enhancements_fresh`, English included) uses the same test, so the three never disagree. A run that finishes re-reads this from disk (`set_operation_idle`), so one whose final stamp write failed (`set_enhancements_stamp` only logs that, and the run still succeeds) leaves the button lit over the set the next start will ask about. The worker also captures its folder, the build key and the tag fingerprint when its run starts: reading them when it ended let a channel, data-folder or cache-folder change during a hidden run stamp a set the run never wrote. Closing the window during a generation stops it at its next job boundary (see *Closing stops a running extraction* above), which after `main()` began is one of these cut-off runs, so the next start asks. `tests/test_enhancements_stale_startup.py` locks this.
