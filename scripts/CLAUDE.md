# scripts/CLAUDE.md

Standalone CLI scripts and the build pipeline. See the root `CLAUDE.md` for project context.

## Files

- `generate_enhancements_ini.py` — reads DataForge entity XMLs (no external JSON) → enhancement INI files in cache (ships, components, ship weapons, FPS weapons descriptions, FPS armor weight tags). The ship component generators (shield, radar, cooler, power plant, quantum drive, bomb rack) and `_run_gen_components` are locked by `tests/test_component_generators.py` (#485).
- `extract_components.py` — diffs base.ini against stock vanilla to produce components.ini.
- `gen_commodity_crafting.py` — generates `commodity_crafting_enhancements.ini` with crafting blueprint usage from DataForge XMLs.
- `compare_kraken_fixture.py` — research/reporting: diffs the `kraken_4.7.ini` ground-truth fixture against the generated `mission_rewards_enhancements.ini` to validate blueprint list output. Read-only.
- `diff_bp_kraken.py`, `diff_bp_annotations.py`, `diff_bp_csv_fixture.py` — read-only diagnostics for `[BP]` / `[BP?]` blueprint annotations on mission rewards. Each compares `mission_rewards_enhancements.ini` against a different ground truth (kraken fixture, applied LIVE `global.ini`, `missions_4.7.177.csv` per-variant fixture). Use when blueprint tags regress.
- `diff_base_ini_channels.py` — read-only: diffs cached `base.ini` between two SC channels (e.g. `LIVE` vs `PTU`) and reports added / removed / changed loc keys as a category-bucket summary plus optional full machine-readable list. Defaults to `%USERPROFILE%\Documents\Smart Citizen`; `--user-data` overrides for OneDrive-redirected installs.
- `diff_mission_rewards_channels.py` — companion to `diff_base_ini_channels.py` for the generated `mission_rewards_enhancements.ini`: diffs mission entries between channels and reports adds / removes / changes. Use to verify a CIG balance pass or new mission archetype propagated through the enhancements pipeline across `LIVE` / `PTU`.
- `add_sco_sample.py` — turns SCO crops from `logs/sco_samples` (saved only when the app starts with `SMART_CITIZEN_SCO_SAMPLES` set; named `<...>_<digits>.png`; rename a misread one to the real number or pass `--digits`) into `DIGIT_SAMPLES` entries via `sco_digit_reader.cut_glyphs`. Prints them for review; `--write` adds the new ones to `src/utils/sco_digit_samples.py`, skipping glyphs already there. `--screen-height` for crops from screens other than 1600 px. Locked by `tests/test_add_sco_sample.py`.
- `discord_notify.py` — GitHub Actions release webhook.
- `build/build_exe.py`, `build/build_all.bat`, `build/clean_cache_for_distribution.py` — build pipeline; see `scripts/build/BUILD_INSTRUCTIONS.md`.

## Design decisions

### Every output is written in one step (#476)
`generate_enhancements_ini.py`'s `write_ini` and `_cached_lookup`'s pickles go through `src/utils/atomic_io.py` (`atomic_write_text`, `atomic_writer`), imported through the same `src` shim as `win_paths`: each file is written to a temp file beside it and swapped in with `os.replace`. A generation cut off by a close or a crash used to leave the INI it was writing truncated (`write_text` truncates first), and the next load took half a category for the whole one. When the swap fails, the write raises and the old file stays whole. There is deliberately no fallback to an in-place write. The bytes are unchanged: UTF-8, no BOM, CRLF on Windows. An unreadable pickle is logged at INFO before it is rebuilt, because scitem's rebuild is the longest job in a generation. The shim's `except ImportError` fallback writes in place as before, and runs only when `src/` is missing. `tests/test_generation_writes.py` locks this, with an AST guard against a new in-place write anywhere in the script.

### Stop points in main() (#476)
Closing Smart Citizen stops a running generation. `main()` takes `should_cancel` (the GUI worker passes `isInterruptionRequested`; None, the default, never stops, so the CLI is unchanged) and asks it between jobs: after the base.ini parse, after the English parse, after the XML path index, before each lookup and each generator, and once more just before the write phase, after the loc-string workarounds. When it returns True, `main()` raises `GenerationStopped`, a plain `Exception` like `pak_extractor.ExtractionCancelled` and not a `RuntimeError`, because a stop is not a failure. The worker matches it by class name, since it loads the script afresh for every run, so keep the name. No INI has been written at any of those points (lookup pickles may have been, each one whole through `atomic_writer`). There is deliberately no check inside the write phase: a run that reached it writes every INI, so a stop can never leave a set that is part old and part new, and the worker then certifies it as usual. The lookups and generators are checked one by one only on the serial path (`max_workers=1`, which the GUI always takes); the pool branches, used only by the CLI and tests, get just the check before the writes. A stop takes up to one job, and the uncached scitem lookup is the longest. `tests/test_generation_writes.py` locks the stop points.

### The SCO Order tab's data in crafting_index.json (3.1.0)
`scan_crafting_blueprints(crafting_order=...)` also reads each blueprint's slots while it has the blueprint parsed (`_blueprint_order_facts`: each `CraftingCost_Select` slot's name, first material, amount, minimum quality and the quality ramps under its own `context`, and pick groups where a select needs fewer than it holds), then `_build_crafting_order` resolves materials to commodity keys, stat records in `crafting/craftedproperties` to names (that folder is kept by `DATAFORGE_KEEP_SUBPATHS` since 3.1.0), shares identical curves by index and keeps every blueprint: a material no carryable names becomes `item:<uuid>` when its entity has a name (listed in `mnames`) or `unknown:<uuid>`, which the drawer shows as an unknown material. Dropping those blueprints hid most of the catalogue (NDB-30 among them), which a tester read as an owned-only filter. The item a blueprint makes is named by `_crafted_item_name`, the same chain the mission blueprint lists use: the `CraftingProcess_Creation` entityClass, then `entity_names_by_filename` (the entity file named like the blueprint, since CIG ships some blueprints ahead of the entity link; a name that is still a loc key counts as none), then the file name minus `bp_craft_`, which a `Crafting: N blueprints with no item name` INFO line lists. NDB-30 and the other NDB repeaters were thought to be file-named, so the search could not find them by name. `main()` writes it into `crafting_index.json` as version 2 beside the materials. This changes the bytes of `crafting_index.json` against older code (the materials part is unchanged), so leave that file out of the byte-for-byte comparison above, or compare its `materials` only. The field names follow the public DataForge parsers and still need checking on a LIVE cache. Locked by `tests/test_crafting_order.py`.

### Mining-laser and handheld-salvage stat enhancements
`generate_enhancements_ini.py` writes the text it adds through `_t(english, **values)` (#579): the English text is the key into the selected language's `languages/<language>/enhancements.json` (`src/utils/enhancement_text.py`, imported through the `src` shim with a no-table fallback), so English output is byte for byte what it was and a text with no translation stays English. `main(language=)` sets the table (`_set_text_language`); the worker passes the language it generates, and a CLI run over `cache/lang/<language>/base.ini` reads the language from that path. Data keys stay English (fire-mode and damage dict keys, mission flags, spawn buckets, the breakdown keys tags read) and are translated only where they are written. `--- STATS ---` and `--- EFFECT ---` are read back inside the script, so they are swapped only in `write_ini` (`_localize_separators`). Left as they are on purpose: the four mission section headers and the Rep label (user settings, and `owned_items.py` finds the POTENTIAL BLUEPRINTS header by its text), tags, item names, raw XML values, units and log lines. The lookup pickles hold XML facts only, so no translated text reaches them. A new `_t()` text needs `python tests/test_enhancement_text.py --write` and an entry in every language's table, which `tests/test_enhancement_text.py` enforces.

`generate_enhancements_ini.py` exposes `enhancements_mining_laser` and `enhancements_salvage_tool` (new in 1.4.0) alongside the ship-weapon / FPS-weapon / component generators. The mining-laser generator reads ship-mounted mining heads under `ships/weapons/mining_laser_*.xml` and emits per-mode (Fracture / Extraction) beam stats plus `SEntityComponentMiningLaserParams` modifier overlays. The salvage generator reads `weapons/fps_weapons/grin_*salvage_repair*.xml` and emits per-mode (Repair / Salvage) rate / efficiency / ramp / energy / heat / wear. Both exclude data that needs a `globalParams` UUID resolved into a base entity (base mining-laser power/range, ship-mounted salvage equipment); the scope cut is documented at the function level and locked by `tests/test_mining_salvage_stats.py`.

### Medical consumables (CureLife pens) — a static, non-DataForge category
`enhancements_medical_consumables` (2.2.0) is the one enhancement generator with no DataForge XML dependency. Every other category derives its added text from entity XML stats; the CureLife pens' stock `item_Desc` is pure lore and never states what the item actually does, so there's no stat to extract. `MEDICAL_CONSUMABLE_EFFECTS` is a fixed dict of curated effect-description copy keyed directly off the 7 known loc keys already in base.ini (the base AdrenaPen/CorticoPen/DeconPen/DetoxPen/MedPen/OpioPen/OxyPen — deliberately not the Xtra variants, BoostPen, or VitalityPen). Because it only reads `loc`, it needs no `DATAFORGE_KEEP_SUBPATHS` entry (`pak_extractor.py`), since it reads no XML subtree. It still needs its own checkbox: `ENHANCEMENTS_FILES` / `ENHANCEMENT_LABELS` / `ENHANCEMENT_CATEGORY_FILES` entries in `settings.py` under the key `medical_consumables`, output file `medical_consumables_enhancements.ini`. Locked by `tests/test_medical_consumables.py`.

### FPS armor weight-class tags (#492)
`_run_gen_armor` puts Tag Builder Armor tags (`[H] ADP-mk4 Core`) on the `item_Name*` keys of every wearable under `entities/scitem/characters/human` (armor, `starwear/helmet`, clothing). It runs with the FPS weapons and its entries are written into `fps_weapons_desc_enhancements.ini`, the Gear checkbox's existing file, not a file of their own: a new file would be missing for every Gear user right after upgrading, and the startup freshness check would then ask them all to regenerate. `build_wearable_index` reads each entity's own Name and Description keys and its `SAttachableComponentParams/AttachDef` Type and SubType, loc-free so it is pickle-cached per DataForge build (`wearables` in `_LOOKUP_VERSIONS`). `armor_name_weights` resolves each name key, case-blind for names and descriptions alike, and `_armor_weight` picks the class: the description's "Item Type:" line first (the only place that says Super Heavy, or "Heavy Utility" for the Novikov and Pembroke suits), then an armor slot's SubType where it names a class (the game's own armor class: most racing and flight helmets have the plain "Helmet" SubType and stay bare, while the few in a Light or Medium slot, such as the Interceptor and OMNI-AFS helmets, get that class), then Clothing for clothing and eyewear slots. Where entities share a name, `_ARMOR_WEIGHT_PRECEDENCE` decides, never the file order. `main()` loads the wearables once per run as the `wearables` lookup job (only while the armor tag is on) and shares them through `ctx["wearables"]`, so the armor and mission generators never both write `wearables.pkl`. Armor bullets in mission POTENTIAL BLUEPRINTS lists get the same tag, behind the same "annotate mission descriptions" toggle as component tags: `armor_bullet_names` maps each bare English bullet name to its tagged text, and `_build_blueprint_body_parts` applies it only when a bullet line is written. The tag is never baked into `blueprint_pools`, so that cache key carries no armor segment, and overrides, the drift check, "Set" headers and bullet and section order keep reading bare names. A display name behind two different tags stays bare. The Armor tab offers no "None (space only)" brackets (`tag_builder.NO_NONE_ENCLOSING_CATEGORIES`): the Blueprint Tracker could not strip a one-word armor tag back off a Game.log name. A stored "none" reads as Square in `AppSettings.get_tag_config` and in `_armor_tag_cfg`. Like component tags, the bullets follow the annotate toggle and the Missions enhancements, not the Gear checkbox, so with Gear off a bullet can carry the tag its item name does not. The DataForge pass, not base.ini Name/Desc pairing, because about a fifth of the armor descriptions have no `_Name` of the same stem, and the leftover base.ini names no entity uses are strings the game never shows. Off by default, like the commodity flags (#325), so the scan is skipped until a user ticks Armor > Weight. Locked by `tests/test_armor_weight_tags.py` (item names, classes, settings, the Armor tab) and `tests/test_armor_blueprint_bullets.py` (mission bullets, the pool key, the single wearables load).

### Recco Battaglia's Scan/Mining contracts — "[RS ####]" mission-title tag (4.9+)
`Battaglia_RPT_Scan_*` / `Battaglia_RPT_ScanMine_*` contracts each target 1-3 mineable ores via sibling `MissionProperty` overrides with `extendedTextToken="ResourceType"`/`"ResourceType2"`/`"ResourceType3"` pointing at a `mineabletype_primary_<ore>` loc key. CIG doesn't expose a per-ore "RS" (resonance-signature) number anywhere in DataForge — checked the full PTU 4.9 cache for both the literal values and any per-mineable stat registry, found neither — so `MINEABLE_RS_VALUES` is a curated table sourced from community reference data (MrKraken/StarStrings, `ptu/4.9` branch `mining.ini`, cross-checked against starminersdepot.com's Alpha 4.8 scanner table). `_battaglia_mineable_rs_in()` scans one contractgen XML for matching titles and formats e.g. `[RS 3600/4300/3900]` (multiple ores slash-joined, in ResourceType/2/3 order) — every contract variant sharing a title targets the same ore set, so first-variant-wins. A generation runs it on each file of the contractgen parse it shares with `scan_contract_generators` (see the single-pass entry below), so there is no separate pre-pass. The tag itself is a hardcoded title-loop append gated by the `"rs"` key in `AppSettings.MISSION_TITLE_TAG_KEYS`/`_MISSION_TITLE_TAG_SETTING` (the "General Tags" checkbox pattern — same shape as `[BP]`/`[ACE]`/`[…Rep]`, not the `TagConfig`/`render_tag()` element system). Locked by `tests/test_battaglia_mineable_rs.py`, which reads the tags off a `_run_gen_missions` run.

### A contract the scan cannot read is skipped with a WARNING, and a scan that skips most fails
`scan_contract_generators` reads each contract in its own `try`: one that raises leaves nothing behind, since its blueprints and items are recorded only once its variant is built, and the scan goes on. The line names the contract and the error type at WARNING, as the ship and component generators log a bad file, and not at ERROR, which would open the error box over one odd contract. It used to be at DEBUG, which a normal run does not show (the app logs at INFO unless it starts with `--debug` or `LOG_LEVEL=DEBUG`), so a bug in that block lost everything quietly: one wrong `ContractVariant(...)` call, tried on LIVE, skipped all 1,809 contracts it reached and 787 entries of `mission_rewards_enhancements.ini`, and the run still finished as a success. So more contracts skipped than giving a variant raise `ContractScanFailed` once the walk ends, as does a walk that stops on an error before any contract gave one (a walk that stops later keeps what it read, with its WARNING, as before), which is meant to take a bug here: failing every category of the run is the deliberate trade. `main()` has written no INI yet, so the old set stays whole, the worker leaves `.dataforge_stamp` empty and the next start offers to generate again. The script stays free of `tr()`: the worker matches the class by name, as it does `GenerationStopped`, and words its box with `extract.contract_scan_failed`, or `extract.contract_scan_stopped` for a walk that stopped (a total of 0), so keep the name and its fields. A listing that fails part-way stops the walk too, and `_run_gen_missions` still ends the run with that error itself. Game data should not be able to do it. A spawn count that is not a whole number does not raise (`_spawn_count`): one written as `4.0` reads as 4, and anything else counts as 0 with a WARNING, so the mission loses that spawn line and keeps its variant, because 52% of LIVE's released contracts read a count, and one change to how counts are written would otherwise stop every generation. A failure in a handler's own spawns skips those spawns with a WARNING of its own and keeps its contracts: it used to end the whole scan, with the later files lost and the variants unsorted. A variant is built by keyword, and a sub-contract's comes from its contract's with `_replace(desc_key=...)`, so two values cannot swap and the two cannot drift apart. `tests/test_contract_scan.py` and `tests/test_mission_variant_tuple.py` lock this.

### The ships a mission spawns, and its cooldown (3.1.0)
With the tag tree beside the cache (`DATAFORGE_TAGS_FILE`, see `src/utils/CLAUDE.md` → `dcb_tags.py`), the Hostiles and Friendlies lines of MISSION DETAILS name the ships instead of counting groups. A `SpawnDescription_Ship` asks for ships by tags; `ShipSpawnIndex.pick` gives every ship entity (`build_ship_spawn_facts`: the root's own `<tags>`, `vehicleName` and the file stem, read only as far as `VehicleComponentParams`, pickled as `ship_spawn_tags`) that carries each wanted tag or a child of it and none of the negative tags, by its name in the run's language (English behind it), each once. Tags under `_SPAWN_SETUP_TAG_FAMILIES` (group identifiers, pilot skill, spawn flags, cargo and crew) set a ship up and pick nothing, so they are left out of the match: no ship carries an identifier and each other family is on one ship at most on LIVE. `Missions/MissionModule` and `Missions/UnmannedAI` look alike but are on the escort and unmanned ships they pick, so they count. Many mission records still ask for a ship by its model tag (`Ship/Model/Hammerhead`, `Ship/Model/Constellation_Andromeda`) while the newer AI ships (`aegs_hammerhead_gs_pu_ai_crim`) carry only their series tag, so an option whose model tag (`_MODEL_TAG_PREFIXES`) no ship carries is matched again with the model named by the entity file name, as whole `_`-separated words (`hammerhead` is not found in `hammerheadx`), the option's other tags still counting: that names 76 of LIVE's 206 options that matched nothing. An option still unmatched is named by its tags as a kind of ship (`Very Easy Ninetails ship`: difficulty, then faction, then the rest, each once, the game mode left out, and no second ship after a label that ends in one, `_ship_kind`), with no brackets, which read as a ship that is not there. About 98% of LIVE's ship options name ships. `_extract_spawn_roster` reads a scope's hostile and friendly groups the way `_extract_spawn_counts` classifies them (`_group_bucket`, `_npc_group_total`, shared with it): a ship group is its slots (`SpawnDescription_ShipOptions`, all spawn) of choices (the game picks one), groups that read the same merge with their amounts added (four recipient groups of one ship from one pool are `4x`, and so are two whose ships match but whose tags differ: `_shown_slot` keeps a choice's label only where it shows, which took Headhunters_claimsweep_desc_hard's two `- Prospectors: 2x MISC Prospector` lines to one `4x`), a group whose choice picks nothing is a count, and on-foot groups stay counts (`- Soldiers x6`). Objectives, unknown groups and turrets stay out, as before. `_slot_choices` merges equal ships at different amounts into a range and choices at one amount into one list, and a list reads `2-3x of A, B, or C`, so the count is not read as that many of each. `_format_roster_group` lays a group out on one line when every slot is a single choice and none names `_ONE_LINE_MAX_NAMES` (3) ships or more (`- Wave 2: 3x A, 1x of B or C, and 3x D`), and otherwise one choice per line: `- Hostile Wave, one of:` with its choices two steps in, then each further slot an `and ...` line one step in (`and one of:` with its own choices under it when it has several). On one line, a long list's serial comma ran into the next choice. The indent is no-break spaces (`_ROSTER_INDENT`), so nothing that trims spaces takes it away. `_roster_block` numbers two or more `_WAVE_LABEL` groups `Wave 1`, `Wave 2`, ..., in file order, and a lone wave keeps its label. Two or more `_TARGETS_LABEL` groups in a block with no wave are numbered the same way (a patrol's hotspots: Stand Our Ground's were a run of identical `- Targets:` lines), while target groups beside a wave are not made waves, since they are what the wave guards: on LIVE, 39 blocks are targets only, 44 pair one wave with one target group (a bounty and its escort, which numbering both together would have turned into Wave 1 and Wave 2) and 3 mix more of each. Any other label that repeats in a block, target groups beside a wave among them, is numbered after its label (`Reinforcements 1`, `Reinforcements 2`, `{label} {n}`); a lone group keeps its label. The order is the game file's, not a spawn order anyone has checked. The joins go through `_LIST_JOINS` (names `A or B`, `A, B, or C`; parts `A and B`, `A, B, and C`), three or more from a text of their own (`{rest}, ...`) so a language without the serial comma leaves it out, and every layout word (`{count}x of {ships}`, `{label}, one of:`, `and one of:`, `and {item}`, `Wave {n}`, `{kind} ship`) is translated. A pool of more than `_POOL_AS_TYPE_OVER` (3) ships with a type, the tag label every pick carries, is that type in its wave (`3x Very Hard Criminal Large Combat Ship`), which counts as one name for the one-line rule, so most groups take one line. Each type is named once, after the Hostiles and Friendlies blocks, under `Ship types:` (`_ship_types_block`), in the order the groups name them, its ships biggest first. The Enhancements tab's Ships per type dropdown beside Hostiles (`AppSettings.get_ships_per_type`: 4, 8, 16, 32, 64, 128 or all; handed to `main(ships_per_type=)`, read by `_ships_per_type`, which takes anything else as 8, and kept as `ShipSpawnIndex.per_type`, 0 for all) sets how many a type lists: up to n all of them, and a bigger type `(n - 2) // 2` at each end with the rest counted between them, `(… 7 others)` (`- Hard Criminal Combat Ship: Crusader A1 Spirit, Aegis Vanguard Harbinger, Aegis Vanguard Warden, (… 7 others), Esperia Talon, Esperia Talon Shrike, Anvil Arrow`). 8 is the default: on LIVE 4-8 ships is a third of the Ship types lines, 9-12 only 3% and 13 or more the rest; the biggest type has 77. Size is the bounding-box volume `build_ship_spawn_facts` reads (`biggest_first`): the DataForge records hold no ship mass (it is in the vehicle part files, which are not extracted), and length (the box's y) was tried and ranked worse, a long thin ship such as the Origin 890 Jump outranking a Reclaimer. `_ship_pools` names the typed pools of the groups a description writes before any line is written (`_variant_detail_lines`, `enhancements_mission`), keyed `(type, ships)`, and hands the names down through `_roster_block` and `_format_roster_group` to `_slot_choices` (`_typed_pool` says whether a pool is a type): pools with the same ships are one, and pools that differ but share a type (their tags differ only in what they leave out) are numbered in the order the groups name them (`Criminal ship 1`, `Criminal ship 2`), each listed under Ship types. One label for all of them listed their union: ORS_ShipWaveAt_Desc showed `Criminal ship` as 77 ships where its five pools hold 31 to 59. A type label's tag names go through `_TAG_NAME_FIXES` first, so CIG's `CombatRaiting2` reads `Combat Rating 2`. A pool of 10 ships was listed in full in every wave that named it before (Stand Our Ground's capital pool, five times). The longest description on LIVE is 4.3k characters at 8 and 5.0k at All. The old Simple / All Ship Details dropdown, whose All Ship Details listed every ship inside each wave, is gone, and its setting (`mission_field/hostiles_detail`) is left unread, so everyone starts at 8. The contract scan stores each variant's `roster`, `cooldown` and `ace_chance` on `ContractVariant`. Its spawns come from the contract's mission properties merged with its template's and its handler's (`_merged_properties`: the template's `contractProperties`, found by the contract's `template` GUID and gathered by `_build_template_lookup(properties=)`, then the handler's `contractParams/propertyOverrides`, then the contract's own `paramOverrides/propertyOverrides`, a later one of a `missionVariableName` taking an earlier one's place, two of one name in one place both kept). Every spawn group on LIVE sits in one of these, and 174 released contracts had template groups the contract alone never showed, most of them template aces (the CFP and HeadHunters patrols' `AllEncounters_AcePilot_BP` and their Search and Destroy objects). A contract's spawn groups in no property, and a handler's when the contract has none of its own (`_contract_spawn_scopes`), are still read: there are none on LIVE, but tests and older files place them so. The scopes reach `_extract_spawn_counts` and `_extract_spawn_roster` as a list of `(element, exclude_within)` pairs (`_groups_in`). `_spawn_chances` reads the chance or switch each `_SPAWN_CHANCE_RULES` entry names (`AcePilotChance_BP` for `AcePilot_BP`, `EnableAlliedReinforcements_BP` for `AlliedSpawnDescriptions_BP`, the reinforcement, interdiction and encounter chances, with any prefix carried over; a chance is its float options' weighted mean, a percentage scaled), and `_group_chance` gives each group its property's: a group at 0 is left out of the counts and the ships, and one between 0 and 1 reads `- Ace Pilots (10% chance): ...`. `[ACE]` needs every variant of a title to have an ace for certain, `[ACE?]` takes one that comes only by chance, and the Ace Pilot line reads `Yes`, `10% chance` or `up to 33% chance` (`_ace_chances`, `_ace_line_text`); on LIVE no ace is certain, so 61 titles read `[ACE?]` and none `[ACE]`, where 10 titles with a chance of 0 used to carry a tag. `AmbushChance_BP`, `InvisibleTimer_ReinforcementChance_BP` and the like name no spawn property they could stand for, so they are left alone. `_variant_detail_lines` groups a description's variants by what the lines show, so a line that is the same for every variant names none, and names each group by what tells it apart (`_variant_names`): its star systems (`_is_system_name`, against `_SYSTEM_TOKENS`, since a contract with no system token falls back to its handler's debugName), with the combat rating added where it tells every group that shares those systems apart, the rating alone when all share one system, and a number only where nothing else does, written `#1` so it is not read as part of a region's name (`Hostiles (Stanton, Pyro)`, `Nyx #1`, `Nyx #2`; `Stanton, Pyro / Nyx #1: 15 min; Nyx #2: 1 h`); a group with no name at all keeps `variant 2` (`_variant_suffix`). Pyro's contracts are split into Regions A to D: `_extract_system` keeps a contract's `Region<X>` token in `system_name` (`Pyro RegionB`), and the text names it as `_place_names` does, `Pyro Region B`, a system's several regions as one `Pyro Regions B, C, D`, in the Hostiles headings, the Cooldown line and the POTENTIAL BLUEPRINTS headers (`[Pyro Regions A, B]`, which split by region in code older than 3.1.0). A Regions block right after the flavour text, ahead of POTENTIAL BLUEPRINTS, says where each region those name is (`- Pyro Region B: Bloom; Orbituary, Starlight Service Station`, `_regions_block`), always shown, so the reader meets the regions before any header uses them; `named_regions` collects them from `_variant_detail_lines` (only the groups a heading or the Cooldown line names) and `_build_blueprint_body_parts`. The places come from the mission location templates (`missiondata/pu_locations`, kept in the cache since 3.1.0): `build_location_region_facts` reads each template's tags and strings (pickled as `location_regions`) and `_region_places` reads them with the tag tree: a region's planets are the bodies its caves and outposts are on (a moon counts as its planet, Pyro5a as Pyro V, named from base.ini's `Pyro3=Bloom`), never a station record's, since some carry a stray body tag (Patch City's hangar is tagged Bloom, a Gaslight room Monox); a station is in the regions its main record carries, the shortest-named record with its station tag, named by that record's `Missions/Text/Name` string, so a room tagged for another region does not move it. On LIVE (Nov 2026): A Pyro I, Monox; Checkmate, Patch City. B Bloom; Orbituary, Starlight Service Station. C Pyro IV, Pyro V; Gaslight. D Terminus; Ruin Station. Rat's Nest, Rod's Fuel, Endgame, Dudley & Daughters and Megumi carry no region tag and are on no line, by the owner's choice to follow the game data with no nudges. `_run_gen_missions` sets the places for its run (`_set_region_places`); a cache without the templates or the tag tree gets no block. The cooldown (`_extract_cooldown`) is the handler's `defaultAvailability` (`hasPersonalCooldown`, `personalCooldownTime`, `abandonedCooldownTime`, minutes) with the contract's `paramOverrides` over it, or a pu_missions record's root attributes; it shows on every mission that has availability, `None` with no personal cooldown, and the abandon time only when it differs and is longer than `_ABANDON_SHOWN_OVER` (1 minute, CIG's default: `None (abandon: 1 min)` was on 421 missions). The personal cooldown's random variation (`personalCooldownTimeVariation`) is left out on purpose: the data does not say whether the game adds it or spreads it both ways, and SCMDB leaves it out too. `enhancements_mission` (pu_missions) does the same for one record, its #165 rule dropping hostiles a shared body cannot speak for. The index is set for one missions run by `_run_gen_missions` (`_set_ship_spawns`, as `_set_text_language` sets the text table); without the tag tree, as on a cache extracted before 3.1.0, the Hostiles and Friendlies lines stay counts and the cooldown still shows. A count adds one option per slot, from the smallest to the biggest (`_ship_group_span`, `_slot_options`, shared with `_ship_group_slots`): a SpawnBreakdown value is a number, or `(fewest, most)` when the options differ (`_span`, `_span_value`, `_span_text`), so a Nyx ambush reads `Hostile Wave x3-4` where adding every option read `x6`. `_add_spawn` adds both ends and `_merge_spawn_breakdowns_max` keeps the worst case of each end. Locked by `tests/test_mission_ships.py`, with the variant fields in `tests/test_mission_variant_tuple.py`.

### The [BP Complete] title tag's mission record
The generator never writes `[BP Complete]`: whether a mission is complete depends on the Owned set, which changes between generations, so `MainWindow` weaves the tag in at load time (see `src/utils/CLAUDE.md`, `owned_items.py` and `blueprint_meta.py`). What the generator adds is the record the app cannot work out from the strings: the contractgen title loop in `_run_gen_missions` puts each blueprint title's description keys (`unique_desc_keys`, sorted) in `ctx["mission_blueprint_descs"]`, for every title in `mission_blueprints` whatever the BP Tag switch says, and `main()` writes it with the mission INI as `mission_blueprint_descs.json` (`write_mission_blueprint_descs`, imported through the same `src` shim, through `atomic_io`, keys sorted so two runs match). The pu-only second pass writes no `[BP]`, so it records nothing. `main()` is the only writer: the app only reads the record, and never starts a generation to fill in a missing or old one (see `blueprint_meta.MISSION_BLUEPRINT_DESCS_FILE`). `tests/test_bp_complete_title_tag.py` locks it.

### Mining Compendium journal — per-ore Base Resource Signature line (2.2.0)
`MINEABLE_RS_VALUES` (see the Battaglia entry above for sourcing) has a second consumer: the "Mining Fundamentals #2: Where to Mine" journal entry (`Journal_General_Mining_Compendium_Content`), reformatted by `scan_crafting_blueprints`'s per-mineral block builder into `<EM3>Name</EM3>` / `Locations:` / `Used To Craft:` blocks. Each ore's block now gets a `Base Resource Signature: <EM4>{value}</EM4>` line (inserted right after the name header, before Locations) whenever `MINEABLE_RS_VALUES` has a confirmed value for it; ores without one (the journal lists 35, the table covers 26) are left unchanged, no placeholder. `_MINING_COMPENDIUM_ORE_ALIASES` bridges the one known spelling mismatch between the journal's own prose and the DataForge loc-key convention (`"Savrilium"` in-journal vs `mineabletype_primary_savrillium`). Locked by `TestMiningCompendiumRSTagging` in `tests/test_commodity_journal.py`.

### DataForge XMLs read as few times as possible, and only XML facts in the lookup pickles (#522)
`generate_enhancements_ini.py` parses each XML as few times as it can, and the `.lookups` pickles it reshapes hold facts read from the XML, never text made from base.ini or the Tag Builder config, so each is keyed on the DataForge build alone (`_LOOKUP_VERSIONS` records the shapes). `scitem_lookups` (`_scitem_facts`, the ~24k scitem files) and `blueprint_pools` (`_blueprint_pool_facts`) are turned into names and `[CLASS-Sx-grade]` tags on every run (`_render_scitem_lookups`, and the name loop in `build_blueprint_pool_lookup`), so a Tag Builder change or the annotate toggle re-renders them instead of parsing every scitem XML again. Because those two hold no loc text, the English-loc fallback mark (`en_loc_cache_mark`, for a translated run whose English base.ini is missing) keys only `standings`, the one pickle still built from the loc: a fallback run and the next English run share the facts pickles, and each renders its own names from them. `_component_name_tag` and `_mining_laser_component_tag` read their XML facts through `_component_tag_facts` / `_mining_laser_name_attr` and share the rendering (`_component_name_tag_from_facts`, `_mining_laser_tag_from_name`) with the cached path. The flight controller and armour lookups (`build_controller_lookup`, `build_armor_lookup`) hold the attribute values the ship block shows (`_controller_flight_stats`, `_armor_stats`) instead of lxml trees, still formatted in `enhancements_ship_dataforge`, so an armour value `_fmt` cannot format fails only its ship, as before. Those two are built on every run (about 0.2 s on LIVE) and never pickled: DataForge patches are applied again before every generation without a re-extraction, so a pickle keyed on the DataForge build would keep a patched controller or armour XML's old values until the next extraction. A pickle must hold builtins only: the app loads this script under a module name of its own, so a pickled class of the script would not load. The scitem walk finds the magazine with lxml's own tag filter when a file is ASCII-compatible and holds no `__polymorphicType` (`_holds_no_poly_type_attr`), which is every file on LIVE today, and keeps the per-element `_poly_type` loop otherwise. `_run_gen_missions` reads each pu_missions XML once (`_scan_pu_missions`: the #165 choice between a body with and without hostiles waits until every file is read) and each contractgen XML and contract template once (`scan_contract_generators` takes `roots` and `template_lookup`; the Battaglia RS tags and the calculated-reward diagnostic run on each root just before it, their errors held and raised where their own calls raised them, and the walk is finished for them if it stops early; a failure listing the files still ends the run). `scan_crafting_blueprints` parses each blueprint once, reads a carryable only when its filename names a commodity, and lowercases the loc keys once (`_commodity_loc_keys`), for the commodity entries, the Mining Compendium and the SCO crafting index (#474) alike. The hot loops parse through `_parse_xml_file` (the bytes read in one call, then `ET.fromstring`: the same parser and errors as `ET.parse`, and faster on Windows). On a LIVE cache (`main()` with `max_workers=1`, medians of three interleaved runs of the 3.0.0 code with #474 and #477 and of #522's final code, each with its own `src/`) a regeneration went from 11.9 s to 6.3 s, a components Tag Builder change from 31.0 s to 6.2 s, and the first generation after an extraction from 33.8 s to 24.0 s, which stays bound by parsing the ~1 GB of scitem XML once; the peak working set fell from about 320 MB to 190 MB. None of this changes a byte of output: every file the generator writes (the nine INIs and `crafting_index.json`) matched the unchanged code on a real LIVE cache, cold, warm, after a components change, with non-default components, commodities and armor configs with the annotate toggle on and off, and on a run whose English base.ini is missing. Run that comparison again for any change here. Two outputs used to depend on the string hash seed, because each took the order of a set: three courier titles in `mission_rewards_enhancements.ini` (`_derive_route_fragment` took the first of a set of bodies) and the order of the materials in `crafting_index.json` (`scan_crafting_blueprints` met each blueprint's materials in set order, #474's code). Both now sort (#522), so two runs of this code match whatever the seed. An endpoint some of a title's agreeing bodies write bare and others with `|Address` also takes the `|Address` form (`_agreed_endpoint_tokens`), so a route follows the tokens rather than which body's greeting sorts first; on a LIVE cache that changed one title against the sorting alone, `Covalex_courier_dc_small_title_001`, whose `Dropoff1` was bare. Against code from before those fixes, set `PYTHONHASHSEED=0` on both sides, and expect those two to differ: the titles give an endpoint their bodies write both bare and with `|Address` its `|Address` form, where the old code gave one form or the other at random, and the index holds the same JSON with its materials in a fixed order. Locked by `tests/test_generator_single_pass.py` and `tests/test_mission_route_title.py` (the route for every order of the bodies, and the `|Address` form), and by `tests/test_battaglia_mineable_rs.py`, `tests/test_calculated_reward_titles.py` and `tests/test_commodity_journal.py`, which read the RS tags, the calculated-reward titles and the blueprint material UUIDs off the code a generation runs: the separate scans they used to call were removed.
