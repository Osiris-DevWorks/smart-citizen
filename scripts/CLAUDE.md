# scripts/CLAUDE.md

Standalone CLI scripts and the build pipeline. See the root `CLAUDE.md` for project context.

## Files

- `generate_enhancements_ini.py` — reads DataForge entity XMLs (no external JSON) → enhancement INI files in cache (ships, components, ship weapons, FPS weapons descriptions, FPS armor weight tags). The ship component generators (shield, radar, cooler, power plant, quantum drive, bomb rack) and `_run_gen_components` are locked by `tests/test_component_generators.py` (#485).
- `extract_components.py` — diffs base.ini against stock vanilla to produce components.ini.
- `gen_commodity_crafting.py` — generates `commodity_crafting_enhancements.ini` with crafting blueprint usage from DataForge XMLs.
- `compare_kraken_fixture.py` — research/reporting: diffs the `kraken_4.7.ini` ground-truth fixture against the generated `mission_rewards_enhancements.ini` to validate blueprint list output. Read-only.
- `diff_bp_kraken.py`, `diff_bp_annotations.py`, `diff_bp_csv_fixture.py` — read-only diagnostics for `[BP]` / `[BP?]` blueprint annotations on mission rewards. Each compares `mission_rewards_enhancements.ini` against a different ground truth (kraken fixture, applied LIVE `global.ini`, `missions_4.7.177.csv` per-variant fixture). Use when blueprint tags regress.
- `diff_base_ini_channels.py` — read-only: diffs cached `base.ini` between two SC channels (e.g. `LIVE` vs `PTU`) and reports added / removed / changed loc keys as a category-bucket summary plus optional full machine-readable list. Defaults to `%USERPROFILE%\Documents\Smart Citizen`; `--user-data` overrides for OneDrive-redirected installs.
- `diff_mission_rewards_channels.py` — companion to `diff_base_ini_channels.py` for the generated `mission_rewards_enhancements.ini`: diffs mission entries between channels and reports adds / removes / changes. Use to verify a CIG balance pass or new mission archetype propagated through the enhancements pipeline across `LIVE` / `PTU`.
- `add_sco_sample.py` — turns SCO crops from `logs/sco_samples` (named `<...>_<digits>.png`; rename a misread one to the real number or pass `--digits`) into `DIGIT_SAMPLES` entries via `sco_digit_reader.cut_glyphs`. Prints them for review; `--write` adds the new ones to `src/utils/sco_digit_samples.py`, skipping glyphs already there. `--screen-height` for crops from screens other than 1600 px. Locked by `tests/test_add_sco_sample.py`.
- `discord_notify.py` — GitHub Actions release webhook.
- `build/build_exe.py`, `build/build_all.bat`, `build/clean_cache_for_distribution.py` — build pipeline; see `scripts/build/BUILD_INSTRUCTIONS.md`.

## Design decisions

### Every output is written in one step (#476)
`generate_enhancements_ini.py`'s `write_ini` and `_cached_lookup`'s pickles go through `src/utils/atomic_io.py` (`atomic_write_text`, `atomic_writer`), imported through the same `src` shim as `win_paths`: each file is written to a temp file beside it and swapped in with `os.replace`. A generation cut off by a close or a crash used to leave the INI it was writing truncated (`write_text` truncates first), and the next load took half a category for the whole one. When the swap fails, the write raises and the old file stays whole. There is deliberately no fallback to an in-place write. The bytes are unchanged: UTF-8, no BOM, CRLF on Windows. An unreadable pickle is logged at INFO before it is rebuilt, because scitem's rebuild takes about 85 s. The shim's `except ImportError` fallback writes in place as before, and runs only when `src/` is missing. `tests/test_generation_writes.py` locks this, with an AST guard against a new in-place write anywhere in the script.

### Stop points in main() (#476)
Closing Smart Citizen stops a running generation. `main()` takes `should_cancel` (the GUI worker passes `isInterruptionRequested`; None, the default, never stops, so the CLI is unchanged) and asks it between jobs: after the base.ini parse, after the English parse, after the XML path index, before each lookup and each generator, and once more just before the write phase, after the loc-string workarounds. When it returns True, `main()` raises `GenerationStopped`, a plain `Exception` like `pak_extractor.ExtractionCancelled` and not a `RuntimeError`, because a stop is not a failure. The worker matches it by class name, since it loads the script afresh for every run, so keep the name. No INI has been written at any of those points (lookup pickles may have been, each one whole through `atomic_writer`). There is deliberately no check inside the write phase: a run that reached it writes every INI, so a stop can never leave a set that is part old and part new, and the worker then certifies it as usual. The lookups and generators are checked one by one only on the serial path (`max_workers=1`, which the GUI always takes); the pool branches, used only by the CLI and tests, get just the check before the writes. A stop takes up to one job, and the uncached scitem lookup is the longest at about 85 s. `tests/test_generation_writes.py` locks the stop points.

### Mining-laser and handheld-salvage stat enhancements
`generate_enhancements_ini.py` exposes `enhancements_mining_laser` and `enhancements_salvage_tool` (new in 1.4.0) alongside the ship-weapon / FPS-weapon / component generators. The mining-laser generator reads ship-mounted mining heads under `ships/weapons/mining_laser_*.xml` and emits per-mode (Fracture / Extraction) beam stats plus `SEntityComponentMiningLaserParams` modifier overlays. The salvage generator reads `weapons/fps_weapons/grin_*salvage_repair*.xml` and emits per-mode (Repair / Salvage) rate / efficiency / ramp / energy / heat / wear. Both exclude data that needs a `globalParams` UUID resolved into a base entity (base mining-laser power/range, ship-mounted salvage equipment); the scope cut is documented at the function level and locked by `tests/test_mining_salvage_stats.py`.

### Medical consumables (CureLife pens) — a static, non-DataForge category
`enhancements_medical_consumables` (2.2.0) is the one enhancement generator with no DataForge XML dependency. Every other category derives its added text from entity XML stats; the CureLife pens' stock `item_Desc` is pure lore and never states what the item actually does, so there's no stat to extract. `MEDICAL_CONSUMABLE_EFFECTS` is a fixed dict of curated effect-description copy keyed directly off the 7 known loc keys already in base.ini (the base AdrenaPen/CorticoPen/DeconPen/DetoxPen/MedPen/OpioPen/OxyPen — deliberately not the Xtra variants, BoostPen, or VitalityPen). Because it only reads `loc`, it's exempt from `CATEGORY_SUBTREES` (`dataforge_diff.py`) and `DATAFORGE_KEEP_SUBPATHS` (`pak_extractor.py`) — there's no XML subtree whose freshness would matter. It still needs its own checkbox: `ENHANCEMENTS_FILES` / `ENHANCEMENT_LABELS` / `ENHANCEMENT_CATEGORY_FILES` entries in `settings.py` under the key `medical_consumables`, output file `medical_consumables_enhancements.ini`. Locked by `tests/test_medical_consumables.py`.

### FPS armor weight-class tags (#492)
`_run_gen_armor` puts Tag Builder Armor tags (`[H] ADP-mk4 Core`) on the `item_Name*` keys of every wearable under `entities/scitem/characters/human` (armor, `starwear/helmet`, clothing). It runs with the FPS weapons and its entries are written into `fps_weapons_desc_enhancements.ini`, the Gear checkbox's existing file, not a file of their own: a new file would be missing for every Gear user right after upgrading, and the startup freshness check would then ask them all to regenerate. `build_wearable_index` reads each entity's own Name and Description keys and its `SAttachableComponentParams/AttachDef` Type and SubType, loc-free so it is pickle-cached per DataForge build (`wearables` in `_LOOKUP_VERSIONS`). `armor_name_weights` resolves each name key, case-blind for names and descriptions alike, and `_armor_weight` picks the class: the description's "Item Type:" line first (the only place that says Super Heavy, or "Heavy Utility" for the Novikov and Pembroke suits), then an armor slot's SubType where it names a class (the game's own armor class: most racing and flight helmets have the plain "Helmet" SubType and stay bare, while the few in a Light or Medium slot, such as the Interceptor and OMNI-AFS helmets, get that class), then Clothing for clothing and eyewear slots. Where entities share a name, `_ARMOR_WEIGHT_PRECEDENCE` decides, never the file order. `main()` loads the wearables once per run as the `wearables` lookup job (only while the armor tag is on) and shares them through `ctx["wearables"]`, so the armor and mission generators never both write `wearables.pkl`. Armor bullets in mission POTENTIAL BLUEPRINTS lists get the same tag, behind the same "annotate mission descriptions" toggle as component tags: `armor_bullet_names` maps each bare English bullet name to its tagged text, and `_build_blueprint_body_parts` applies it only when a bullet line is written. The tag is never baked into `blueprint_pools`, so that cache key carries no armor segment, and overrides, the drift check, "Set" headers and bullet and section order keep reading bare names. A display name behind two different tags stays bare. The Armor tab offers no "None (space only)" brackets (`tag_builder.NO_NONE_ENCLOSING_CATEGORIES`): the Blueprint Tracker could not strip a one-word armor tag back off a Game.log name. A stored "none" reads as Square in `AppSettings.get_tag_config` and in `_armor_tag_cfg`. Like component tags, the bullets follow the annotate toggle and the Missions enhancements, not the Gear checkbox, so with Gear off a bullet can carry the tag its item name does not. The DataForge pass, not base.ini Name/Desc pairing, because about a fifth of the armor descriptions have no `_Name` of the same stem, and the leftover base.ini names no entity uses are strings the game never shows. Off by default, like the commodity flags (#325), so the scan is skipped until a user ticks Armor > Weight. Locked by `tests/test_armor_weight_tags.py` (item names, classes, settings, the Armor tab) and `tests/test_armor_blueprint_bullets.py` (mission bullets, the pool key, the single wearables load).

### Recco Battaglia's Scan/Mining contracts — "[RS ####]" mission-title tag (4.9+)
`Battaglia_RPT_Scan_*` / `Battaglia_RPT_ScanMine_*` contracts each target 1-3 mineable ores via sibling `MissionProperty` overrides with `extendedTextToken="ResourceType"`/`"ResourceType2"`/`"ResourceType3"` pointing at a `mineabletype_primary_<ore>` loc key. CIG doesn't expose a per-ore "RS" (resonance-signature) number anywhere in DataForge — checked the full PTU 4.9 cache for both the literal values and any per-mineable stat registry, found neither — so `MINEABLE_RS_VALUES` is a curated table sourced from community reference data (MrKraken/StarStrings, `ptu/4.9` branch `mining.ini`, cross-checked against starminersdepot.com's Alpha 4.8 scanner table). `_build_battaglia_mineable_rs_tags()` is a standalone pre-pass (same shape as `_build_template_lookup`/`_build_random_phase_templates`) that scans contractgen XML for matching titles and formats e.g. `[RS 3600/4300/3900]` (multiple ores slash-joined, in ResourceType/2/3 order) — every contract variant sharing a title targets the same ore set, so first-variant-wins. The tag itself is a hardcoded title-loop append gated by the `"rs"` key in `AppSettings.MISSION_TITLE_TAG_KEYS`/`_MISSION_TITLE_TAG_SETTING` (the "General Tags" checkbox pattern — same shape as `[BP]`/`[ACE]`/`[…Rep]`, not the `TagConfig`/`render_tag()` element system). Locked by `tests/test_battaglia_mineable_rs.py`.

### Mining Compendium journal — per-ore Base Resource Signature line (2.2.0)
`MINEABLE_RS_VALUES` (see the Battaglia entry above for sourcing) has a second consumer: the "Mining Fundamentals #2: Where to Mine" journal entry (`Journal_General_Mining_Compendium_Content`), reformatted by `scan_crafting_blueprints`'s per-mineral block builder into `<EM3>Name</EM3>` / `Locations:` / `Used To Craft:` blocks. Each ore's block now gets a `Base Resource Signature: <EM4>{value}</EM4>` line (inserted right after the name header, before Locations) whenever `MINEABLE_RS_VALUES` has a confirmed value for it; ores without one (the journal lists 35, the table covers 26) are left unchanged, no placeholder. `_MINING_COMPENDIUM_ORE_ALIASES` bridges the one known spelling mismatch between the journal's own prose and the DataForge loc-key convention (`"Savrilium"` in-journal vs `mineabletype_primary_savrillium`). Locked by `TestMiningCompendiumRSTagging` in `tests/test_commodity_journal.py`.
